# Общие правила для всех проектов

Действуют в любом проекте; `CLAUDE.md` проекта главнее.

## Язык

- С пользователем — только по-русски: ответы, вопросы, пояснения, планы,
  отчёты.
- Коммит-сообщения, документация, комментарии и докстринги — по-русски,
  если в проекте не заведено иное; в чужом проекте, который ведётся
  по-английски, сохраняется язык проекта.
- Код и идентификаторы (модули, классы, функции, переменные, ключи
  конфигурации) — по-английски; технические термины и названия —
  в оригинальном написании.
- В OpenSpec структурные заголовки и SHALL/MUST/MAY — по-английски,
  содержание — по-русски.

## Качество русского языка

- Писать по-русски, а не калькой с английского: не «сетевая
  неприятность», а «обрыв связи»; не «молча не находит», а «не находит
  и не сообщает об ошибке»; не «кадры двух природ», а «кадры двух видов».
- Не заимствовать слово, у которого есть русский эквивалент:
  «провижининг» — «создание учётных записей», «спайк» — «пробная
  задача», «спека» — «спецификация».
- В спецификациях и проектных документах — нейтральные формулировки,
  без разговорных оборотов («не дерутся за вызов», «упрёмся
  в производительность»).
- Термины — единообразно: неправильное поведение программы — «дефект»,
  `import` — «импортирует». Слова нет в словаре проекта — взять
  общепринятое, нет общепринятого — спросить.
- В документах нет «коллег», «мы», «нас», «они»: есть проект, его
  код, окружение, ветки и задачи. Правила и сведения адресуются
  проекту («правила проекта», а не «правила для коллег»), линии —
  по имени ветки («ветка `dev`», а не «линия коллег»). Люди —
  по роли или по имени: разработчики, тестировщики, девопсы,
  администраторы, руководство, бизнес. Обсуждение — предметно
  и с адресатом по теме: код и тесты — с разработчиками, стенды
  и конвейер — с девопсами, сроки и приоритеты — с руководством,
  поведение продукта — с бизнесом.
- После длинного документа — отдельный проход по формулировкам.

## Передача работы между сессиями

- Точка входа в сессию — раздел «Текущая работа» файла `todo.local.md`
  в корне репозитория, в `.gitignore`, у каждой машины свой: снимок
  состояния, а не журнал; состав — в навыке `/handoff`.
- Хук `~/.claude/hooks/session-handoff.sh` при старте отдаёт модели
  снимок и перечень `docs/open-questions/`, пользователю — выжимку
  (нужен `jq`), а при выходе отмечает сессию, которая меняла репозиторий
  без `/handoff`. Проектная копия хука и навыка в `.claude/` заменяет
  пользовательскую и служит источником правил.
- Сообщение о сессии без `/handoff`: восстановить снимок по `git log`
  и состоянию дерева либо `claude --resume <идентификатор>`, затем
  `/handoff`.
- Вывод хука заканчивается строкой «Конец сводки.»; нет её — сказать
  пользователю, что вывод обрезан.
- Сессия начинается с вопросов из снимка.
- В конце сессии снимок переписывает `/handoff`.
- Вопрос, который нельзя решить сейчас из-за внешних обстоятельств или
  неизвестного срока, — файлом в `docs/open-questions/` с условием
  пересмотра (шаблон — `README.md` каталога). В `todo.local.md` — только
  вопросы к пользователю, мешающие ближайшей работе.
- Решений и требований в снимке нет — только ссылки; ход изменения
  OpenSpec — ссылкой на его `tasks.md`.

## Документация проекта

- Одно сведение хранится в одном месте, в остальных — ссылка
  относительным путём.
- Куда что идёт:
  - проверяется автоматически — спецификация OpenSpec
    (`openspec/specs/`, обоснование активного изменения — его
    `design.md`);
  - выбор инструмента, процесса или стека между вариантами — запись
    в `docs/decisions/`;
  - событие без выбора — коммит;
  - вопрос без решения — `docs/open-questions/`;
  - устройство, руководства, разборы, которые не выводятся из кода, —
    остальные документы `docs/`, указатель — `docs/README.md`;
  - текущая работа и очередь — `todo.local.md`, только ссылки;
  - файл правил агентов (`CLAUDE.md`, `AGENTS.md`) — только то, что
    нужно в каждой сессии: соглашения, команды, запреты; подробности —
    ссылкой на `docs/`.
- Запись решения — Y-statement: «в условиях …, учитывая …, выбрано …,
  чтобы …, ценой …» в одно-три предложения; варианты — по строке;
  пересмотр — одной строкой; не длиннее страницы. Имя
  `NNNN-тема-латиницей.md`, указатель — `docs/decisions/README.md`
  проекта, он правится вместе с записями. Шаблон и обоснование — там же.
- Записи решений редактируются, как любой документ: изменившееся
  решение правится в своей записи тем же изменением, которое его
  изменило, историю хранит git; новая запись — для нового решения,
  а не для поправки прежнего. Решённый открытый вопрос переезжает
  в запись или спецификацию, файл вопроса удаляется.
- В записях, правилах и документах нет дат поручений, цитат, хронологии,
  номеров сборок и хешей; документ описывает нынешнее состояние,
  устаревший текст правится тем же изменением, которое сделало его
  неверным.
- Журнал сделанного и файлы-сводки сессий не заводятся: историю хранят
  git и архив OpenSpec.
- Имена файлов документации — латиницей, слова через дефис.
- Факт о системе перед записью проверяется по живому состоянию:
  командой, файлом, журналом.

## Вопросы к пользователю

- Задача выполняется самостоятельно до конца; вопросы копятся
  и задаются после всего, что от ответа не зависит. Сразу спрашивать
  только перед необратимым: удаление данных пользователя, необратимая
  операция во внешней системе.
- Задачи, принятые в обсуждении без вопросов, начинаются сразу.
- Проверяемое командой, запуском программы, через D-Bus или сокет,
  по журналу проверять самому; пользователю — только нажатия клавиш,
  действия мышью и оценку вида на экране.
- Решённое не переспрашивается. Перед вопросом искать ответ
  в `docs/decisions/` (запись по теме — целиком), спецификациях OpenSpec
  и `design.md`, `todo.local.md`, `docs/open-questions/`, памяти,
  `git log -p -S'<тема>'` и репликах пользователя в транскриптах
  `~/.claude/projects/<проект>/*.jsonl` (`"type":"user"` со строковым
  `content`). Вывод субагента «не решено» перепроверять по транскриптам.
- Решения нигде нет — обсудить с пользователем, а не принимать самому.
  Самому — только подготовка фактов, механическая работа и уже решённые
  шаги.
- Перечень вопросов в рабочем документе или отчёте субагента —
  не источник правды: перед вопросом сверить по `git log`, что правилось
  позже. Устаревший перечень исправить сразу, решённое заменить ссылкой
  на запись.
- Вопросы — по одному: коротко понимание, затем тот вопрос, от которого
  зависят остальные, по возможности на примере из системы пользователя;
  следующий — после ответа. Выясняемое по коду, конфигу или спецификации
  не спрашивается.
- Вопрос задаётся с вариантами ответа на выбор (инструмент
  `AskUserQuestion`): два-четыре взаимоисключающих варианта с кратким
  следствием каждого, рекомендуемый — первым с пометкой; свободный
  ответ остаётся возможным. Вопрос в прозе без вариантов — только когда
  варианты неизвестны и их нельзя составить по системе пользователя.

## Где закрепляются правила работы

- Поправку пользователя к поведению агента, годную для любого проекта,
  записать в этот файл, правило одного проекта — в `CLAUDE.md` проекта,
  а не в память.
- В памяти — сведения (обстоятельства проекта, доступы, решения
  по предметной области), не правила.

## OpenSpec

- Действует там, где OpenSpec заведён; без просьбы не заводить.
- Изменение OpenSpec — когда добавляется или меняется наблюдаемое
  поведение; спецификация и код правятся одним изменением. Исправление,
  возвращающее поведение к спецификации, правка документации,
  переименование, обновление зависимостей и разовая настройка — коммитом.
- Перед правкой поведения сверяться со спецификацией:
  `openspec list --specs`, `openspec show <имя>`.
- Решение изменения — в его `design.md`; выбор шире изменения — записью
  в `docs/decisions/`, в `design.md` — ссылка.
- Ход работы — только в `tasks.md` изменения.
- Готовое изменение: `openspec validate <имя> --strict`, затем
  `openspec archive <имя> -y`. Незавершённых задач к архивации нет:
  выполнены, перенесены в `todo.local.md` или в `docs/open-questions/`.
- Язык артефактов — поле `context` в `openspec/config.yaml`.

## Устройство кода

- Таймеры, такты и опрос по расписанию запрещены: всё делается
  по событиям от источника (ожидание процесса, уведомления файловой
  системы, подписка).
- Намерение поставить таймер обсуждается с пользователем до кода.
- Таймер без источника событий (датчики, внешний интерфейс без
  уведомлений) — временное решение: причина и условие замены —
  в документации проекта, над кодом — комментарий с меткой `WARNING`.
- Таймер, для которого источник событий есть, заменяется сразу.
  `FIXME` — только след найденного таймера в чужом коде, снимается
  заменой.
- Срок ожидания в тестах и оснастке рассчитывается от замеренной
  длительности операции на самом медленном стенде конвейера с тройным
  запасом, а не от рабочей станции; замер, стенд и расчёт — в комментарии
  у константы. Нестабильность по срокам сначала проверяется замером
  на стенде (скорость одного ядра, длительность операции), а не по loadavg.

## Ветви, pull request'ы и конвейер

- Пока пакет задач не выполнен, pull request'ов нет: каждая задача —
  своя ветвь и коммиты, ветвь можно отправить в origin как копию, но
  ворота конвейера по ней не ждут и не запускают.
- Когда задачи исчерпаны, ветви сливаются в одну местную ветвь, на ней
  выполняются все шаги конвейера локально (проверки, типы, полный набор
  тестов), и только после зелёного прогона открывается один общий
  pull request.
- Обычный push не должен ничего собирать в конвейере; сборку запускает
  только pull request в целевую ветвь.
- Массовое изменение (одно правило на много файлов, переработка
  по группам, несколько навыков или сценариев одной темы) идёт одним
  pull request'ом, а не серией по файлу или задаче: ветви задач
  сливаются в одну, как описано выше.
- Изменение, затрагивающее несколько репозиториев, выходит только
  набором: группой ветвей с общим манифестом, которая принимается
  и выкатывается вместе (в монорепозитории — release-sets). Отдельные
  pull request'ы по репозиториям не открываются, даже если часть
  готова раньше.
- Проектное правило (например, `.claude/rules/` проекта) уточняет
  имена ветвей и состав прогона, но не отменяет этот порядок.
- Этот раздел — порядок разработки на этой машине; в `CLAUDE.md`,
  `AGENTS.md` и `.claude/rules/` репозиториев он не переносится:
  у других разработчиков может быть свой порядок.

## Починка падающего набора тестов

- На местном стенде полный набор не гоняется многократно: один прогон
  до первого падения, упавший тест чинится прогонами только его, затем
  прогон продолжается со следующего теста. Три полных прогона
  на нестабильность — только когда всё зелёное. Прогоны конвейера идут
  целиком, как настроены.
- Параллельность местного прогона — как в конвейере: число
  исполнителей, наборы файлов одновременно.
- Исправления сводятся в один коммит на репозиторий перед отправкой.

## Повышение привилегий

- Команда с правами root запускается самим агентом и только так:
  `sudo -A -p '<зачем нужны права, по-русски>' команда`; пояснение
  обязательно, знаков процента в нём нет.
- Пароль спрашивает окно Quickshell askpass
  (`~/.local/bin/handmade-scripts/sudo-askpass`, путь — в `/etc/sudo.conf`
  и `SUDO_ASKPASS`). `pkexec`, `su`, pinentry, zenity, rofi, отдельный
  терминал и просьба выполнить команду вручную запрещены.
- Окно не открылось — чинить окно, а не искать обход.
- Окно askpass не закрывать принудительно и не завершать ждущий
  `sudo`: окно, закрытое без ответа, и пустой ответ засчитываются
  pam_faillock как неудачный вход, три подряд блокируют `sudo` на
  10 минут независимо от пароля. Ждущий `sudo` — сказать пользователю,
  в каком окне ввести пароль; сразу несколько окон не открывать.
  Проверка блокировки — `faillock --user $USER`, сброс требует root.
- pacman — с `--noconfirm`; удаление пакетов и данных — списком и только
  по явному решению пользователя.

## Субагенты

- Поставленная задача выполняется в фоновом субагенте; основная сессия
  ставит задачу, принимает и проверяет результат, отчитывается.
  В основной сессии остаются разговор, вопросы, координация и одно-два
  действия на решающем шаге. Основная сессия на Fable сама выполняет
  только команды без правки файлов (git, проверки состояния, запуск
  навыков); любая правка файлов, даже в пару строк, — субагенту
  на Sonnet с точной запиской: ход Fable дороже всей задачи Sonnet.
  Поиск причины замеченного недочёта — сразу задача субагенту.
- Пакет связанных задач, среди которых есть непосильные для Sonnet,
  ставится одному координатору на Opus (в отдельном workspace через
  `/duty:dispatch`, где он есть): координатор делит пакет на подзадачи
  и раздаёт их своим субагентам (Sonnet — рутина, Opus — сложное), сам
  код не пишет, сводит ветви, прогоняет проверки, задаёт вопросы
  пользователю у себя и возвращает один отчёт с таблицей проверок.
  Глубже одного уровня под координатором субагенты не вкладываются.
  Независимые мелкие задачи координатора не требуют — их раздаёт
  основная сессия напрямую.
- В проекте с плагином `duty` задача по его критерию выноса идёт через
  `/duty:dispatch` по умолчанию, без вопроса пользователю, если обратима;
  модель — по лесенке навыка; основная сессия её не выполняет и не
  поручает субагенту Agent.
- Мерило — расход токенов: задача, которую дешевле сделать самому, чем
  передать субагенту весь нужный контекст (несколько команд по уже
  известным фактам), делается в основной сессии; правки файлов этим
  мерилом не оправдываются, см. выше.
  Субагенту — то, что требует чтения многих файлов, долгих прогонов или
  разбора, который раздул бы контекст основной сессии.
- Числа одновременных субагентов предел не ограничивает. Задача,
  которая не мешает идущим и обратима, запускается без вопроса.
- Модель называется явно при каждом запуске и выбирается по стоимости
  токенов: самая дешёвая, которой хватит для задачи. Рутинная задача
  (поиск, правка по образцу, прогон проверок и разбор вывода, сбор
  сведений, настройка через REST, правка документов по готовому
  решению) — `model: sonnet`; `model: opus` — только там, где нужен
  разбор причин, проектирование или нетривиальный код. Сомнение
  решается в пользу более дешёвой модели.
- Fable субагентом не запускается, в том числе через
  `subagent_type: fork`. Задача слишком сложна для Opus или требует
  оркестрации — предложить пользователю Fable (или Fable с субагентами
  на Opus) с объяснением; запуск — после согласия.
- Перед запуском субагента с тестами, сборками или стендами проверить
  `/proc/loadavg` и `free`: загрузка за минуту ниже числа ядер, доступной
  памяти не меньше четверти; иначе очередь не стартует. Субагенту
  передаётся предел параллельности (`-n`, число экземпляров,
  `CARGO_BUILD_JOBS`).
- Ожидать фоновый процесс по PID (`while kill -0 "$pid"`) или
  по файлу-отметке, а не циклом `until ! pgrep -f '<текст>'`. Перед отчётом
  субагент завершает свои циклы ожидания и фоновые оболочки.
- Останавливать только свои процессы по известным PID; `pkill` по имени,
  `killall`, `kill` родителям найденных `sleep` и любое завершение
  по образцу запрещены.
- Контекст субагента превысил 500 000 токенов и осталось больше
  ~20 % сделанного — в безопасной точке (закоммиченный шаг, остановленные
  процессы) завершить работу запиской о передаче: цель, сделанное
  с хешами, где остановился, следующие шаги, команды проверки, принятые
  решения. Остался последний шаг — довести самому. Оценку назвать
  в отчёте; условие передаётся каждому долгому субагенту. Основная
  сессия поступает так же и продолжает в новой сессии (`/new`).
- `Co-Authored-By` в коммитах и pull request'ах называет модель, которая
  делала работу; историю ради подписи не переписывают.
