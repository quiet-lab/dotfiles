# Ограничивать ли размер сегмента TCP для трафика туннеля `amn0`

## Вопрос

Ставить ли в таблицу `inet amn` ограничение размера сегмента TCP по MTU `amn0` для всех соединений, помеченных в туннель.

## Что мешает решить сейчас

Правка меняет весь трафик туннеля, через который работают агенты
и браузеры; решение о ней за пользователем, а замеров, кроме одного
сайта, нет.

## Условие пересмотра

Ещё один сайт из набора `zones` перестал открываться на рукопожатии TLS или пользователь решил вопрос.

## Контекст

- Адреса AUR (`aur.archlinux.org`, 209.126.35.78) входят в набор `zones`
  (интервал 209.122.0.0–209.126.75.255 из подсетей США). Соединение,
  помеченное в туннель, устанавливается, HTTP без TLS отвечает (`301`
  за 0,2 с), а HTTPS обрывается после Client Hello по сроку: ответ сервера
  с сертификатами не доходит.
- `curl --interface amn0` к тому же адресу отвечает за 0,3 с. Отличие —
  размер сегмента TCP: при пометке маршрут сокета выбран по `enp43s0`
  (MTU 1500, MSS 1460), а MTU `amn0` — 1376 (`amn0.conf.template`);
  правила с `tcp option maxseg` в `system/amnezia/amn.nft` нет.
- Другие сайты набора (`api.anthropic.com`, `api.ipify.org`) работают:
  вероятно, их серверы обрабатывают ICMP о размере пакета, а сервер AUR —
  нет. Гипотеза о MSS проверена только этим сравнением.
- Устройство туннеля — [`../amnezia-split-tunnel.md`](../amnezia-split-tunnel.md).

## Что действует до решения

Запросы к AUR привязываются к `amn0` вручную (`curl --interface amn0`).
Соединение без привязки, в том числе у `yay`, должно обрываться так же
(`yay` не проверялся); пакеты AUR собираются тем же приёмом или после
решения вопроса.

## Возможные исходы

- Ограничение принято: в цепочку `postrouting` таблицы `inet amn`
  добавляется `oifname "amn0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu`,
  ручная привязка `--interface amn0` не нужна.
- Ограничение отвергнуто: привязка остаётся, сайты с тем же обрывом
  перечисляются в `amnezia-split-tunnel.md`, раздел «Ограничения».
