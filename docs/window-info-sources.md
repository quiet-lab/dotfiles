# Откуда брать сведения об окнах в сессии Wayland

Разбор выполнен 22.09.2026 на Hyprland 0.56.2, wayland 1.26.0,
wayland-protocols 1.49.

## Назначение документа

Демону workspaced нужны два признака, которых нет в `hyprctl clients -j`:

- **диалог или окно приложения** — родитель окна (`xdg_toplevel.set_parent`)
  и модальность (`xdg-dialog-v1`), без них принятие появившихся окон
  в workspace испортит геометрию диалогов (пробная задача о диалогах —
  [`window-model.md`, раздел 4](window-model.md#4-нерешённое));
- **различение окон одного приложения** — профиль браузера и вид диалога
  (печать, диспетчер задач, «Сохранить как»).

Здесь собрано, что об окне может узнать сторонняя программа и какой ценой.
Итог пробы о диалогах и решение по профилям Chrome лежат
в [`window-model.md`](window-model.md) и не повторяются; здесь — разбор
источников сведений, на который та проба опирается.

## Способ проверки

Готовой программы для перечисления глобальных объектов Wayland
(`wayland-info`, `wlrctl`) в системе нет, ставить её не понадобилось:
проверка сделана тремя небольшими пробами на C во временном каталоге
сессии, в репозиторий они не входят. Чтобы повторить:

- перечень глобальных объектов — клиент на `libwayland-client`, один
  `wl_registry` с выводом имени и версии каждого объекта;
- события об окнах — клиент трёх протоколов (`wlr-foreign-toplevel-management`,
  `ext-foreign-toplevel-list`, `hyprland-toplevel-mapping`); заголовки
  получаются `wayland-scanner` из XML: `ext-foreign-toplevel-list-v1.xml`
  лежит в `/usr/share/wayland-protocols/staging/`, два других скачиваются
  из репозиториев wlr-protocols и hyprland-protocols;
- настоящий диалог — приложение GTK4 в двадцать строк: главное окно плюс
  второе с `gtk_window_set_transient_for` и `gtk_window_set_modal`. Под
  Wayland оно проверяет протоколы, под `GDK_BACKEND=x11` — свойства X11.

Окна XWayland живут на `DISPLAY=:0`, свойства читает `xprop` из пакета
`xorg-xprop`.

## Протоколы Wayland

Hyprland 0.56.2 анонсирует 73 глобальных объекта; для сведений об окнах
существенны пять.

| Глобальный объект | Версия | Что даёт стороннему клиенту |
|---|---|---|
| `zwlr_foreign_toplevel_manager_v1` | 3 | `app_id`, `title`, `state`, `output_enter`, `output_leave`, `closed`; событие `parent` описано в версии 3, но Hyprland его не отправляет |
| `ext_foreign_toplevel_list_v1` | 1 | `app_id`, `title`, `identifier`, `closed` — и больше ничего: минимализм протокола объявлен в его описании |
| `hyprland_toplevel_mapping_manager_v1` | 1 | по хэндлу окна из любого из двух протоколов выше отдаёт адрес окна Hyprland |
| `xdg_wm_dialog_v1` | 1 | только от клиента к композитору: `set_modal` и `unset_modal`; событий в протоколе нет |
| `xdg_toplevel_tag_manager_v1` | 1 | только от клиента к композитору: метка и описание окна; событий в протоколе нет |

Событие `parent` появилось в третьей версии `wlr-foreign-toplevel-management`
и передаёт хэндл родительского окна либо пустое значение. Объявленная версия
сама по себе ничего не гарантирует: wlroots это событие не заполняет,
композитор обязан вызвать `wlr_foreign_toplevel_handle_v1_set_parent`.
Вызывают labwc и Wayfire; sway и niri не вызывают, хотя объявляют версию 3; в исходниках
Hyprland 0.56.2 вызова нет, и на живой сессии событие не пришло ни разу,
в том числе для модального диалога GTK4.

Ни в одной принятой редакции wayland-protocols способа узнать родителя чужого
окна нет: в XML `ext-foreign-toplevel-list-v1` слово `parent` не встречается.
Открытые предложения (все — merge request в wayland-protocols):

У KDE роль менеджера окон играет собственный
`org_kde_plasma_window_management`, у GNOME общедоступного равноценного
протокола нет. Переносимый источник сведений об окнах один —
`ext-foreign-toplevel-list`, и он даёт три поля: `app_id`, `title`,
`identifier`.

## Что делают библиотеки интерфейса

| Библиотека | `xdg_toplevel.set_parent` | `xdg-dialog` (модальность) | `xdg-toplevel-tag` |
|---|---|---|---|
| GTK4 | да | да | нет |
| GTK3 (а значит и Firefox) | да | нет | нет |
| Qt6 | да | да, начиная с 6.8 | нет |
| Qt5 | не проверено | нет | нет |
| Chromium, Google Chrome, Яндекс.Браузер, Electron | **нет** | нет | нет |
| SDL3, kitty, foot, Wine | — | — | да |

**Chromium не вызывает ни одного из трёх.** В дереве
`ui/ozone/platform/wayland` вызова `xdg_toplevel_set_parent` нет ни разу;
метод `XdgToplevel::SetSystemModal` объявлен с пустым телом и отметкой
[`crbug.com/378465003`](https://issues.chromium.org/issues/378465003).
Поэтому любое дополнительное окно браузера приходит композитору
самостоятельным окном верхнего уровня: без родителя, без модальности
и без метки. Это касается и окон, открытых по Ctrl+N, и диспетчера задач,
и отстыкованного окна средств разработчика. Предпросмотр печати Chromium
рисует внутри вкладки, а выбор файла отдаёт порталу, то есть окно диалога
принадлежит чужому процессу.

Следствие для демона: сведений о родстве окон браузера нет **ни у кого** —
ни у протокола, ни у композитора, ни у плагина. Для них остаются только
заголовок окна и обращение к порталу.

## Hyprland: что внутри и что наружу

Что композитор знает и чем пользуется сам, а также состав
`hyprctl clients -j` — в [`window-model.md`, раздел 4](window-model.md#4-нерешённое).
Сверх того проверено:

- поле `identifier` протокола `ext-foreign-toplevel-list` — это `stableId`
  из `hyprctl clients -j`, та же шестнадцатеричная строка (`ForeignToplevel.cpp`
  печатает `stableID` форматом `{:x}`, `HyprCtl.cpp` — тем же). Сверка всех
  открытых окон на живой сессии совпала полностью, так что связывать окно
  протокола с окном IPC можно без вспомогательных средств. В 0.56.2 есть
  и селектор окон `stableid:`;
- `hyprland-toplevel-mapping-v1` даёт тот же результат в виде адреса окна:
  запросы `get_window_for_toplevel` и `get_window_for_toplevel_wlr`, ответ —
  событие `window_address` из старшей и младшей половин адреса либо `failed`,
  если окна уже нет;
- отправки события `parent` в реализации `wlr-foreign-toplevel-management`
  нет: ни в исходниках тега `v0.56.2`, ни на живой сессии;
- модальность композитор использует в трёх местах (отказ в фокусе родителю,
  обработка попадания указателя, затемнение родителя; настройки
  `general:modal_parent_blocking` и `decoration:dim_modal`), но в IPC
  не печатает. Правило окна `modal` опирается на `CWindow::isModal()`, а тот
  возвращает модальность окна XWayland и на окна Wayland не действует;
- порядок событий: `openwindow` в `socket2` приходит на 1–3 мс раньше, чем
  `done` обоих протоколов toplevel, то есть подключение к Wayland сведения
  об окне раньше не даёт.

## Плагин композитора

Плагин получает объект окна целиком: `CWindow::parent()` и
`CWindow::isModal()` (`/usr/include/hyprland/src/desktop/view/Window.hpp`),
`m_parent`, `m_dialog`, `anyChildModal()`, `m_children` и `m_toplevelTag`
у ресурса xdg-shell (`/usr/include/hyprland/src/protocols/XDGShell.hpp`).
Выдать это наружу есть чем: `registerHyprCtlCommand` заводит свою команду
`hyprctl`, `addEvent` — своё событие на шину, то есть в `socket2`,
`addLuaFunction` — функцию в конфиг Hyprland, `registerCallbackDynamic` —
обработчик открытия окна.

Исходники композитора для сборки не нужны: заголовки и `pkg-config` ставит пакет
`hyprland`, и минимальный плагин, читающий родителя и модальность, собирается
одной командой `g++ -shared -fPIC --no-gnu-unique -std=c++26 $(pkg-config
--cflags hyprland)` — проверено; `hyprpm` для этого тоже не понадобился.

Цена и оговорки:

- проверка совместимости строит хеш из `GIT_COMMIT_HASH` композитора
  и версий его библиотек, поэтому плагин пересобирается после каждого
  обновления пакета `hyprland`, включая исправительные выпуски; иначе
  композитор его не загрузит;
- ошибка в плагине завершает работу композитора, а с ним и сессии;
- для окон Chromium плагин бесполезен: родителя и модальности у композитора
  нет (см. раздел о библиотеках интерфейса).

## Сведения о процессе

`/proc/<pid>` по `pid` из `hyprctl clients -j` даёт командную строку,
рабочий каталог и окружение. Профиль браузера виден прямо в командной
строке: `--profile-directory` и `--user-data-dir` у Chromium и его
производных, `-P` и `--profile` у Firefox.

Приложение из контейнера distrobox читается так же: процессы `fedora-box`
живут в пространстве идентификаторов процессов хоста, поэтому `cmdline`,
`cwd` и `exe` доступны напрямую. Различается пространство монтирования,
поэтому файлы контейнера видны через `/proc/<pid>/root/`, а сам контейнер
опознаётся по `/proc/<pid>/root/etc/os-release`. Приложение во flatpak
опознаётся по `/proc/<pid>/root/.flatpak-info`.

Предел способа: окна одного процесса неразличимы. У двух окон Chromium один
`pid`, и ничего, кроме заголовка, их не разделяет — из-за этого профиль
`AI.dev2026` и переехал в отдельный каталог данных с собственным классом
окна (решение — [`window-model.md`, раздел 2.2](window-model.md#22-семейства-и-варианты)).

## XWayland

У окон X11 есть всё, чего не хватает: `WM_TRANSIENT_FOR` — родитель,
`_NET_WM_WINDOW_TYPE_DIALOG` — тип окна, `_NET_WM_STATE_MODAL` —
модальность, `_NET_WM_PID` — процесс, `WM_CLASS` — класс. Проверено
на тестовом приложении, запущенном с `GDK_BACKEND=x11`.

Слабое место — сопоставление: `hyprctl clients -j` отдаёт только признак
`xwayland`, идентификатора окна X11 там нет, и связывать приходится
по процессу, заголовку и размеру. Плагин композитора это снимает, потому
что знает и окно X11, и адрес. Подписываться на изменения следует через
xcb на события корневого окна, а не опрашивать `xprop` по кругу.

## Порталы и D-Bus

Слежение за пользовательской шиной доступно без дополнительных прав.
Вызовы `org.freedesktop.portal.FileChooser` и `org.freedesktop.portal.Print`
называют вид диалога и процесс, который его заказал, ещё до появления окна.
Родительское окно передаётся строкой `wayland:<ручка>` (экспорт через
`zxdg_exporter_v2`, его Chromium поддерживает) или `x11:<идентификатор>`;
ручку Wayland превращает в окно только композитор, стороннему клиенту она
ничего не говорит.

Токен `xdg-activation` тоже не помогает: какое окно его предъявило, знает
только композитор.

Ни `org.gtk.Application`, ни `org.freedesktop.Application` открытые
приложения на шину не выставляют.

Какая реализация портала отвечает за выбор файла в этой сессии и почему
окно приходит с собственным классом — в
[`media-and-portals.md`](media-and-portals.md).

## Признаки размера и заголовка

Годятся только как дополнение. Снаружи доступны размер окна, совпадение
процесса с уже принятым окном, заголовок и начальный заголовок, время
появления. Все признаки зависят от приложения, его версии и языка
интерфейса. Отдельно стоит учесть: у тестового приложения GTK4 главное окно
получило класс по идентификатору приложения, а дочернее — по имени
программы, то есть у одного приложения окно и его диалог могут прийти
с разными классами.

## Рекомендуемый набор для демона workspaced

1. **`hyprctl clients -j` и события `socket2`** — основа: адрес, класс,
   заголовок, процесс, `stableId`. Менять нечего.
2. **Плагин композитора** — тонкий, без собственной логики: обработчик
   открытия окна кладёт в шину событие с адресом окна, адресом родителя,
   признаком модальности и меткой, и регистрирует команду для полного
   среза. Тогда демону не нужны ни клиент Wayland, ни новый канал связи:
   добавляется вариант сообщения и ветка разбора строки события. Закрывает
   диалоги GTK4, Qt6 и XWayland; окна браузеров — нет.
3. **`/proc/<pid>`** — профили браузеров; в демоне это уже используется при
   восстановлении сессии.
4. **Порталы по D-Bus** — для окон Chromium единственный источник, который
   знает о готовящемся диалоге выбора файла или печати.
5. **Заголовок окна** — для окон браузеров опора на него обязательна,
   а не запасная.

Собственный клиент Wayland демону сейчас не нужен: родителя Hyprland
не отправляет, а остальное уже даёт IPC. Если понадобится переносимость
на другой композитор, работа сводится к одному модулю: отдельный поток
с циклом очереди событий, сообщения в общий канал демона, окна связываются
по `identifier`. Нужные крейты — `wayland-client`, `wayland-protocols`,
`wayland-protocols-wlr`.

Все перечисленные источники работают по событиям, опрос и сроки ожидания
не нужны ни в одном из них.

## Что остаётся невозможным

- Различать окна одного процесса, относящиеся к разным профилям браузера,
  пока браузер запущен одним экземпляром.
- Узнавать вид диалога иначе как по заголовку: предназначенную для этого
  метку `xdg-toplevel-tag` не задаёт ни одно приложение системы.
- Получать модальность и родителя окон Chromium — их не знает и композитор.
- Связывать токен активации или ручку родителя из портала с конкретным
  окном, будучи сторонней программой.

## Что предложить разработчикам

Прямые заявки в Hyprland закрыты как не планируемые:
[#6879](https://github.com/hyprwm/Hyprland/issues/6879) — свой протокол
менеджера окон со связями между окнами,
[#9549](https://github.com/hyprwm/Hyprland/issues/9549) — правила окон для
модальных диалогов. Запроса на вывод родителя и модальности в `hyprctl` никто
не заводил. Имеет смысл предложить три небольших изменения:

1. **Hyprland: поля `parent` и `modal` в `hyprctl clients -j`.** Сведения
   у композитора есть, сериализация дописывается в одном месте, изменение
   только добавляет поля.
2. **Hyprland: отправка события `parent`** в реализации
   `wlr-foreign-toplevel-management`. Протокол объявлен версии 3, событие
   в нём описано, отправки нет; изменение приводит композитор в соответствие
   с собственным объявлением.
3. **Chromium: вызов `xdg_toplevel.set_parent` для дочерних окон** и
   заполнение `SetSystemModal` — отметка
   [`crbug.com/378465003`](https://issues.chromium.org/issues/378465003).
   Без этого диалоги браузеров не отличит ни один композитор.

Если первые два предложения примут, плагин композитора станет не нужен,
а с ним исчезнет и пересборка после каждого обновления Hyprland.

## Источники
