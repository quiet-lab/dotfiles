делится на серию изменений OpenSpec. Документ описывает цель и план, поэтому
требований с MUST здесь нет — они появляются в изменениях, каждое из которых
ссылается сюда. Причины выбора инструментов и отвергнутые варианты этому
документу тоже не принадлежат: их место в `docs/decisions/`.

Состояние: серия из семи изменений реализована целиком 23.09.2026, шаг 7
ждёт проверки пользователем; вне серии реализовано изменение `live-layout`
(раскладка workspace в памяти), оно тоже ждёт проверки пользователем (см.

## 1. Зачем понадобилась новая модель

Действующая модель исходит из того, что у приложения ровно одно окно, а
единственное поведение клавиши — обмен ячеек. В работе это мешает по четырём
причинам.

- **Одно приложение — одно окно.** В `openspec/specs/ws-config/spec.md`,
  требование «Файл конфига и его разделы», приложение в таблице `apps`
  workspace получает одну ячейку шаблона или один `rect`, а в
  `openspec/specs/ws-daemon/spec.md`, требование «Идентификация окон», окно
  приложения помечается единственным тегом `app:<имя>`. Второе окно того же
  браузера или второй терминал в модель не укладываются. Требование «Захват
  открытых окон приложения» той же спецификации это и закрепляет: «Если
  подходящих окон несколько, захватывается одно; остальные остаются
  посторонними».
- **Обмен ячеек как единственное поведение.** Требование «Цепочка приложения»
  (`ws-daemon`) описывает один порядок действий: окно приложения и окно главной
  ячейки меняются местами. Для workspace, где окна намеренно стоят друг поверх
  друга (`surf` с шаблоном `overlay`), обмен не подходит: там требуется вывести
  выбранное окно на передний план, а способа задать другое поведение нет.
- **Свободные посторонние окна.** Требование «Посторонние окна» (`ws-daemon`)
  предписывает окну без тега оставаться свободным: за workspace оно не следует,
  в его состав для панели не входит, а частью workspace становится только по
  команде сохранения (требование «Запись по команде сохранения» в `ws-config`).
  Окно, открытое по ходу работы — neovide из yazi, второе окно браузера, — при
  переносе workspace на другой стол остаётся позади.
- **Общее окно принадлежит последнему вызвавшему.** Требование «Поднятие
  workspace на столе» (`ws-daemon`) формулирует общее приложение так: оно имеет
  одно окно, «которое следует за последним вызовом». Окно, нужное в двух
  workspace, кочует между столами по факту последнего поднятия, а не по тому,
  где работает пользователь. Панель показывает это как исчезновение: по
  требованию «Иконки workspace в плитке стола»
  (`openspec/specs/qs-workspaces/spec.md`) плитка строится из значков окон
  активного workspace стола и свободных окон этого стола, а окна припаркованных
  workspace (`special:pool`) не показываются вовсе. Окно, ушедшее вместе с
  другим workspace на другой стол, из плитки исходного стола пропадает, хотя для
  пользователя оно остаётся частью его работы.

Новая модель отвечает на все четыре: приложение получает список окон, поведение
клавиши выбирается режимом workspace, окно принимается в workspace по событию
своего появления, а окно, нужное нескольким workspace, входит в них все и
следует за пользователем.

## 2. Целевая модель

### 2.1 Уровни конфигурации

Настройки окна распределяются по трём уровням; ближайший к workspace побеждает.

1. **Приложение** (`[apps.<имя>]`). Клавиша или цепочка назначается приложению
   независимо от того, входит ли оно в какой-нибудь workspace. Там же задаётся
   положение и размер по умолчанию — куда встаёт окно, если workspace о нём
   ничего не говорит.
2. **Workspace** (`[workspaces.<имя>]`). Для приложения переопределяются
   положение и размер (ячейка шаблона или `rect`), поведение окна по клавише
   (режим) и сама клавиша. Пример: на одном workspace все окна Chromium
   отзываются на общую клавишу семейства, на другом у каждого профиля своя
   клавиша.
3. **Положение по умолчанию у workspace** — место для окон, которые в нём не
   описаны.

Режим поведения задаётся в конфигурации workspace полем `mode`, а для
отдельного приложения — полем `mode` его записи в workspace. Режимов два:

- режим обмена мест `swap` (по умолчанию): клавиша ставит приложение
  на главное место, меняя его местами с прежним главным приложением;
- режим `stack`: окна стоят на своих местах, клавиша меняет только порядок
  по глубине и фокус.

Режим задаёт только поведение клавиши: раскладка workspace и память
о геометрии окон в обоих режимах одинаковы ([раздел 2.4](#24-геометрия-и-память-о-состоянии-окна)).

Имена полей выбраны изменениями серии: связь варианта с семейством — поле
`family` приложения (шаг 1), переопределения — поля записи приложения в таблице
`apps` workspace (шаг 5): место `cell` или `rect` (ровно одно из двух), клавиша
`chain` и режим `mode`, например `chrome-ai = { cell = "right", chain = "SUPER+V" }`.
Прежние формы записи — имя ячейки строкой и `{ rect = … }` — остаются. Имя
и форма положения по умолчанию у workspace (уровень 3) пока не выбраны, поэтому
запись без места недопустима.

Ключ приложения в workspace — `chain` его записи там, а без него — собственная
клавиша приложения. Переопределение освобождает собственную клавишу в этом
workspace: её может занять другое приложение того же workspace, а если никто
не занял, она по-прежнему ведёт цикл приложения. Без поля `mode` приложение
берёт режим workspace, в том числе приложение без ячейки (место задано `rect`,
в том числе записью сессии): оно тоже меняется местами с главным,
а оставить главное приложение на месте позволяет `mode = "stack"` у записи.
Исключение, по которому приложение без ячейки выбиралось в режиме `stack`
(решение D7 шага 5), снято изменением `live-layout`: с раскладкой в памяти
именно такой обмен и нужен пользователю. Режим приложения задаёт
только поведение его клавиши. Все приложения, отзывающиеся
на одну цепочку, дают одну привязку `workspaced key '<цепочка>'`, а что она
делает, демон решает при нажатии по активному workspace текущего стола:
привязки зависят только от конфига.

### 2.2 Семейства и варианты

У приложения два уровня описания:

- **семейство** — все окна Chromium, все окна wezterm;
- **вариант** — Chromium с профилем AI.dev2026; терминал, запущенный под herdr.

Вариант фиксируется при запуске и потом не меняется. Опознаётся он по классу или
заголовку окна, заданным в момент запуска: `wezterm start --class <имя>` меняет
`app_id` под Wayland, `neovide --wayland_app_id <имя>` (или переменная
`NEOVIDE_APP_ID`) — то же для neovide; и то и другое проверено по справке
программ. За тем, какая программа работает внутри терминала, демон не следит:
терминал, запущенный как yazi, остаётся вариантом yazi независимо от того, что в
нём открыто дальше.

Связь варианта с семейством задаётся явным полем `family` в записи приложения:
запись остаётся плоской, а workspace ссылается на вариант по его имени, как
на любое другое приложение. Уровней ровно два — семейство и его варианты.

Workspace ссылается либо на семейство, либо на вариант, и более точное совпадение
побеждает:

- указано семейство — все его окна лежат стопкой в одной ячейке;
- указан вариант — в свою ячейку попадает именно он, остальные окна семейства
  идут в стопку семейства;
- окно, подходящее и варианту, и семейству, относится к варианту.

Клавиши подчиняются тому же правилу. В workspace, описывающем только семейство,
клавиша семейства ведёт цикл по всем его окнам, включая окна вариантов,
а собственная клавиша варианта — только по окнам варианта. Если workspace
описывает и семейство, и вариант, каждая запись отзывается на свою клавишу
и цикл семейства окон варианта не включает (шаг 5, решение D6 изменения
`workspace-overrides`).

**Профили браузера.** Окна разных профилей Chrome различаются только отдельным
каталогом данных: проба 21.09.2026 показала, что у окон двух профилей одного
процесса совпадают `class`, `initialClass`, `initialTitle` и `pid`, протокол
xdg-toplevel-tag Chromium не поддерживает, `/proc/<pid>/cmdline` хранит аргументы
первого запуска, ключ `--class` под ozone действует на процесс и при запуске
второго профиля в работающий процесс не применяется, `--window-name` навсегда
заменяет заголовок страницы и новым окнам не передаётся, а наследование
приложения от активного окна ненадёжно (окно другого профиля из меню аккаунтов
совпадает и по pid, и по классу, и по прежнему активному окну; окна,
восстановленные браузером при старте, приходят без истории фокуса). Пользователь
принял решение: профиль `AI.dev2026` переезжает в отдельный каталог данных
(`--user-data-dir`) и получает собственный класс окна (`--class`), после чего
опознаётся полем `class`, как остальные варианты, и от демона ничего нового
не требует. Цена решения — второй процесс браузера, пропавший переключатель
профилей, внешние ссылки в экземпляре по умолчанию и перенос каталога профиля;
подробности и порядок переезда —
в `../openspec/changes/archive/2026-09-22-app-families/design.md`.

### 2.3 Цикл по клавише

Клавиша приложения перестаёт быть однократным действием и становится циклом по
его экземплярам. Цикл одинаков в обоих режимах; различается лишь то, что значит
«выбрать» экземпляр.

```
клавиша K, ни одного экземпляра нет
   └──▶ запустить первый экземпляр

клавиша K, активное окно не принадлежит приложению
   └──▶ запомнить prev = активное окно workspace (всегда чужое приложение)
        выбрать экземпляр 1
                   │
                   │  K
                   ▼
        выбрать экземпляр 2 ──K──▶ … ──K──▶ выбрать экземпляр N
                                                  │
                                                  │  K
                                                  ▼
                                      цикл закончен:
                                      prev есть → поднять prev, фокус prev
                                      prev нет  → следующее приложение workspace
```

Пояснения к схеме:

- prev — последнее активное окно workspace, не принадлежащее вызванному
  приложению; по построению это окно другого приложения. В режиме обмена мест
  prev — первое окно приложения, бывшего главным в начале цикла:
  конец цикла там обязан вернуть расстановку, а не просто фокус (решение D3
  изменения `key-cycle-stack`).
- Шаг цикла определяется активным окном, а не счётчиком нажатий, поэтому
  клавиша приложения, окно которого сейчас активно, — это конец цикла: если
  prev нет, она выбирает следующее приложение workspace. Исключение — режим
  обмена мест: клавиша приложения, которое не главное, начинает цикл заново
  и ставит на главное место активное окно, если оно экземпляр этого
  приложения, иначе первый экземпляр. Так окно, которое пользователь только
  что двигал мышью и которое поэтому активно, встаёт на главное место,
  а фокус не возвращается к prev (изменение `live-layout`, решение D7).
- Порядок «следующего приложения workspace»: по порядку записи в конфиге
  workspace, неописанные — после описанных, по порядку появления (принято
  22.09.2026, см. [раздел 4](#4-нерешённое)). Приложения без окон
  пропускаются: конец цикла не запускает программу, которую не вызывали.
- У приложения вне workspace prev нет и следующего приложения тоже, поэтому
  за последним его экземпляром идёт первый.
- Выбор экземпляра мышью учёта не меняет (у приложения, которое уже главное,
  и в режиме `stack`): демон продолжает цикл по порядку и не
  запоминает, какие экземпляры уже были показаны. Пользователь кликнул по второму
  экземпляру из трёх — следующее нажатие клавиши выбирает третий, а за ним
  наступает конец цикла и возврат к prev; первый экземпляр повторно не
  показывается.
- При единственном экземпляре цикл сводится к переключателю «туда и обратно»:
  первое нажатие выбирает экземпляр, второе возвращает prev. Это верно для обоих
  режимов.

| Режим | «Выбрать экземпляр» значит | Конец цикла |
|---|---|---|
| обмен мест (`swap`) | поставить приложение на главное место: вызванное и главное приложения меняются местами целиком, с прямоугольниками, в которых стоят их окна, стопка на стопку; повторные нажатия перебирают экземпляры на главном месте | обратный обмен мест, фокус прежнему главному окну |
| `stack` | поднять экземпляр наверх и дать ему фокус, положение не менять | prev поднимается наверх и получает фокус |

Стопки, то есть несколько экземпляров в одном месте, работают в обоих режимах —
поэтому и правила принятия окон пересматриваются сразу для обоих.

### 2.4 Геометрия и память о состоянии окна

**Раскладка workspace в памяти.** У каждого workspace демон держит раскладку:
каждому приложению его раздела назначено место — исходное (ячейка шаблона
или `rect` записи, после обмена — исходное место другого приложения) и, если
окно сдвигали или меняли его размер, изменённый прямоугольник. Главное
приложение хранится явно: при первом обращении это приложение из поля `main`
раздела, а без него — записанное в главную ячейку шаблона; главное место —
место главного приложения. Раскладка одна на workspace и одинакова в обоих
режимах. По ней встают новые окна приложения (Ctrl+N), запускаемые
приложения, окна, приходящие на стол без запомненного прямоугольника, и по
ней идёт обмен мест. Введено изменением `live-layout` (см.
[раздел 5](#5-серия-изменений)).

**Снятие с экрана в момент действия.** Hyprland 0.56.2 не сообщает
о перемещении и изменении размера окна ни событием сокета, ни событием Lua,
поэтому демон читает прямоугольники окон у композитора тогда, когда
собирается по раскладке действовать: перед циклом клавиши приложения, перед
поднятием и вытеснением workspace, перед переносом на стол, перед уходом окна
со стола workspace (общее окно за пользователем, перетаскивание, отделение),
перед удалением workspace из списка стола и перед командами сохранения.
Раскладка снимается только на столе, где workspace активен: изменённым местом
приложения становится прямоугольник его первого экземпляра, скрытые
и полноэкранные окна не учитываются, а прямоугольник, совпадающий
с исходным, изменённого места не даёт. Окна, сдвинутые командами `half`,
`place` и `maximize`, снимаются так же, как сдвинутые мышью. Опроса
и таймеров нет; `workspaced status --json` показывает раскладку (`cells`,
`main`, `moved`) на момент последнего действия.

**Сдвиг окна становится местом приложения.** Поднятие не двигает окна,
которые уже стоят на столе, ни в одном режиме; перенос workspace на стол
оставляет окна в тех прямоугольниках, где они стояли; окно, приходящее
на стол (возврат после вытеснения, следование общего окна за пользователем),
встаёт туда, где его оставили в этом workspace, а без этого — на место своего
приложения. Для этого демон помнит у каждого окна прямоугольник для каждого
его workspace; у общего окна места в разных workspace независимы. Обмен мест
в режиме `swap` передаёт места целиком: окно, сдвинутое пользователем,
отдаёт свой прямоугольник прежнему главному приложению, а само встаёт
на главное место — с изменённым размером, если главное окно тоже растягивали.
Экземпляры, кроме первого, встают при обмене стопкой на место приложения.

**Возврат к описанию.** Когда в workspace не остаётся окон приложения
(закрытие, отделение, сверка состава), изменённое место этого приложения
снимается, и следующее окно встаёт на исходное место. Событие закрытия
несёт только адрес окна, поэтому у изменённого места хранится окно, с которого
оно снято; пока у приложения в workspace есть другие окна, место остаётся.
Ctrl+Super+Пробел (команда `workspaced arrange`) снимает изменённые места всех
приложений workspace: окна стола встают на исходные места, назначенные
сейчас, окна без описания — стопками по классу в центр экрана, а обмен мест
и главное приложение сохраняются. Команда введена изменением
`desktop-move-and-arrange`, снятие изменённых мест — изменением `live-layout`.

**Конфиг и снимок.** В `config.toml` раскладка попадает только
по Ctrl+Super+S Ctrl+Super+W: место, совпадающее с ячейкой шаблона, пишется
именем ячейки, иначе `rect`, а `main` — главное приложение; после записи
раскладка собирается заново из файла. Правка раздела workspace в файле
(в том числе откат `chezmoi apply`) снимает его раскладку и сразу применяет
новую на столе, где workspace активен, не меняя фокуса; раскладки остальных
workspace остаются. Снимок сессии (Ctrl+Super+S дважды) хранит у workspace
назначение мест, главное приложение (`main`) и изменённые места (`moved`),
а у окна — прямоугольники `rects` по всем его workspace; после перезапуска
демона или перезагрузки они снова становятся раскладкой и памятью окон.
Геометрия до развёртывания в снимок не записывается.

### 2.5 Принадлежность окон

**Состав определяется событием, а не правилом.** Окно входит в workspace, если
выполнено одно из четырёх условий: демон запустил его для этого workspace; оно
появилось, пока workspace был активен; пользователь перетащил его туда; workspace
забрал его при поднятии. Описание в конфиге задаёт только место и клавишу, но не
состав. Состав хранится у окна тегом композитора `ws:<имя>`, по тегу на каждый
workspace, поэтому переживает перезапуск демона так же, как номер экземпляра.
Тег `ws:W` бывает только у окна, приложение или семейство которого описано в `W`
эффективного конфига (файл вместе с дополнительными приложениями сессии): окно,
вошедшее в workspace, который его не описывает, заводит там запись о месте.
Сверка с конфигом (после перечитывания, при старте демона, после загрузки
сессии) снимает теги, которым описание больше не соответствует. Выполнено
шагом 4.

**Принятие окна, появившегося по ходу работы.** Любое окно, появившееся при
активном workspace, принадлежит этому workspace. Если для его приложения в
workspace описано положение, окно встаёт туда (стопкой к остальным окнам того же
приложения), иначе — в положение по умолчанию: центр экрана с собственным
размером окна. Пример: из yazi в терминале запускается neovide — его окно
попадает в тот же workspace и встаёт на место neovide, а не остаётся свободным.
Окно приложения, которого в конфиге нет, становится дополнительным приложением
сессии: имя по классу окна, командная строка и каталог из процесса, место —
записанный прямоугольник. На столе без активного workspace окно остаётся
свободным, как раньше. Выполнено шагом 3.

Часть этого правила действует с шага 2: окно, подходящее приложению конфига
по `class` и `title`, захватывается сразу при появлении и встаёт на место своего
приложения в активном workspace своего стола — так второе окно браузера
по Ctrl+N появляется на месте браузера, а не по центру экрана. Стол окна демон
при этом не меняет и фокус не трогает.

**Диалоги в workspace не принимаются.** Признака диалога у композитора нет
(см. [раздел 4](#4-нерешённое)), поэтому диалоги описаны в конфиге двумя
способами: поле `dialog_title` у приложения оставляет свободным его окно
с подходящим заголовком (диспетчер задач браузера, отстыкованное окно средств
разработки), список `ignore_classes` в корне конфига — окна перечисленных
классов (порталы выбора файла, запрос пароля). Оба описания ведёт пользователь:
они зависят от набора программ и языка интерфейса. Пока Hyprland не выводит
родителя окна и модальность, обойтись без них нельзя — открытый вопрос
[`open-questions/hyprland-window-parent.md`](open-questions/hyprland-window-parent.md).

**Общие окна.** Окно может входить в несколько workspace. При поднятии workspace
свободные окна его приложений захватываются всегда; приложению, у которого после
этого в поднимаемом workspace нет ни одного окна, workspace забирает в общее
пользование его окна из других workspace: по семейству — все окна семейства,
по варианту — окна варианта. Новое окно запускается только тогда, когда
подходящего не нашлось и там. Окна, которые в workspace уже есть, окнами других
workspace не дополняются: иначе второе окно браузера, открытое в другом
workspace, становилось бы общим само. Следствие: Super+Backspace над последним
окном приложения, описанного для `W` в файле конфига, убирает окно из `W` только
до следующего поднятия `W`. Выполнено шагом 4.

**Следование за столом.** Общее окно идёт за пользователем: при переходе на стол
оно переносится туда и встаёт в состояние, запомненное для workspace этого стола
(см. [раздел 2.4](#24-геометрия-и-память-о-состоянии-окна)). Где стоять окну,
входящему в workspace, решает одно правило для всех операций — поднятия,
вытеснения, переноса, преемника, смены стола, отделения и удаления workspace
из списка стола:

1. на столе, где сейчас композитор, если активный там workspace содержит окно;
2. иначе на своём нынешнем столе при том же условии;
3. иначе на столе с наименьшим номером, где активен workspace окна;
4. иначе на `special:pool`.

Шаги 3 и 4 отвечают на случай, когда пользователь не на столе ни одного
из workspace окна. Окно на `special:hidden` правило не трогает. Демон переносит
окна по событию композитора о смене стола, уточнив текущий стол у композитора,
поэтому окно приходит и при переходе клавишей, и при клике по плитке панели;
фокус при этом не меняется. Если окно будет появляться с заметным запаздыванием,
к событию можно добавить переключение столов через демон (решение D5 изменения
`shared-windows`). Выполнено шагом 4.

**Перенос workspace на стол.** Ctrl+Super+1…8 переносит workspace, активный
на текущем столе, на названный стол вместе с окнами всех его приложений
и переходит туда; workspace, активный на том столе, сворачивается, как при
всяком поднятии. Окна встают на новом столе туда, где стояли на прежнем,
в обоих режимах: перенос меняет стол, а не раскладку; вернуть окна на места
из описания можно расстановкой (Ctrl+Super+Пробел).
Workspace числится ровно на одном столе: перенос убирает его из списка
прежнего стола. Активным на прежнем столе становится преемник — workspace,
который был активен там до перенесённого, а если его в списке стола уже
нет, то стоящий в списке перед перенесённым (для первого в списке —
последний). Преемник поднимается сразу: его окна возвращаются на прежний
стол, а композитор и фокус остаются у перенесённого workspace. Прежний
активный workspace каждого стола демон помнит до своей остановки, в снимок
сессии это не попадает. Если других workspace в списке нет, стол остаётся
без активного. Поднятие с явным столом (`raise --desktop N`, запись
`[[binds]]` со столом) преемника не выбирает. Цепочка workspace переносом
по-прежнему не занимается: без явного стола она переходит на стол, где
workspace уже активен. Общее окно перенесённого workspace едет вместе с ним,
а преемник, который поднимается без перехода, его не забирает: окно придёт
на прежний стол, когда туда вернётся пользователь. Введено изменением
`desktop-move-and-arrange`, сохранение прямоугольников в режиме обмена ячеек —
изменением `move-desktop-keeps-geometry`, преемник на прежнем столе —
изменением `move-desktop-successor`, общие окна при переносе — шагом 4.

**Клавиша приложения, когда активный workspace приложение не описывает.** Пусть
нажата клавиша `K`, активен workspace `W`, приложение в `W` не описано:

| Случай | Условие | Что делает `K` |
|---|---|---|
| а | ни один запущенный workspace приложения не содержит | открыть приложение в `W` |
| б | приложение есть в запущенном workspace `V`, и `V` клавишу не переопределяет | поднять `V` |
| в | приложение есть в запущенном `V`, и `V` переопределяет клавишу на `K'` | `K` перетаскивает окно из `V` в `W`, окно становится общим; `K'` по-прежнему поднимает `V` |

Случай «в» и есть способ перетащить окно между workspace. Пример из конфига
сессии: собственная клавиша Chrome с профилем AI.dev2026 (`chrome-ai`) —
Shift+Super+V, а `surf` назначает ему Super+V. На столе с `work` Super+V
поднимает `surf`, а Shift+Super+V переносит окно Chrome AI в `work`, и окно
входит теперь в оба workspace. После этого `work` описывает `chrome-ai`
записью сессии без переопределения, и обе клавиши в `work` ведут цикл по его
окну: клавиша сначала ищет своё приложение в активном workspace — описанное
в нём или вошедшее туда окном — и только без него поднимает другой workspace
(решение D16). Когда окно отделено от `work`, Super+V снова поднимает `surf`.
В самом `surf` обе клавиши ведут цикл. Так же устроены пары Super+B и Shift+Super+B (Chrome профиля
Default), Super+Y и Shift+Super+Y (Яндекс.Браузер).

«Запущенным» считается workspace из списка какого-либо стола, в том числе
ожидающий ленивого поднятия; workspace, которого нет ни в одном списке, клавиша
приложения не поднимает. Описанным в workspace приложение считается, если
там есть запись его самого или его семейства. Если приложение описано в двух
запущенных workspace и один из них его клавишу не переопределяет, действует
случай «б»: поднять workspace естественнее, чем перетаскивать окно. В случае
«а» приложение открывается в `W` по правилам захвата при поднятии: свободные
окна, без них окна других workspace в общее пользование, без окон — запуск;
окно выбирается без обмена мест и встаёт на своё место в `W`, а без записи —
в центр экрана со своим размером. В случае «в» перетаскиваются все нескрытые
окна приложения, из прежних workspace они не уходят, `W` получает запись
о месте. Кроме собственной клавиши, перетаскивание доступно командой
`workspaced app <имя> --pull` и ключом `pull = true` у действия `{ app = … }`
в `[[binds]]`. Случаи «а» и «б» выполнены шагом 4, случай «в» — шагом 5.

**Обратное действие — Super+Backspace** (команда `workspaced detach`): снимает
с активного окна тег активного workspace стола. Окно, входящее ещё в другие
workspace, остаётся открытым и уходит по правилу размещения — на стол, где
активен другой его workspace, либо на `special:pool`. Если это был последний
workspace окна, окно закрывается штатным запросом. Когда из workspace уходит
последнее окно дополнительного приложения сессии, его запись снимается в этом
workspace; если окно закрыто и других окон у приложения нет нигде, запись
с командой снимается во всех workspace. Super+Delete по-прежнему закрывает окно
совсем. Введено шагом 3, где общих окон ещё не было и окно закрывалось всегда;
нынешнее поведение — шагом 4.

### 2.6 Панель

Значки окон в плитке стола берутся из состава активного workspace по данным
демона (список `windows` у workspace в состоянии для панели), а не из
физического расположения окон. Выполнено шагом 6 (изменение
[`panel-shared-windows`](../openspec/changes/archive/2026-09-23-panel-shared-windows/)).
Следствия:

- значок окна из состава показывается в плитке стола, где его workspace
  активен, где бы окно ни стояло: на этом столе, на другом, на
  `special:hidden` или, пока демон его переносит, на `special:pool`; порядок
  значков — порядок окон композитора;
- общее окно показывается в плитках всех столов, где активен его workspace,
  одинаковым значком: окно, стоящее на другом столе, не приглушается и ничем
  не отмечено, потому что при переходе на стол плитки оно придёт туда само;
  приглушённый значок по-прежнему означает только скрытое окно;
- скрытое окно из состава показывается приглушённым во всех плитках, где
  активен его workspace; правило стола происхождения осталось для свободных
  окон;
- свободным считается окно, не входящее в состав ни одного workspace
  из списков столов: окно стола без активного workspace, окно класса
  из `ignore_classes`, диалог по `dialog_title`. Такое окно показывается,
  как раньше, в плитке стола, где стоит, после окон активного workspace;
  без демона свободны все окна, и плитки строятся по расположению;
- workspace стоят в порядке попадания на стол и при переключении не меняют
  позиций (изменение `ws-tile-order`); в плитке стола, на котором сейчас
  композитор, они показаны табами в верхнем ряду плитки двойной высоты:
  активный таб чёрный и слит с нижним рядом окон, неактивные лежат на серой
  полосе (изменение `ws-tile-tabs`); в плитках остальных столов — значками
  в начале ряда, активный подсвечен, неактивные затенены;
- значки окон показываются только у активного workspace, окна неактивных
  workspace в плитке не видны (решение пользователя от 23.09.2026, изменение
  `ws-tile-order`);
- если в плитке неактивного стола значков workspace и окон больше 10,
  а неактивных workspace два и больше, их значки сворачиваются в одну
  кнопку с числом свёрнутых («+2»): чёрный непрозрачный прямоугольник
  с ярко-зелёной надписью увеличенным шрифтом лежит поверх ряда у правого
  края, вплотную к блоку номера стола, и закрывает значки, которые
  не поместились; клик по ней открывает меню «Поднять <имя>». Серая метка
  «+N» остаётся только в ряду без сворачивания (решение пользователя
  23.09.2026).

Левый клик по значку окна, которое не скрыто и стоит не на столе плитки,
переводит композитор на стол плитки; демон переносит туда окно по событию
смены стола, а панель передаёт окну фокус и поднимает его наверх, когда
получит событие композитора о переносе окна. Workspace плитки уже активен
и повторно не поднимается. Ожидание снимается без фокуса, если окно
закрыто, композитор перешёл на другой стол, пользователь кликнул по другому
значку или связь с демоном потеряна; таймеров нет. Повторный клик скрывает
окно только в плитке стола, на котором оно стоит. Подсказка у значка
называет workspace окна и стол, где оно стоит, с пометкой «придёт при
переходе».

Для проверок без мыши панель отдаёт ряд плитки строкой JSON командой
`qs -c panel ipc call workspaces row <стол>` и выполняет левый клик по значку
окна командой `qs -c panel ipc call workspaces activate <стол> <адрес>`;
формат ответа — решение D12 изменения `panel-shared-windows`.

### 2.7 Сессии

Экземпляры приложений и общие окна сохраняются в снимке сессии
и восстанавливаются из него (шаг 7, изменение
[`session-instances`](../openspec/changes/session-instances/), решения D1–D19
его `design.md`).

- **Запись окна.** Окно с тегом экземпляра записывается экземпляром: имя
  приложения, номер, список workspace по тегам состава, стол, прямоугольник
  и прямоугольники `rects` по всем своим workspace. Командную строку из `/proc`
  и рабочий каталог получает только экземпляр с собственным процессом, кроме
  первого, — например, второй neovide, открытый из yazi. Первый экземпляр
  запускается командой приложения из конфига, а окна процесса, который держит
  и другие окна (второе окно браузера), открывает сам процесс.
- **Перезапуск демона.** Запись, для которой есть живое окно с тем же тегом,
  считается исполненной: ничего не запускается, состав живого окна не
  меняется, из записи берутся только прямоугольники по workspace.
- **Раскладка workspace.** У каждого workspace снимок хранит назначение мест,
  главное приложение `main` и изменённые места `moved` (изменение
  `live-layout`, [раздел 2.4](#24-геометрия-и-память-о-состоянии-окна)).
- **Перезагрузка.** Поднятие workspace остаётся ленивым. Первый экземпляр
  запускается командой приложения при поднятии своего workspace, экземпляр
  с командной строкой — при поднятии первого из своих workspace, свободное
  окно приложения — сразу после поднятия workspace активного стола.
  Появившееся окно сопоставляется с записью сначала по pid запущенного
  процесса, затем по приложению в порядке номеров, получает номер, состав
  и место из снимка и встаёт по правилу размещения.
- **Вторые окна браузера** демон не открывает: их восстанавливает сам
  браузер, если у него включено «При запуске: продолжить с того же места»,
  а демон ждёт их по событиям композитора и раскладывает по записям. Сейчас
  эта настройка не задана ни в одном профиле
  ([`host-state.md`](host-state.md)), и второе окно браузера после
  перезагрузки не возвращается. Ожидание таких окон снимают клавиша
  приложения, команда сохранения и загрузка сессии; сроков у него нет.
- **Загрузка именованной сессии** сверяет живые окна приложения с записями
  по порядку номеров: переиспользованное окно получает состав из снимка,
  лишние окна закрываются штатным запросом, недостающие восстанавливаются,
  как при старте.
- **Совместимость.** Снимок прежнего формата (без номеров экземпляров)
  читается и восстанавливается по прежнему правилу «одно приложение — одно
  окно»; первое же сохранение пишет новый формат.

**Состав workspace живёт и на уровне сессии** (решение пользователя
от 22.09.2026). Сохранение сессии не меняет конфиг и поведение workspace: оно
запоминает дополнительные приложения workspace — окна, которых в конфиге нет, —
с их положением и размером. Для записи workspace в конфиг на постоянной основе
служит отдельная комбинация клавиш. Клавиши задал пользователь:
`CTRL+SUPER+s CTRL+SUPER+s` — сохранить сессию, `CTRL+SUPER+s CTRL+SUPER+w` —
записать workspace в конфиг; прежняя `SUPER+TAB SUPER+s`, которая делала и то
и другое сразу, снята. Повод: случайное нажатие прежней цепочки правило файл
под chezmoi, а откат правки расстановку не возвращал. Выполнено изменением
`session-save-extra-windows` (см. [раздел 5](#5-серия-изменений)).

**Снимок сессии пишет только команда сохранения** (решение пользователя
от 22.09.2026, выполнено шагом 3). Прежде `default.toml` обновлялся в обработчике
каждого события, изменившего состояние, и всё время описывал то, что на экране.
Теперь снимок — сохранённое состояние, к которому возвращаются: его пишут
команда сохранения сессии, команда `session save <имя>` и загрузка именованной
сессии, которая страхует прежнее состояние. Шагом 3 команда сохранения заодно
расширена на все столы с активным workspace; раскладки их workspace она
снимает с экрана, поэтому сдвинутое окно дополнительного приложения даёт
изменённое место в раскладке, а прямоугольник записи, с которым приложение
принято, не меняется (изменение `live-layout`). Плата: списки столов,
раскладки workspace и записи дополнительных приложений между сохранениями живут только
в памяти демона, и перезапуск демона или перезагрузка возвращают систему
к последнему снимку.

### Пробные задачи

- **Диалоги.** Выполнена 22.09.2026, шаг 3 сделан по её итогам. Вопрос был:
  как отличить диалог (выбор файла, «Сохранить как», просмотр медиа в Telegram,
  окна Steam) от окна приложения, ведь в сессии все окна плавающие, и признак
  «окно появилось при активном workspace» сам по себе принимает и диалоги. Без
  этого принятие окон испортило бы геометрию диалогов.

  Проверено на Hyprland 0.56.2: готового признака композитор
  не сообщает. В `hyprctl clients -j` у окна есть `address`, `class`, `title`,
  `initialClass`, `initialTitle`, `floating`, `pinned`, `xdgTag`,
  `xdgDescription`, `swallowing`, `grouped` и прочее, но ни родителя окна, ни
  модальности там нет; объект окна Lua (`HL.Window`
  в `/usr/share/hypr/stubs/hl.meta.lua`) повторяет тот же набор, а событие
  `openwindow` несёт только адрес, workspace, класс и заголовок. Внутри
  композитора сведения есть: `CWindow::parent()` читает
  `xdg_toplevel.set_parent`, а `CXDGToplevelResource::anyChildModal()` —
  протокол xdg-dialog-v1; наружу ни то, ни другое не выводится. Правило конфига
  `modal:1` опирается на `CWindow::isModal()`, а тот смотрит только на
  `_NET_WM_STATE_MODAL` окна XWayland, то есть на нативные окна Wayland
  не действует. Полей `xdgTag` и `xdgDescription` не заполняет ни одно
  приложение системы.

  Что из этого следует. Диалог, приходящий отдельным классом (портал
  `xdg-desktop-portal-gtk` для «Сохранить как», `termfilechooser` для yazi),
  приложению конфига не подходит, но шаг 3 принимает любое появившееся окно,
  поэтому такой диалог всё равно попал бы в workspace — его снимает список
  `ignore_classes`. Диалог с классом самого приложения (диспетчер задач Chrome)
  отличить нечем: для него нужен `dialog_title`. Из двух оставшихся путей —
  эвристика по размеру и заголовку либо запрос в Hyprland на вывод родителя
  и модальности в `clients -j` и в объект окна Lua — шаг 3 выбрал второй,
  а до ответа диалоги описываются в конфиге: `dialog_title` по заголовку (та же
  эвристика, но её пишет пользователь, а не демон) и `ignore_classes` по классу
  окна. Эвристика по размеру отвергнута: она зависит от приложения, его версии
  и языка интерфейса, а ошибка в ней портит геометрию только что открытого
  окна.

  Разбор всех источников сведений об окне —
  в [`window-info-sources.md`](window-info-sources.md); главное из него:
  окна Chromium, а с ними Chrome, Яндекс.Браузера и Electron, приходят без
  родителя и без модальности, потому что браузер не вызывает ни
  `xdg_toplevel.set_parent`, ни `xdg-dialog`, и для них не помогут ни плагин
  композитора, ни запрос в Hyprland. Поэтому обращений два — в Hyprland
  и в Chromium; их черновики лежат в [`upstream/`](upstream/README.md)
  и не отправлены, а сам вопрос со сроком пересмотра —
  в [`open-questions/hyprland-window-parent.md`](open-questions/hyprland-window-parent.md).
- **Профили Chrome.** Выполнена 21.09.2026, итоги и решение —
  в [разделе 2.2](#22-семейства-и-варианты).

## 5. Серия изменений

Семь изменений OpenSpec; порядок согласован. Серия реализована целиком
23.09.2026: шаги 1—6 проверены пользователем и заархивированы, шаг 7
ждёт проверки перезагрузкой. После шага 7 вне серии реализовано изменение

Вне серии 22.09.2026 заведено изменение
[`desktop-move-and-arrange`](../openspec/changes/archive/2026-09-22-desktop-move-and-arrange/):

конфига (Ctrl+Super+Пробел) и правка карты XKB, из-за которой раскладку
переключал не только Super+Пробел. На порядок шагов оно не влияет: состава
workspace не меняет и опирается на режимы, введённые шагом 2.

### Шаг 1. Семейства и варианты, несколько окон у приложения

Выполнен 22.09.2026, изменение заархивировано:
`../openspec/changes/archive/2026-09-22-app-families/`.

- **Входит:** в конфиге — связь варианта с семейством, клавиша и положение по
  умолчанию у приложения; в демоне — приложение как список окон, теги
  экземпляров.
- **Спецификации:** ws-daemon («Идентификация окон», «Захват открытых окон
  приложения», «Цепочка приложения» в части нескольких окон, «Поднятие workspace
  на столе» и «Расстановка окон» в части нескольких окон), ws-config («Файл
  конфига и его разделы», «Запись по команде сохранения» в части нескольких окон).
- **После шага:** у приложения может быть несколько окон, демон их различает и
  сопоставляет с семейством или вариантом; поведение клавиши пока прежнее.
- **Зависит:** проба о профилях Chrome выполнена, решение принято.

### Шаг 2. Цикл по клавише и режим `stack`

Выполнен 22.09.2026, проверен пользователем и заархивирован:
[`key-cycle-stack`](../openspec/changes/archive/2026-09-22-key-cycle-stack/).

- **Входит:** цикл по экземплярам с возвратом к prev в обоих режимах, поле `mode`
  у workspace, режим `stack`, захват появившегося окна приложения конфига.
- **Спецификации:** ws-daemon («Цепочка приложения», «Расстановка окон», «Захват
  открытых окон приложения», «Идентификация окон», «Посторонние окна»),
  ws-config («Файл конфига и его разделы», «Цепочки клавиш и привязки»).
- **После шага:** клавиша приложения перебирает его окна и возвращает фокус
  прежнему окну; workspace `surf` работает подъёмом окон вместо обмена ячеек;
  новое окно приложения появляется на месте приложения, а не по центру экрана.
- **Зависит:** от шага 1.

### Между шагами 2 и 3. Дополнительные окна workspace на уровне сессии

Изменение `session-save-extra-windows` (22.09.2026) — предвестник шага 3: оно
вводит состав workspace на уровне сессии, но без автоматического принятия окон.
Окно входит в workspace только по явной команде.

- **Входит:** команда сохранения сессии (`CTRL+SUPER+s CTRL+SUPER+s`) —
  посторонние окна текущего стола входят в активный workspace как
  дополнительные приложения сессии; запись в конфиг переезжает на свою цепочку
  (`CTRL+SUPER+s CTRL+SUPER+w`) и записывает дополнительные приложения сессии
  заодно; поиск подходящего приложения конфига по `class` и `title` при
  сохранении; перечитывание конфига пересобирает ячейки изменённого workspace.
  Заодно демон переведён на события: таймеров в нём не остаётся.
- **Спецификации:** ws-sessions («Дополнительные приложения сессии» — новое,
  «Файлы сессий», «Загрузка сессии», «Восстановление при старте»), ws-config
  («Файл конфига и его разделы», «Цепочки клавиш и привязки», «Слежение
  за конфигом», «Запись по команде сохранения»), ws-daemon («Посторонние окна»,
  «Идентификация окон», «Состояние для панели»), hyprland-binds («Раскладка
  клавиш сессии»).
- **После изменения:** окно, открытое по ходу работы, одной командой становится
  частью workspace на время сессии и ездит вместе с ним; файл под chezmoi
  правится только цепочкой, которая кончается на `w`.
- **Зависит:** от шага 1. От шага 2 не зависит, поэтому выполнено раньше него.

### Шаг 3. Окна, появившиеся по ходу работы

Выполнен 22.09.2026, проверен пользователем 23.09.2026 и заархивирован:
[`windows-join-workspace`](../openspec/changes/archive/2026-09-23-windows-join-workspace/).

- **Входит:** принятие такого окна в активный workspace, постановка его
  в стопку или в положение по умолчанию; понятие постороннего окна сузилось
  до свободного окна на столе без активного workspace. Диалоги описаны
  в конфиге (`dialog_title`, `ignore_classes`). Super+Backspace отделяет окно
  от workspace и закрывает его. Снимок сессии пишет только команда сохранения,
  и она же проходит по всем столам с активным workspace.
- **Спецификации:** ws-daemon («Посторонние окна», «Захват открытых окон
  приложения», «Состояние для панели», новое «Отделение окна»), ws-config
  («Файл конфига и его разделы», «Цепочки клавиш и привязки», «Запись
  по команде сохранения»), ws-sessions («Файлы сессий», «Дополнительные
  приложения сессии»), hyprland-binds («Раскладка клавиш сессии»).
- **После шага:** neovide, запущенный из yazi, попадает в workspace и переезжает
  вместе с ним; окно программы, которой в конфиге нет, становится
  дополнительным приложением сессии само.
- **Зависит:** от шагов 1 и 2; проба о диалогах выполнена.

### Шаг 4. Общие окна

Выполнен 23.09.2026, проверен пользователем и заархивирован:
[`shared-windows`](../openspec/changes/archive/2026-09-23-shared-windows/).

- **Входит:** состав «многие ко многим» тегами `ws:<имя>`, захват открытых окон
  при поднятии, перетаскивание окна операцией `workspaced app <имя> --pull`,
  Super+Backspace без закрытия общего окна, следование окна за столом.
- **Спецификации:** ws-daemon (новые «Состав workspace» и «Следование общего
  окна за столом»; «Поднятие workspace на столе», «Цепочка приложения»,
  «Расстановка окон», «Идентификация окон», «Состояние для панели», «Захват
  открытых окон приложения», «Перенос workspace на стол», «Отделение окна»),
  ws-config («Цепочки клавиш и привязки», «Запись по команде сохранения»;
  «Генерация привязок для Hyprland» не менялась), ws-sessions
  («Дополнительные приложения сессии»).
- **Решения** (`design.md` изменения): состав — тегом у окна, а не выводом
  из конфига (D1); четыре события входа, три выхода и сверка с эффективным
  конфигом (D2); поднятие забирает окна других workspace, только когда своих
  окон у приложения в workspace нет (D3); одно правило размещения из четырёх
  шагов (D4); следование по событию смены стола с уточнением стола
  у композитора (D5); своё состояние окна в каждом workspace (D6); порядок
  случаев клавиши приложения (D7); перетаскивание признаком `pull` без новой
  клавиши (D8); Super+Backspace закрывает только последнее вхождение (D9);
  перенос и преемник по тому же правилу (D10); панель получает состав
  по тегам и пока не меняется (D11); запись workspace в конфиг по составу
  (D12); на столе нет конфликта двух workspace (D13); что переживают
  перезапуск и перезагрузка (D14); открытое или перетащенное приложение
  выбирается без обмена ячеек (D15); общее окно из вытесняемого workspace
  «приходит» в поднятый (D16); состав окнам прежней версии выдаётся по списку
  до сверки (D17); тег снимается и с закрываемого окна (D18).
- **Уточнения замысла:** случай «в» клавиши приложения шаг 4 ввёл операцией
  `pull`, а собственной клавишей приложения он наступает с шага 5; поднятие ищет окна других
  workspace вместо запуска, а не дополняет ими имеющиеся; правило размещения
  дополнено шагами 3 и 4 для пользователя, который не на столе ни одного
  из workspace окна; список требований шага дополнен теми, что затронул
  состав по тегам.
- **После шага:** одно окно живёт в нескольких workspace, идёт за пользователем
  между столами и убирается из workspace по Super+Backspace.
- **Зависит:** от шагов 1—3.

### Шаг 5. Переопределения на уровне workspace

Выполнен 23.09.2026, проверен пользователем и заархивирован:
[`workspace-overrides`](../openspec/changes/archive/2026-09-23-workspace-overrides/).

- **Входит:** переопределение места, клавиши и режима для приложения внутри
  workspace полями записи приложения (`cell` или `rect`, `chain`, `mode`);
  команда `workspaced key <цепочка>` и одна привязка на цепочку; таблица
  клавиши приложения целиком — собственная клавиша приложения, нажатая
  в workspace, который его не описывает, перетаскивает окно (случай «в»);
  режим клавиши на уровне приложения; запись workspace в конфиг правкой
  записей на месте. В конфиге сессии Super+B/V/Y — клавиши `surf`,
  Shift+Super+B/V/Y — собственные клавиши браузеров.
- **Спецификации:** ws-config («Файл конфига и его разделы», «Цепочки клавиш
  и привязки», «Запись по команде сохранения»; «Генерация привязок для
  Hyprland» не менялась), ws-daemon («Цепочка приложения»), hyprland-binds
  («Раскладка клавиш сессии»).
- **Решения** (`design.md` изменения): переопределение — поля записи
  приложения, запись без места недопустима (D1); ключ приложения в workspace —
  переопределение, иначе собственная клавиша, и переопределение освобождает
  собственную клавишу (D2); одна привязка `workspaced key` на цепочку, выбор
  при нажатии по активному workspace (D3); путь клавиши из пяти шагов (D4);
  команда `workspaced app` действует как собственная клавиша (D5); описанным
  считается и приложение, чьё семейство записано в workspace (D6); цикл идёт
  в режиме приложения, приложение без ячейки в workspace режима обмена
  выбирается в режиме `stack`, память о геометрии остаётся за режимом
  workspace (D7; отменено изменением `live-layout`); проверки конфига идут
  по ключам (D8); запись workspace
  в конфиг правит записи на месте (D9); собственные клавиши браузеров —
  Shift+Super+буква, клавиши `surf` прежние (D10); сессии не меняются (D11);
  сценарий «Приложение без workspace» уточнён (D12); workspace, описывающий
  приложение через семейство, откликается на его собственную клавишу (D13);
  запись без переопределений пишется короткой формой (D14); ошибка места
  запоминается при разборе, отказ даёт проверка конфига (D15); клавиша
  ведёт к окну там, где оно сейчас есть: если приложение этой клавиши
  (собственной или назначенной любым workspace) входит в активный workspace
  описанием или окном, цикл идёт в нём, и только иначе действуют прежние
  шаги D4 (D16, по замечанию пользователя при проверке).
- **Уточнения замысла:** команда записи workspace в конфиг прежде собирала
  таблицу `apps` заново по алфавиту, теряя порядок записей и комментарии
  внутри таблицы, — теперь она правит таблицу на месте; выбор пути клавиши
  прежде не учитывал семейство, хотя состав и сверка шага 4 его учитывали;
  список спецификаций шага дополнен требованиями «Запись по команде
  сохранения» и «Раскладка клавиш сессии», где заодно исправлены устаревшие
  строки о Super+Backspace и Super+T/C/E; сценарий «Приложение без workspace»
  и обмен ячеек с приложением без ячейки согласованы правилом режима (D7,
  D12; пересмотрено изменением `live-layout`); в примере раздела 2.5 новую клавишу получал `surf`, в конфиге сессии
  выбрано обратное — новые клавиши получили браузеры, а `surf` сохранил
  прежние (D10).
- **После шага:** на одном workspace профили браузера отзываются на общую
  клавишу семейства, на другом — каждый на свою (проверено на временном
  конфиге: в конфиге сессии семейства Chrome нет); в `surf` Super+B/V/Y
  работают как раньше, на другом столе поднимают `surf`, а Shift+Super+B/V/Y
  забирают окно браузера в текущий workspace; после этого обе клавиши ведут
  цикл по окну в текущем workspace.
- **Зависит:** от шагов 1, 2 и 4. Архивируется после `shared-windows`: три
  требования взяты из его дельт.

### Шаг 6. Панель

Выполнен 23.09.2026, проверен пользователем и заархивирован:
[`panel-shared-windows`](../openspec/changes/archive/2026-09-23-panel-shared-windows/).

- **Входит:** значки окон по составу активного workspace из данных демона,
  общее окно в плитках обоих столов, клик по значку окна, стоящего на другом
  столе, со сменой стола и фокусом после прихода окна, скрытое окно
  из состава во всех своих плитках, сворачивание неактивных workspace
  в плитке неактивного стола, подсказка с workspace окна, IPC `workspaces`
  для проверок. Порядок значков workspace и скрытие окон неактивных workspace
  введены раньше изменением `ws-tile-order`, табы workspace в плитке активного
  стола двойной высоты — изменением `ws-tile-tabs`.
- **Спецификации:** qs-workspaces («Иконки workspace в плитке стола»,
  «Ограничение числа иконок», «Отображение скрытых окон», «Действия над окном
  из плитки», «Подсказка при наведении»).
- **Решения** (`design.md` изменения): ряд окон — список `windows` активного
  workspace стола в порядке композитора (D1); свободные окна по расположению,
  после окон workspace (D2); значок окна на другом столе не приглушается (D3);
  клик — переход на стол и фокус по событию о приходе окна, без повторного
  поднятия workspace (D4); скрытое окно из состава — по составу (D5);
  подсказка называет workspace и стол окна (D6); сворачивание неактивных
  workspace в кнопку «+k» (D7); одна модель ряда по адресам с пересчётом
  по событиям (D8); IPC `workspaces row` и `activate` (D9); демон
  не меняется (D10); переподключение без изменений (D11); уточнения
  реализации — поле `at`, признак `away`, стол из данных события
  `workspacev2`, формат ответа `row` (D12).
- **Уточнения замысла:** ряд свободных окон не исчез, а остался для окон вне
  состава всех workspace — иначе из панели пропали бы порталы выбора файла
  и окна столов без workspace (D2); требование ws-daemon «Состояние для
  панели» не менялось, данных хватило (D10); изменены три требования
  qs-workspaces, которые документ считал неизменными: «Отображение скрытых
  окон», «Действия над окном из плитки», «Подсказка при наведении».
- **После шага:** плитка стола показывает то же, что демон считает составом
  активного workspace, включая общие окна в двух плитках; клик по общему окну
  в плитке другого стола приводит к окну на этом столе.
- **Зависит:** от шага 4. Архивируется после `shared-windows`
  и `workspace-overrides`.

### Шаг 7. Сессии

Выполнен 23.09.2026, ждёт проверки пользователем (перезагрузка):
[`session-instances`](../openspec/changes/session-instances/).

- **Входит:** запись окон приложений в снимок экземплярами — номер, состав
  workspace, прямоугольники режима `stack` (изменением `live-layout`
  расширено на оба режима), командная строка у экземпляра
  с собственным процессом; восстановление экземпляров и общих окон при старте
  и при загрузке именованной сессии; перезапуск демона без повторных
  запусков.
- **Спецификации:** ws-sessions («Файлы сессий», «Загрузка сессии»,
  «Восстановление при старте»), ws-daemon («Состав workspace», «Идентификация
  окон»).
- **Решения** (`design.md` изменения): окно приложения записывается
  экземпляром с номером, составом и прямоугольниками `stack` (D1); командная
  строка — только у экземпляра с собственным процессом, кроме первого (D2);
  второе окно браузера открывает сам браузер, демон его ждёт и раскладывает
  (D3); экземпляр запускается вместе с первым из своих workspace, поднятие
  остаётся ленивым (D4); появившееся окно сопоставляется с записью сначала
  по pid, затем по приложению в порядке номеров (D5); номер экземпляра
  берётся из снимка, если свободен (D6); состав и место восстановленного окна
  — из записи по правилу размещения (D7); при перезапуске демона живые теги
  главнее снимка (D8), при загрузке сессии снимок главнее тегов (D9);
  ожидание окон процесса — только после запуска демоном и до клавиши
  приложения, сохранения или загрузки, без сроков (D10); поднятие workspace
  не отдаёт приложению окна других workspace, пока ждёт его экземпляр
  с командной строкой (D11); снимок прежнего формата читается, откат
  не требует правки снимка (D12); скрытое окно восстанавливается видимым
  (D13); геометрия до развёртывания, цикл клавиши и prev в снимок
  не попадают (D14); прямоугольник окна приложения в снимке теперь читается
  (D15). При реализации добавлены: сохранение переносит записи workspace,
  ещё не поднятых после старта (D16); скрытое свободное окно приложения
  не запускается (D17); загрузка снимка нового формата не выдаёт состав
  по спискам столов (D18); подробности реализации и поля `restore`,
  `restore_apps` в `workspaced status --json` (D19).
- **Уточнения замысла:** прямоугольник окна приложения прежде записывался
  в снимок, но нигде не читался — ни при старте, ни при загрузке, хотя
  требование «Загрузка сессии» велело ставить окно на место из снимка (D15);
  демон никогда не запускал второй экземпляр сам, второе окно появлялось
  только от пользователя, поэтому запуск экземпляра по записи снимка введён
  этим шагом как новое поведение (D2, D4); оговорка о втором окне браузера
  была неточна — браузер, восстановивший свои окна сам, давал окно, которое
  принималось как новое в workspace стола, где появилось, а не туда, где было
  (D3); общие окна после перезагрузки прежде собирались заново только
  по описаниям в конфиге и записям о месте, без номера и порядка
  экземпляров (D14 `shared-windows`, D7).
- **После шага:** после перезагрузки система возвращается к тому набору
  окон, с которым работал пользователь на момент последнего сохранения:
  экземпляры с номерами, их состав и места в каждом workspace; перезапуск
  демона не запускает копий окон.
- **Зависит:** от шагов 1—4. Архивируется после `shared-windows`,
  `workspace-overrides` и `panel-shared-windows` (все три заархивированы).

**Оговорка про сессии.** Снимок сессии описывает экземпляры, их состав
и места, поэтому перезапуск демона и перезагрузка возвращают систему
к последнему сохранению. Переживают перезагрузку: первые экземпляры
приложений (их запускает команда приложения), экземпляры с собственным
процессом (второй neovide, открытый из yazi, — по записанной командной
строке и каталогу), свободные окна и дополнительные приложения сессии,
состав workspace, в том числе общие окна, прямоугольники окон по всем их
workspace и раскладки workspace (назначение мест, главное приложение,
изменённые места). Не переживают: содержимое окон — вкладки, открытые
файлы, историю терминала восстанавливают сами приложения; вторые окна
браузеров, пока в профилях не включено «При запуске: продолжить с того же
места» ([`host-state.md`](host-state.md)): демон их не открывает, чтобы
не получить пустые окна; геометрия до развёртывания, незаконченный цикл
клавиши, prev и история активных workspace стола. Изменения, сделанные
после последнего сохранения, теряются, как и прежде.

### Вне серии, после шага 7: live-layout

Реализовано 23.09.2026 (коммиты демона `ea2ad71`, `6a23d03`, 142 теста),
ждёт проверки пользователем:
[`live-layout`](../openspec/changes/live-layout/). Повод — проверка шага 5
на `work`: окно Chrome AI, перетащенное в `work` и подогнанное мышью,
по Super+V не вставало на главное место, а herdr не занимал его
прямоугольник.

- **Входит:** раскладка workspace в памяти демона
  ([раздел 2.4](#24-геометрия-и-память-о-состоянии-окна)), обмен мест вместо
  обмена ячеек, память окна в обоих режимах, возврат к описанию при закрытии
  последнего окна приложения и по Ctrl+Super+Пробел, запись раскладки
  в конфиг по Ctrl+Super+W, раскладка в снимке сессии, применение правки
  раздела конфига сразу.
- **Спецификации:** ws-daemon («Расстановка окон», «Цепочка приложения»,
  «Расстановка по команде», «Следование общего окна за столом»), ws-config
  («Файл конфига и его разделы», «Слежение за конфигом», «Запись по команде
  сохранения»), ws-sessions («Файлы сессий», «Загрузка сессии»,
  «Восстановление при старте», «Дополнительные приложения сессии»).
- **Решения** (`design.md` изменения): раскладка — места приложений, одна
  на workspace, в обоих режимах (D1); раскладка снимается с экрана в момент
  действия, событий о перемещении у Hyprland нет, опрос и плагин отвергнуты
  (D2); снимается первый экземпляр записи на столе активного workspace,
  скрытые и полноэкранные окна пропускаются (D3); перечень действий, перед
  которыми снимается раскладка (D4); главное приложение хранится явно,
  обмен передаёт места целиком (D5); обмен мест для всех приложений,
  решение D7 шага 5 отменено (D6); клавиша неглавного приложения в режиме
  `swap` ставит его на главное место (D7); память окна одинакова в обоих
  режимах, режим задаёт только клавишу (D8); закрытие последнего окна
  приложения снимает его изменённое место, у места хранится окно-владелец
  (D9); расстановка по команде снимает изменённые места, но не обмен (D10);
  запись workspace пишет раскладку (D11); перечитывание изменённого раздела
  сразу применяет раскладку (D12); снимок хранит раскладку, прямоугольник
  записи дополнительного приложения не переписывается (D13); снимок прежнего
  формата читается (D14); поля `main` и `moved` в `workspaced status --json`
  (D15); порядок архивации (D16); подробности реализации и уточнения
  проверок (D17).
- **Уточнения замысла:** режим `stack` перестал быть единственным режимом
  с памятью прямоугольников; исключение для приложения без ячейки (D7 шага 5)
  снято; конец цикла по активному окну в режиме `swap` действует только для
  главного приложения.
- **Зависит:** от шагов 5 и 7. Архивируется после `workspace-overrides`
  (заархивирован) и `session-instances`: шесть требований взяты из их дельт.
