## MODIFIED Requirements

### Requirement: Состав workspace
Окно MUST входить в workspace `W`, если у окна есть тег `ws:W`; у окна, входящего в несколько workspace, MUST быть по тегу на каждый. Окно MUST входить в workspace по одному из пяти событий: демон запустил окно для этого workspace; окно появилось на столе, где этот workspace активен (требование «Посторонние окна»); workspace забрал окно при поднятии (требование «Захват открытых окон приложения»); окно перетащено в workspace цепочкой приложения с признаком перетаскивания (требование «Цепочка приложения»); окно восстановлено из снимка сессии или переиспользовано загрузкой сессии, и workspace записан в его записи снимка (спецификация ws-sessions, «Восстановление при старте», «Загрузка сессии»). Окно, восстановленное из снимка, MUST входить во все workspace своей записи, описывающие его приложение, и MUST NOT входить при этом в активный workspace стола, где оно появилось, если того нет в записи. Окно MUST выходить из workspace по команде отделения окна (требование «Отделение окна»), при закрытии, при сверке с конфигом и при загрузке сессии, если workspace нет в записи снимка, которой досталось окно. Перезапуск демона без перезагрузки состава живого окна MUST NOT менять, кроме снятия тегов сверкой. Входя в workspace, окно MUST NOT выходить из остальных своих workspace. Все операции, которым нужны окна workspace, — поднятие, перенос, парковка, цикл клавиши приложения, prev, следующее приложение workspace, память прямоугольников, расстановка, отделение, запись по командам сохранения и состояние для панели — MUST определять окна workspace по этим тегам.

Тег `ws:W` MUST быть только у окна, приложение которого, само или его семейство, описано в `W` эффективного конфига (файл конфига вместе с дополнительными приложениями сессии). Поэтому окно, входящее в workspace, который его приложение не описывает, MUST заводить там запись о месте приложения (требование «Дополнительные приложения сессии» спецификации ws-sessions). Сверка тегов состава с эффективным конфигом MUST выполняться там же, где сверка тегов экземпляров (требование «Посторонние окна»): после перечитывания конфига, при старте демона и при загрузке сессии. Тег `ws:W` MUST сниматься, если `W` в эффективном конфиге нет или `W` не описывает приложение окна; окно, у которого не осталось тегов состава, MUST оставаться на месте с тегом экземпляра и считаться свободным окном приложения. Окну с тегом экземпляра, но без тегов состава, при старте демона и после загрузки сессии MUST быть выдан состав: окно на столе, где активен workspace, описывающий его приложение, MUST войти в этот workspace; окно на `special:pool` MUST войти во все workspace из списков столов, которые описывают его приложение и не активны; иначе окно MUST остаться свободным.

#### Scenario: Окно входит в workspace тегом
- **WHEN** на столе 1 активен `work`, и пользователь открыл второе окно Chromium
- **THEN** `hyprctl clients -j` показывает у окна теги `app:chromium#2` и `ws:work`

#### Scenario: Окно в двух workspace
- **WHEN** окно `chrome-ai` из `surf` перетащено в `work` командой `workspaced app chrome-ai --pull`
- **THEN** у окна теги `app:chrome-ai#1`, `ws:surf` и `ws:work`, в `workspaced status --json` у окна `"workspaces": ["surf", "work"]`

#### Scenario: Состав после перезапуска демона
- **WHEN** окно `chrome-ai` входит в `surf` и `work`, и демон перезапущен
- **THEN** после старта окно по-прежнему входит в оба workspace, ни одно приложение не запускается повторно

#### Scenario: Сверка снимает лишний тег состава
- **WHEN** окно `chrome-ai` перетащено в `work` после последнего сохранения сессии, и демон перезапущен
- **THEN** записи о месте `chrome-ai` в `work` после старта нет, тег `ws:work` с окна снят, окно остаётся в `surf`, в журнале строка о снятом теге

#### Scenario: Окна прежней версии демона получают состав
- **WHEN** демон новой версии запущен при окнах `work` на столе 1 (там же в списке неактивный `surf`) и окнах `surf` на `special:pool`, у которых есть только теги экземпляров
- **THEN** окна на столе 1 входят в `work`, окна на `special:pool` — в `surf`, и поднятие `surf` на столе 1 паркует окна `work`

#### Scenario: Состав из снимка после перезагрузки
- **WHEN** в снимке сессии окно `chromium` с номером 2 записано с `workspaces = ["surf"]`, у `surf` в снимке запись о месте `chromium`, после перезагрузки `work` поднят на столе 1, `surf` ждёт ленивого поднятия на столе 2, и Chromium открыл это окно на столе 1
- **THEN** окно несёт теги `app:chromium#2` и `ws:surf`, тега `ws:work` у него нет, и оно стоит на столе 2 по правилу размещения

### Requirement: Идентификация окон
Демон MUST запускать приложения сам (отдельная сессия процессов, каталог `cwd`, сложенное окружение) и сопоставлять появившееся окно с приложением по pid процесса или его потомков; если у приложения заданы `class` и, при необходимости, `title`, окно, которому эти выражения соответствуют, MUST сопоставляться с ожидающим приложением и без совпадения по pid, так как окно приложения из контейнера (distrobox, podman) не является потомком запущенного процесса. У приложения MUST быть допустимо несколько окон — экземпляров. После сопоставления окно MUST получить тег `app:<имя>#<номер>`, где номер — наименьший свободный номер среди живых окон этого приложения, начиная с 1; окно, сопоставленное с записью снимка сессии (спецификация ws-sessions, «Восстановление при старте»), MUST получить номер этой записи, если он свободен среди живых окон приложения, а иначе наименьший свободный. По тегу окно опознаётся при перезапуске демона, а по номеру задаётся порядок экземпляров: чем меньше номер, тем раньше экземпляр в порядке. Номер экземпляра MUST быть один на окно, сколько бы workspace окно ни входило: порядок экземпляров во всех workspace одинаков. Тег `app:<имя>` без номера, оставшийся от прежней версии демона, MUST читаться как экземпляр этого приложения. Окно варианта MUST считаться и окном его семейства: захватываться, переноситься, расставляться и входить в workspace всюду, где workspace описывает семейство; в какие workspace окно входит, задают теги состава (требование «Состав workspace»).

Ожидание окна MUST быть событийным и MUST NOT ограничиваться сроком: демон MUST узнавать о выходе запущенного процесса от самого процесса, а о появлении окна — от композитора, и MUST NOT опрашивать ни то, ни другое по таймеру. Если процесс завершился, а подходящего свободного окна в системе нет, ожидание MUST остаться в силе и принять первое подходящее окно, когда оно появится. Если процесс завершился, а подходящее свободное окно уже есть (одноэкземплярное приложение вроде Telegram открыло окно в прежнем процессе), демон MUST считать это окно окном приложения сразу. Ожидание приложения, которого в эффективном конфиге не стало, MUST сниматься (требование «Посторонние окна»). Совпадение по pid процесса и его потомков MUST проверяться раньше совпадения по `class` и `title`: окно процесса, запущенного для записи снимка сессии, MUST NOT доставаться ожиданию запуска приложения по классу. Повторный вызов приложения, пока запущенный процесс жив, MUST NOT заводить второго запуска; запуск экземпляров по записям снимка сессии повторным вызовом не считается; повторный вызов после выхода процесса MUST принять подходящее свободное окно, а при его отсутствии снять прежнее ожидание и запустить приложение заново, чтобы клавиша не осталась без ответа. Окно без тега, не принятое ожиданием, MUST доставаться подходящему приложению конфига (требование «Захват открытых окон приложения»), а если такого приложения нет — считаться посторонним (требование «Посторонние окна»).

#### Scenario: Тег после запуска
- **WHEN** демон запустил `editor-front` и его окно появилось
- **THEN** `hyprctl clients -j` показывает у окна тег `app:editor-front#1`

#### Scenario: Второй экземпляр приложения
- **WHEN** у `chromium` есть окно с тегом `app:chromium#1`, пользователь открыл второе окно Chromium, и поднят `work` с `chromium` в ячейке `left`
- **THEN** второе окно получает тег `app:chromium#2`, оба окна стоят в ячейке `left`, второй Chromium не запускается

#### Scenario: Освободившийся номер
- **WHEN** окно с тегом `app:chromium#1` закрыто, окно `app:chromium#2` осталось, и захвачено ещё одно окно Chromium
- **THEN** новое окно получает тег `app:chromium#1`, и в порядке экземпляров оно идёт первым

#### Scenario: Окно из контейнера
- **WHEN** у приложения `chrome` задано `class = "(?i)^google-chrome$"`, демон запустил его через `distrobox-enter`, и через две секунды появилось окно класса `google-chrome`, чей процесс не потомок `distrobox-enter`
- **THEN** окно сразу получает тег `app:chrome#1` и занимает своё место, а не остаётся посторонним до следующего поднятия workspace

#### Scenario: Окно появилось много позже запуска
- **WHEN** приложение запускается долго (прогрев контейнера, холодный старт браузера) и его окно появилось через минуту после команды
- **THEN** окно получает тег своего приложения и встаёт на своё место: ожидание сроком не ограничено

#### Scenario: Процесс вышел, а окно открылось в прежнем
- **WHEN** Telegram уже запущен, нажата его клавиша, запущенный процесс передал запрос прежнему и завершился
- **THEN** демон по выходу процесса принимает открытое окно Telegram как окно приложения, не дожидаясь никакого срока

#### Scenario: Повторное нажатие после неудачного запуска
- **WHEN** приложение запущено, процесс завершился без окна, окна в системе нет, и клавиша приложения нажата ещё раз
- **THEN** прежнее ожидание снято, приложение запускается заново, и в журнале строка об этом

#### Scenario: Перезапуск демона
- **WHEN** демон перезапущен при открытых окнах трёх приложений с тегами, и у одного из них два окна
- **THEN** после старта `workspaced status --json` показывает все четыре окна у их приложений с прежними номерами экземпляров, ни одно приложение не запускается повторно

#### Scenario: Тег прежней версии
- **WHEN** демон запущен при открытом окне с тегом `app:neovide` без номера
- **THEN** окно считается экземпляром `neovide`, участвует в расстановке и цепочке, а второй `neovide` не запускается

#### Scenario: Номер экземпляра из снимка
- **WHEN** после перезагрузки восстанавливаются записи `neovide` с номерами 1 и 2, и окно второго экземпляра (процесс `neovide notes.md`) появилось раньше окна первого
- **THEN** окно процесса `neovide notes.md` получает тег `app:neovide#2`, окно первого экземпляра — `app:neovide#1`, и ни одно из них не достаётся ожиданию запуска `neovide` по классу раньше своего
