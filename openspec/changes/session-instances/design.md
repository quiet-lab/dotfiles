# Design: Экземпляры и общие окна в снимке сессии

## Context

Мотивация — в `proposal.md`, замысел целиком и место шага в серии —
в [`docs/window-model.md`](../../../docs/window-model.md): раздел 2.4
(память о состоянии окна), 2.5 (принадлежность окон, правило размещения),
2.7 (сессии), раздел 4 (предложение о сохранении экземпляров, принятое
22.09.2026), раздел 5, шаг 7 и оговорка про сессии. Решения прежних шагов
действуют и здесь: [`app-families`](../archive/2026-09-22-app-families/design.md)
— теги экземпляров (D4, D5), место первого экземпляра при записи (D15);
[`key-cycle-stack`](../archive/2026-09-22-key-cycle-stack/design.md) —
прямоугольники режима `stack` только в памяти (D9, этот шаг его пересматривает);
[`windows-join-workspace`](../archive/2026-09-23-windows-join-workspace/design.md)
— снимок только по команде (D6);
[`shared-windows`](../shared-windows/design.md) — состав тегами (D1), сверка
и выдача состава окнам прежней версии (D2, D17), поднятие забирает окна
других workspace (D3), правило размещения (D4), своё состояние в каждом
workspace (D6), что переживает перезапуск и перезагрузку (D14);
[`workspace-overrides`](../workspace-overrides/design.md) — сессии не менялись
(D11); [`panel-shared-windows`](../panel-shared-windows/design.md) — демон
не менялся (D10).

Что есть сейчас (демон, коммит `e772598`).

- **Снимок** (`session::snapshot`, `state::SessionWindow`): у окна
  с тегом экземпляра записываются имя приложения, стол (`1`…`8`, `pool`,
  `hidden`) и прямоугольник; номера экземпляра, тегов состава и командной
  строки нет. Свободное окно без тега записывается со столом, командной
  строкой, каталогом и прямоугольником. У workspace — назначения ячеек
  (`st.cells`) и дополнительные приложения сессии (`st.extra`).
  Прямоугольники режима `stack` (`st.geom`) в снимок не попадают.
- **Старт** (`session::restore_default`): списки столов, ячейки
  и дополнительные приложения из снимка (`apply_lists`), ленивое поднятие
  активных workspace других столов (`set_lazy`), сверка тегов
  (`adopt_live_foreign`: `drop_stale_pending`, `free_stale_tagged`,
  `sync_membership(true)` — сверка состава и выдача состава окнам прежней
  версии), свободные окна снимка сопоставляются с живыми по команде
  и каталогу, недостающие запускаются сразу (`spawn_missing_foreign`,
  ожидание `ExpectedForeign` по команде и каталогу). Затем поднимается
  активный workspace активного стола, после него — `[startup]`.
  **Окна приложений из снимка при старте не читаются вовсе**: приложение
  запускается поднятием своего workspace, если в нём нет его окон
  (`raise_on` → `spawn`), по одному окну на приложение.
- **Загрузка** (`session::load`): окно приложения, которого в снимке нет,
  закрывается; из окон приложений снимка берутся только имена и столы —
  по одному запуску на приложение без живых окон (`apps_to_start`).
  Прямоугольники окон приложений из снимка не используются: окна встают
  поднятием активных workspace.
- **Запуск** (`Daemon::spawn`): на приложение заводится не больше одного
  ожидания `Pending`; повторный вызов при живом процессе ждёт. Демон
  никогда не запускает второй экземпляр сам: второе окно появляется
  от пользователя (Ctrl+N, запуск из терминала) и принимается
  по событию `openwindow` (`capture_new`, `join`).
- **Сопоставление появившегося окна** (`on_open`): ожидание `Pending`
  по pid процесса и его потомков, затем ожидание `Pending` по классу
  и заголовку (`Pending::matches`), затем свободное окно из снимка по команде
  и каталогу (`expected`), иначе принятие в активный workspace стола.
- **Процессы браузеров.** У окон одного браузера один pid (проба профилей
  Chrome 21.09.2026, `docs/window-model.md`, раздел 2.2). Запуск команды
  браузера при работающем процессе передаёт запрос прежнему процессу,
  и тот открывает ещё одно окно, а запущенный процесс завершается; демон
  принимает такое окно по выходу процесса (сценарий «Процесс вышел, а окно
  открылось в прежнем», ws-daemon). У `herdr` ключ `--always-new-process`,
  у neovide по процессу на окно. В `Preferences` профилей Chromium, Chrome
  (оба каталога данных) и Яндекс.Браузера ключа `session.restore_on_startup`
  нет (проверено 23.09.2026): действует значение браузера по умолчанию,
  и восстановит ли браузер свои окна после перезагрузки, из конфига не видно.

## Goals / Non-Goals

**Goals:**

- После перезагрузки возвращаются экземпляры приложений с номерами,
  составом workspace и местами в каждом workspace.
- Перезапуск демона без перезагрузки не запускает копий и не меняет
  состав живых окон.
- Загрузка именованной сессии сверяет окна по экземплярам.
- Всё ожидание — по событиям, без сроков.

**Non-Goals:**

- Содержимое окон (вкладки, файлы, история): его восстанавливают приложения.
- Запуск вторых окон браузера демоном.
- Геометрия до развёртывания, незаконченный цикл клавиши, prev, история
  активных workspace стола.
- Изменение конфига, панели и настроек браузеров.

## Decisions

**D1. Окно приложения записывается экземпляром.** Запись окна
с тегом экземпляра в списке `windows` снимка получает поля:

- `app` — имя приложения (как сейчас);
- `instance` — номер из тега `app:<имя>#<номер>` (тег без номера — `1`);
- `workspaces` — workspace по тегам состава, по алфавиту; пустой список
  у свободного окна приложения;
- `desktop` и `rect` — где окно стоит и его прямоугольник (как сейчас);
- `rects` — таблица «workspace → прямоугольник» для workspace окна
  в режиме `stack`: запомненный прямоугольник `st.geom[W][адрес]`, а для
  окна, стоящего на столе, где `W` активен, — нынешний прямоугольник
  (то же правило, что у `extra_rect` в `save.rs`, решение D12 шага 4);
  для workspace режима обмена ячеек прямоугольник не пишется: там место
  задаёт ячейка приложения (`st.cells`, уже в снимке);
- `cmd` и `cwd` — по решению D2.

Признак нового формата — поле `instance`: оно есть у каждого окна
приложения в снимке новой версии, поэтому пустой `workspaces` при нём
означает свободное окно приложения, а не прежний формат (D12).

Рассмотренные варианты:

- *Состав отдельной таблицей у workspace* (`[workspaces.work] windows = [
  "chromium#1", …]`). Отвергнут: состав хранится у окна тегами (решение D1
  шага 4), и запись окна с его workspace повторяет устройство тегов;
  таблица у workspace дублировала бы номер окна в нескольких местах,
  и сверка «запись ↔ окно» шла бы в два прохода.
- *Адрес окна в снимке.* Отвергнут: адрес не переживает перезагрузку,
  а при перезапуске демона окно и так узнаётся по тегу экземпляра (D8).
- *Прямоугольник для каждого workspace, в том числе режима обмена.*
  Отвергнут: в режиме обмена окно встаёт в ячейку (раздел 2.4 документа),
  записанный прямоугольник противоречил бы назначению ячеек.

**D2. Командная строка — только у экземпляра с собственным процессом, кроме
первого.** Экземпляр получает `cmd` и `cwd`, если у его процесса (`pid`
окна) нет других окон среди клиентов композитора и экземпляр не первый
у своего приложения (не наименьший номер среди живых окон приложения).
Команда и каталог берутся тем же путём, что у свободного окна (`proc_info`,
`launchable`, правило требования «Файлы сессий»: flatpak, строка Chromium,
относительный путь, `/proc/<pid>/exe`); если команда не найдена, экземпляр
записывается без неё и восстанавливается как окно без командной строки.
Первый экземпляр запускается командой приложения из конфига (или записи
дополнительного приложения сессии), как сейчас; окна, чей процесс держит
и другие окна, открывает сам процесс (D3).

Так устроено предложение, принятое 22.09.2026 (`docs/window-model.md`,
раздел 4): экземпляры, запущенные пользователем, сохраняются по командной
строке из `/proc` и рабочему каталогу. Пример: neovide, открытый из yazi
командой `neovide notes.md` в `~/notes`, — второй экземпляр `neovide`
с `cmd = ["neovide", "notes.md"]` и `cwd = "~/notes"`; первый экземпляр
запускается командой `neovide` из конфига.

Рассмотренные варианты:

- *Командная строка из `/proc` у всех экземпляров.* Отвергнут: у первого
  экземпляра терялись бы окружение, аргументы и каталог из конфига
  (`app_command` с `env`, `--class` у herdr); у браузера из контейнера
  distrobox процесс окна живёт внутри контейнера, и его путь
  (`/opt/google/chrome/chrome`) с хоста не запускается; окна одного
  процесса браузера дали бы несколько одинаковых команд и лишние окна.
- *Без командной строки, всё командой приложения.* Отвергнут: второй
  neovide с файлом вернулся бы пустым, а принятое предложение требует
  `/proc`.
- *Командная строка, если она отличается от команды приложения.*
  Отвергнут: команда приложения проходит через обёртки (`distrobox-enter`,
  `wezterm-gui start`, скрипт `/usr/bin/firefox`), и сравнение
  с `/proc/<pid>/cmdline` ненадёжно.

**D3. Второе окно браузера восстанавливает браузер; демон его ждёт
и раскладывает.** Экземпляр без командной строки, кроме первого, демон
не запускает: браузер, запущенный для первого экземпляра, открывает
остальные окна сам, если у него включено продолжение с того же места.
Демон ждёт такие окна по событию `openwindow` и сопоставляет с записями
(D5). Если браузер своих окон не восстановил, записи остаются
неисполненными до снятия ожидания (D10): второе окно не возвращается,
как и сейчас, но и не открывается пустым.

Условие — настройка браузера «При запуске: продолжить с того же места»
(`session.restore_on_startup = 1` в `Preferences` профиля). Сейчас ключа
нет ни в одном профиле (Context); менять настройку браузеров изменение
не берётся, задача 5.4 записывает условие в `docs/host-state.md`,
а проверка вживую 4.1 показывает, как ведут себя браузеры при
нынешнем значении.

Рассмотренные варианты:

- *Повторный запуск команды приложения* (у Chromium при работающем
  процессе это новое окно, как `chromium --new-window`). Отвергнут: окно
  открывается пустым, а если браузер восстанавливает окна сам, появляются
  лишние; у браузеров из контейнера это ещё и лишний вызов
  `distrobox-enter`.
- *Принимать окна, восстановленные браузером, как новые* (нынешнее
  поведение: `capture_new` в активный workspace стола, где окно появилось).
  Отвергнут: окно второго workspace (`surf`) оказывается в первом (`work`),
  номер и прямоугольник `stack` теряются. Предложение документа «демон
  раскладывает их по стопкам» этим решением выполнено точнее: окно встаёт
  в стопку своего приложения в своём workspace.

**D4. Экземпляр запускается вместе с первым из своих workspace.**
Восстановление при старте остаётся ленивым (требование «Восстановление при
старте»): полностью поднимается только активный workspace активного стола,
остальные — при первом переходе на стол или первом вызове. Экземпляр
с командной строкой запускается при поднятии первого из своих workspace,
до захвата и запуска приложений этого workspace (D11). Экземпляр без
workspace (свободное окно приложения) запускается сразу после поднятия
workspace активного стола, как свободные окна снимка: своей командой,
а без неё — командой приложения, если у приложения нет ни окон, ни
ожидания запуска. Первый экземпляр запускается командой приложения
поднятием workspace, как сейчас.

Отвергнуто: запускать все экземпляры при старте — это отменило бы ленивое
поднятие, которое требование сохраняет, и открыло бы окна неактивных
workspace на `special:pool`, хотя они могут и не понадобиться.

**D5. Появившееся окно сопоставляется с записью: сначала по pid, затем
по приложению в порядке номеров.** План восстановления — список записей
снимка, ожидающих окна, в памяти демона (`st.restore`). Порядок проверки
в `on_open` для окна без тега:

1. ожидание `Pending` по pid процесса и его потомков (как сейчас);
2. запись экземпляра с командной строкой по pid запущенного для неё
   процесса и его потомков;
3. свободное окно снимка по команде и каталогу (как сейчас);
4. ожидание `Pending` по классу и заголовку (как сейчас);
5. запись без командной строки приложения окна (`app_for_window`),
   если для этого приложения восстановление ждёт окон (D10): запись
   с наименьшим номером среди ожидающих;
6. принятие окна в активный workspace стола (как сейчас).

Совпадения по pid идут раньше совпадений по классу, иначе окно второго
neovide, запущенного по записи, досталось бы ожиданию первого по классу
`^neovide$`. Окно, принятое ожиданием `Pending` (шаг 1 или 4), тоже
сопоставляется с записью: берётся запись этого приложения без командной
строки с наименьшим номером, у которой в `workspaces` есть workspace,
для которого приложение запущено (`Pending.workspace`), а без такой —
с наименьшим номером вообще.

Рассмотренные варианты:

- *Сопоставление по заголовку.* Отвергнут: заголовок окна браузера — это
  заголовок страницы, при появлении окна он пустой или временный
  и меняется событием `windowtitle` позже; ждать заголовка значило бы
  откладывать размещение без срока.
- *Порядок появления без учёта приложения.* Отвергнут: окна разных
  приложений появляются в произвольном порядке.
- *Сопоставление по адресу.* Отвергнут: после перезагрузки адреса другие.

Следствие, принятое сознательно: окна одного процесса браузера между собой
неразличимы, и если браузер откроет их не в том порядке, окно из `surf`
может встать на место окна из `work` и наоборот. Содержимое окон
от этого не меняется, пользователь переставит их клавишами или
Super+Backspace.

**D6. Номер экземпляра берётся из снимка, если свободен.** Окно,
сопоставленное с записью, получает тег `app:<имя>#<номер записи>`, если
этого номера нет среди живых окон приложения, иначе наименьший свободный,
как сейчас. Без этого окно второго экземпляра, появившееся раньше первого,
получило бы номер 1, и порядок экземпляров в цикле клавиши поменялся бы.
Требование «Идентификация окон» (ws-daemon) дополняется этим правилом;
в остальных случаях номер по-прежнему наименьший свободный.

**D7. Состав и место восстановленного окна — из записи.** Окно получает
теги состава тех workspace записи, которые описывают его приложение
в эффективном конфиге (инвариант решения D1 шага 4: иначе сверка сняла бы
тег сразу). Дополнительные приложения сессии уже восстановлены
`apply_lists`, поэтому записи о месте общего окна в эффективном конфиге
есть. Затем окно встаёт по правилу размещения (`window_home`, решение D4
шага 4) для нынешних активных workspace столов: на стол, где активен его
workspace, в режиме обмена — в ячейку своего приложения (`State::rect_for`),
в режиме `stack` — в прямоугольник записи для этого workspace, а без него —
на место из конфига; если ни один его workspace не активен —
на `special:pool`. Все прямоугольники `rects` записи становятся
запомненными (`st.geom[W][адрес]`), и при следующем поднятии или переходе
на стол окно придёт туда, где его оставили. Место из ожидания `Pending`
(прямоугольник, посчитанный поднятием) заменяется местом по записи: они
совпадают всюду, кроме режима `stack`, где запись точнее. Фокус
восстановление не меняет; ожидание `Pending` с фокусом (главное приложение
поднимаемого workspace) отдаёт его, как сейчас.

Свободное окно приложения (запись без `workspaces`) встаёт на свой стол
в свой прямоугольник, как свободное окно снимка.

**D8. Перезапуск демона без перезагрузки: живые теги главнее снимка.**
При старте запись снимка, для которой есть живое окно с тем же тегом
экземпляра, считается исполненной: ничего не запускается, теги состава
окна не меняются, из записи берутся только прямоугольники `rects` — для
workspace, в которые окно входит сейчас. Это продолжает решение D14 шага 4:
теги живут в композиторе, и окно, убранное из `W` по Super+Backspace после
сохранения, после перезапуска демона в `W` не возвращается. Сверка
состава с эффективным конфигом (`sync_membership`) по-прежнему снимает
теги, которым записи сессии больше не соответствуют.

Запись с командной строкой, для которой живого окна нет (экземпляр закрыт
после сохранения), запускается при поднятии своего workspace, как
свободные окна снимка при каждом старте: перезапуск демона возвращает
систему к последнему снимку. Запись без командной строки, для которой
живого окна нет, при живых окнах приложения снимается сразу со строкой
в журнале: процесс приложения уже работает и своих окон заново
не откроет.

Рассмотренные варианты:

- *Снимок главнее тегов и при перезапуске.* Отвергнут: перезапуск демона —
  не команда пользователя о сессии; окна двигались бы и теряли состав,
  набранный после сохранения, хотя шаг 4 обещает обратное (сценарий
  «Состав после перезапуска демона»).
- *Сверка по адресу окна.* Отвергнут по D1: тег экземпляра однозначен
  и переживает перезапуск так же.

**D9. Загрузка именованной сессии: снимок главнее тегов.** Загрузка —
явная команда «привести систему к снимку», поэтому, в отличие от
перезапуска, состав переиспользованных окон приводится к записи. Для
каждого приложения живые окна по возрастанию номера сопоставляются
с записями снимка по возрастанию номера; переиспользованное окно сохраняет
свой номер, получает теги состава из записи (лишние снимаются) и встаёт
по D7. Живые окна сверх числа записей закрываются штатным запросом, как
окна приложений, которых в снимке нет (требование «Загрузка сессии»:
окно, которого в снимке нет, закрывается). Недостающие записи
восстанавливаются, как при старте (D4, D5); первый экземпляр приложения
без живых окон запускается командой приложения, как сейчас.

Отвергнуто: оставлять лишние окна свободными — требование загрузки
закрывает окна, которых в снимке нет, и для лишнего экземпляра делать
исключение нет причины.

**D10. Ожидание окон, которые открывает сам процесс, — только после запуска
демоном и до явного действия пользователя.** Записи без командной строки
(кроме первой) ждут окон, только если демон сам запустил приложение при
восстановлении (при старте или загрузке): только тогда процесс может
открыть свои окна заново. Ожидание снимается:

- когда все записи приложения исполнены;
- нажатием клавиши приложения или командой `workspaced app` для него;
- командой сохранения сессии и загрузкой сессии;
- остановкой демона (ожидание живёт только в памяти).

Сроков нет: окно приходит событием композитора
([`docs/decisions/0007-no-timers.md`](../../../docs/decisions/0007-no-timers.md)).
Записи с командной строкой ждут окна своего процесса и снимаются
с предупреждением в журнале, если процесс завершился без окна, — как
свободные окна снимка (`on_child_exit`).

Рассмотренные варианты:

- *Срок ожидания.* Запрещён записью `0007`.
- *Снимать ожидание по первому событию `activewindow`.* Отвергнут:
  композитор сам отдаёт фокус каждому появившемуся окну, в том числе
  восстановленному, и действие пользователя по событию не отличить.
- *Ждать без конца.* Отвергнут: окно, открытое по Ctrl+N через час,
  ушло бы на место записи снимка, возможно на другой стол.

Остаётся риск, принятый сознательно: если браузер своих окон
не восстановил, а пользователь, не нажимая клавишу браузера, открыл новое
окно по Ctrl+N, это окно исполнит запись снимка и встанет на её место
(в её workspace, возможно на другом столе). Нажатие клавиши браузера или
сохранение сессии этот случай снимает.

**D11. Поднятие workspace учитывает ожидаемые экземпляры.** В `raise_on`
перед захватом свободных окон (`adopt_untagged`) и отдачей окон в общее
пользование (`share_windows`) запускаются записи с командной строкой,
у которых в `workspaces` есть поднимаемый workspace и которые ещё
не запускались. Затем для приложения `X`, у которого в поднимаемом
workspace `W` окон нет, поднятие выбирает по порядку:

1. первый экземпляр `X` (запись с наименьшим номером среди записей `X`
   в снимке) входит в `W` и ещё не исполнен — `X` запускается командой
   приложения, как сейчас;
2. у `X` есть запущенная, но не исполненная запись с командной строкой
   в `W` — поднятие окна других workspace не отдаёт и `X` не запускает:
   окно этого приложения ожидается;
3. иначе — решение D3 шага 4: окна других workspace в общее пользование,
   без них запуск.

Без второго пункта поднятие второго workspace отдало бы в общее
пользование первый экземпляр раньше, чем появится свой: neovide с номером 2,
открытый в `surf`, встретил бы там neovide с номером 1 из `work`. Для записей
без командной строки, кроме первой, поднятие не ждёт (пункт 3): если браузер
ещё не открыл окно, действует решение D3 шага 4, а окно, открытое браузером
позже, придёт в свою запись и станет вторым окном приложения в этом
workspace. Запускать для такой записи команду приложения нельзя: у работающего
браузера она открывает новое пустое окно (D3).

**D12. Совместимость форматов.** Снимок прежнего формата (у окон
приложений нет `instance`) читается без ошибки и восстанавливается
по прежнему правилу: окна приложений запускаются поднятием workspace
по одному на приложение, состав выдаётся по решению D2 шага 4, ожидания
вторых окон нет. Первое же сохранение пишет снимок нового формата.
Прежняя версия демона читает снимок нового формата: `SessionWindow`
не запрещает неизвестные поля, и `instance`, `workspaces`, `rects`
пропускаются, а `cmd` и `cwd` у окна приложения она не использует.
Откат поэтому не требует правки снимка.

**D13. Скрытое окно восстанавливается видимым.** Запись окна
на `special:hidden` сохраняет `desktop = "hidden"`, номер и состав,
а восстановленное окно встаёт по D7, то есть на свой стол. Откуда окно
было скрыто, помнит только панель (`origins` в `Workspaces.qml`), и после
перезагрузки этой памяти нет: возвращённое на `special:hidden` окно было бы
скрыто и забыто. Свободные окна снимка на `special:hidden` по-прежнему
не запускаются (`spawn_missing_foreign`): свободных окон шаг не касается.

**D14. Границы шага.** В снимок не записываются: геометрия до развёртывания
(`maximized`), незаконченный цикл клавиши (`st.cycle`), последнее окно
с фокусом (`st.focus`), история активных workspace стола (`prev_active`),
ленивые поднятия (`st.lazy` восстанавливается из активных workspace, как
сейчас). Содержимое окон демон не восстанавливает.

**D15. Прямоугольник окна приложения в снимке теперь читается.** Сейчас
прямоугольник окна приложения пишется, но нигде не читается: при старте
окна приложений из снимка не используются, а загрузка берёт у них только
имя и стол, хотя требование «Загрузка сессии» велит ставить
переиспользованное окно «на место из снимка». Этим шагом прямоугольник
используется там, где он и есть место окна: у свободного окна приложения
(D7) и у записи режима `stack` (через `rects`). В режиме обмена место
задаёт ячейка; формулировка требования «Загрузка сессии» уточняется: окно
встаёт по правилу размещения на место из снимка — ячейку своего приложения
или прямоугольник, запомненный для workspace.

**D16. Сохранение переносит записи workspace, ещё не поднятых после
старта.** Принято при реализации 23.09.2026. После перезагрузки
неактивные workspace и активные workspace других столов поднимаются
лениво, и до поднятия окон их экземпляров нет. Если бы снимок писал только
живые окна, сохранение до первого перехода на стол 2 потеряло бы записи
`surf` (номера, состав, прямоугольники `stack`), и следующая перезагрузка
вернула бы только первые экземпляры. Поэтому снимок, кроме живых окон,
пишет записи плана, которые ждут поднятия своего workspace и окна которых
с тем же тегом нет (`carried_entries`), как они есть. По той же причине
команда сохранения снимает не весь план, а ожидания окон (D10): записи,
чей процесс уже запущен, и записи без командной строки приложений,
запущенных при восстановлении; запись, которая ждёт поднятия, остаётся
в плане и исполняется при поднятии, как без сохранения. Загрузка сессии
снимает план целиком, как и сказано в D10. Отвергнуто: снимать при
сохранении весь план — это ломало бы восстановление неподнятых workspace,
а риск D10 (окно по Ctrl+N исполняет запись) касается только записей,
которые ждут окна, а не поднятия.

**D17. Свободное окно приложения, скрытое при снимке, не запускается.**
Принято при реализации. Запись без workspace на `special:hidden` не
запускается при старте — так же, как свободные окна снимка на
`special:hidden` (D13 оставляет их правило без изменений): скрытое окно
вне workspace после перезагрузки было бы скрыто и забыто. Если такое окно
всё же придёт в запись (его открыл процесс приложения), оно встаёт на
текущий стол в прямоугольник записи. Запись без workspace с `pool` встаёт
на `special:pool`.

**D18. Загрузка снимка нового формата не выдаёт состав по прежнему
правилу.** Принято при реализации. Сверка при загрузке
(`adopt_live_foreign`) выдаёт окнам с тегом экземпляра без тегов состава
состав по спискам столов (решение D2 шага 4). После загрузки снимка нового
формата состав переиспользованным окнам уже дал снимок (D9), и свободное
окно приложения (запись без `workspaces`) должно остаться свободным, а
выдача по спискам столов сделала бы его членом активного workspace стола.
Поэтому для снимка нового формата выдача отключена; сверка тегов с
эффективным конфигом остаётся. Для снимка прежнего формата и при старте
демона выдача действует, как прежде: окна прежней версии демона иначе
остались бы без состава.

**D19. Подробности реализации.** Состояния записи плана — три
(`RestoreState`): «ждёт» (запись с командой — запуска, запись без команды —
окна либо запуска первого экземпляра), «запущена (pid)», «исполнена или
снята»; исполненные записи остаются в плане, потому что по ним видно, какой
экземпляр в снимке первый (D11, пункт 1). `restore_plan` возвращает кроме
записей прямоугольники для памяти `stack` и строки о снятых записях;
`raise_restore_step` получает ещё и конфиг: запись варианта (`herdr`) ждёт
и в workspace, где описано семейство. Первый экземпляр запускается
командой приложения только по записи того же приложения, а не варианта:
команда семейства открыла бы не то окно. Приложение отмечается запущенным
при восстановлении (D10), когда поднятие запускает его первый экземпляр
(D11, пункт 1), при загрузке и при запуске свободного окна приложения
командой приложения. `workspaced status --json` показывает план (`restore`)
и такие приложения (`restore_apps`) — по ним ведутся проверки раздела 3.

## Risks / Trade-offs

- [Браузер не восстанавливает свои окна при нынешних настройках] → второе
  окно браузера не вернётся, как и сейчас; условие записано
  в `docs/host-state.md` (задача 5.4), проверка вживую 4.1 это покажет.
  Демон пустых окон не открывает (D3).
- [Окна одного процесса браузера неразличимы, порядок появления может
  не совпасть с порядком номеров] → окна встанут на места друг друга;
  содержимое не теряется, состав исправляется клавишами (D5).
- [Ctrl+N до нажатия клавиши браузера, когда браузер не восстановил свои
  окна, исполняет запись снимка] → принято (D10); снимается нажатием
  клавиши приложения или сохранением сессии.
- [Экземпляр, закрытый после сохранения, снова открывается при
  перезапуске демона] → так уже ведут себя свободные окна снимка и первые
  экземпляры приложений: перезапуск возвращает систему к снимку (D8).
- [Загрузка сессии закрывает лишние окна браузера вместе с вкладками] →
  по требованию «Загрузка сессии»; браузер хранит закрытые окна в истории.

## Migration Plan

Бинарник собирается и подменяется, `workspaced.service` перезапускается.
Снимок `default.toml` прежнего формата восстанавливается по прежнему правилу
(D12); после первой команды сохранения (Ctrl+Super+S дважды) он пишется
в новом формате. Откат — прежний бинарник: новые поля снимка он пропускает.
