# Design: Раскладка workspace в памяти

## Context

Мотивация — в `proposal.md`. Замысел серии и место изменения в ней —
[`docs/window-model.md`](../../../docs/window-model.md): раздел 2.1 (режим
приложения и исключение для приложения без ячейки), 2.3 (цикл по клавише),
2.4 (геометрия и память о состоянии окна), 2.5 (перенос workspace на стол,
общие окна). Изменение вне серии шагов 1–7, оно пересматривает решения:
[`key-cycle-stack`](../archive/2026-09-22-key-cycle-stack/design.md) — память
прямоугольников только в режиме `stack`;
[`shared-windows`](../archive/2026-09-23-shared-windows/design.md) — своё
состояние окна в каждом workspace (D6, остаётся), место общего окна
при записи (D12);
[`workspace-overrides`](../workspace-overrides/design.md) — режим
приложения без ячейки (D7, отменяется), сессии не меняются (D11);
[`session-instances`](../session-instances/design.md) — прямоугольники окна
только для workspace режима `stack` (D1, расширяется).

Что есть сейчас (демон, коммит `3c2558d`).

- **Места приложений** — `State::cells` (`workspace → приложение → Place`,
  ячейка или прямоугольник), собираются из конфига при первом обращении
  (`State::cells_of`). Главное приложение — то, у кого `Place::Cell` равна
  главной ячейке шаблона (`State::main_app`); поле `main` раздела учитывается
  только для фокуса при поднятии.
- **Обмен ячеек** (`swap_to_main`, `swap_cells`): вызванное приложение
  получает `Place::Cell(<главная ячейка>)`, прежнее главное — место
  вызванного; окна обоих ставятся по `rect_for`.
- **Память прямоугольников** `State::geom` (`workspace → адрес → прямоугольник`)
  ведётся только для workspace режима `stack`: `remember_geometry` перед
  вытеснением, `leave_geom` перед уходом общего окна, запись при поднятии
  и захвате. `raise_target` ставит окно в режиме `swap` в ячейку всегда,
  кроме переноса workspace на другой стол, а в режиме `stack` — только
  приходящее окно.
- **Режим приложения** (`Config::app_mode`): запись без ячейки в workspace
  режима `swap` выбирается в режиме `stack` (решение D7 `workspace-overrides`).
- **Шаг цикла** (`cycle_step`): активное окно — последний экземпляр
  вызванного приложения — значит конец цикла, в режиме `swap` тоже.
- **Расстановка** (`arrange`, `arrange_plan`): окна стола — по `rect_for`,
  назначения ячеек не меняются; в режиме `stack` `geom` заменяется местами
  плана.
- **Запись workspace** (`save.rs::save_workspace`): место приложения —
  прямоугольник первого экземпляра, где бы окно ни стояло (`live_rect`),
  имя ячейки — только если приложение и было в ячейке и стоит ровно в ней
  (`app_item`); `main` — `State::main_app`.
- **Снимок сессии**: `SessionWorkspace::cells` пишет `State::cells`;
  у окна `rects` только для workspace режима `stack`; `update_extra_rects`
  переписывает прямоугольник записи дополнительного приложения по окну
  и кладёт `Place::Rect` в `State::cells`.
- **Перечитывание** (`keep_cells`): назначения изменённого раздела
  снимаются и собираются заново при следующем обращении; окна встают по ним
  при следующем поднятии, потому что поднятие в режиме `swap` расставляет
  окна по ячейкам.
- **События композитора** (`src/hypr.rs`): `openwindow`, `closewindow`,
  `movewindowv2` (смена workspace композитора), `workspacev2`,
  `activewindowv2`; остальные приходят как `Other`.

## Goals / Non-Goals

**Goals:**

- Положение и размер окна, заданные пользователем, становятся местом его
  приложения в раскладке workspace и участвуют в обмене мест.
- Раскладка живёт в памяти демона и в снимке сессии, в конфиг попадает
  только по команде записи workspace.
- Закрытие последнего окна приложения возвращает его место к описанию.
- Без событий о геометрии и без опроса.

**Non-Goals:**

- Слежение за перемещением окна в реальном времени.
- Изменения панели, конфига сессии и формата конфига.
- Судьба записи дополнительного приложения сессии при закрытии окна.

## Decisions

**D1. Раскладка — места приложений, одна на workspace, в обоих режимах.**
Раскладка workspace в памяти назначает каждому приложению его раздела место:
исходное — ячейку шаблона или `rect` записи (после обмена — исходное место
другого приложения) — и, если окно сдвигали, изменённый прямоугольник.
Прямоугольник места — изменённый, а без него — исходный. В коде: `State::cells`
остаётся назначением исходных мест, рядом появляется
`State::moved: BTreeMap<workspace, BTreeMap<приложение, Moved>>`
(`Moved { rect, owner }`, об `owner` — D9), `State::rect_for` сначала смотрит
в `moved`. Раскладка нужна там, где сейчас работает `rect_for`: новое окно
(Ctrl+N), запуск приложения, окно без запомненного прямоугольника, обмен
мест, запись workspace.

Изменённое место хранится отдельно от исходного, чтобы расстановка по команде
могла вернуть окна к описанию, не отменяя обмена мест (D10), а запись
в конфиг — узнать ячейку (D11).

Рассмотренные варианты:

- *Раскладка — только прямоугольники окон* (`State::geom` для обоих режимов,
  без мест приложений). Отвергнут: в режиме `swap` стопка экземпляров
  меняется местом целиком, новое окно приложения встаёт на место
  приложения, а запись в конфиг пишет одно место на приложение — всем им
  нужно место приложения, а не набор прямоугольников окон.
- *Писать изменённое место сразу в конфиг.* Запрещено пользователем: файл
  меняется только командой записи workspace.
- *Хранить временную копию раздела workspace в формате конфига.* Отвергнут:
  повторяет `State::cells` и требует синхронизации двух представлений.

**D2. Раскладка снимается с экрана в момент действия; событий
о перемещении нет.** Hyprland 0.56.2 не сообщает о перемещении и изменении
размера окна:

- сокет событий `.socket2.sock` присылает `openwindow`, `closewindow`,
  `movewindowv2` (окно сменило workspace композитора), `activewindowv2`,
  `windowtitlev2`, `fullscreen`, `changefloatingmode` и подобные — события
  о геометрии среди них нет;
- события Lua-конфига (`HL.EventName` в `/usr/share/hypr/stubs/hl.meta.lua`):
  `window.active`, `window.class`, `window.close`, `window.destroy`,
  `window.fullscreen`, `window.kill`, `window.move_to_workspace`,
  `window.open`, `window.open_early`, `window.pin`, `window.title`,
  `window.update_rules`, `window.urgent` — тоже без геометрии.

Поэтому раскладка в памяти — это фактические прямоугольники окон, которые
демон читает у композитора (`hyprctl clients -j`) тогда, когда собирается
по раскладке действовать. Список окон демон и так читает для каждого такого
действия, лишних запросов нет. Между действиями раскладку никто не читает:
панель геометрию окон не показывает, а `workspaced status --json` показывает
раскладку на момент последнего действия.

Рассмотренные варианты:

- *Опрос положения окон.* Запрещён записью
  [`0007`](../../../docs/decisions/0007-no-timers.md); источник событий для
  этого не нужен — достаточно читать в момент действия.
- *Таймер `hl.timer` в `hyprland.lua`, сравнивающий геометрию.* Тот же опрос.
- *Привязка композитора на отпускание кнопки мыши* (`release` у
  `SUPER+mouse:272`), вызывающая команду демона. Отвергнута: срабатывает
  только при перетаскивании с Super, но не при изменении размера за край
  окна (`general.resize_on_border`), не при перетаскивании за заголовок,
  нарисованный приложением, и не при командах `half`, `place`,
  `maximize`; раскладку всё равно пришлось бы читать в момент действия,
  и путь был бы вторым.
- *Плагин Hyprland с перехватом изменения геометрии.* Отвергнут: сборка
  под каждую версию композитора и его внутренний ABI ради того, что даёт
  чтение в момент действия.

**D3. Что снимается.** Снятие раскладки workspace `W` идёт только на столе,
где `W` активен: окно другого стола стоит там в состоянии другого workspace.
Для каждой записи приложения `W` берётся первое окно `W` этой записи на этом
столе в порядке экземпляров (`placed_windows`, как у цикла), не скрытое и не
в полноэкранном режиме композитора (`fullscreen` 1 или 2: у такого окна
`hyprctl clients -j` отдаёт размер экрана, а не окна). Его прямоугольник
становится изменённым местом записи; если он совпадает с исходным,
изменённого места не остаётся. Места записей без таких окон не меняются.
Заодно для каждого окна `W` на столе запоминается его прямоугольник для `W`
(`State::geom`, D8). Окна, которые двигали команды `half`, `place`,
`maximize`, снимаются так же, как сдвинутые мышью: это тоже действия
пользователя с геометрией окна. В коде — чистая функция
`absorb_plan(cfg, st, ws, n, clients, mon)` и метод `Daemon::absorb`.

Место записи берётся у первого экземпляра — так же, как запись workspace
пишет место первого экземпляра (решение D15 `app-families`). Остальные
экземпляры в режиме `swap` при обмене встают стопкой на место приложения,
как и сейчас.

Отвергнуто: снимать только активное окно — сдвинутое и затем оставленное
окно (пользователь переключился на другое) потерялось бы.

**D4. Когда снимается.** Перед каждым действием, которое читает раскладку или
уводит окна со стола workspace:

- клавиша приложения и команда `workspaced app` — перед циклом в `W`;
- поднятие — для workspace, активного на целевом столе (вытесняемого или
  того же), и для workspace, переносимого с другого стола (перенос
  на стол — поднятие с явным столом); это заменяет `remember_geometry`;
- уход окна `W` со стола `W`: общее окно уходит за пользователем
  (`follow`) или к другому своему workspace (`send_to`), окно
  перетаскивается в другой workspace (`bring`), отделяется к другому
  workspace (`detach`) — снимается раскладка того workspace, со стола
  которого окно уходит; это заменяет `leave_geom`;
- удаление workspace из списка стола (`remove`);
- команды сохранения сессии (все столы с активным workspace) и записи
  workspace (активный на текущем столе).

Расстановка по команде раскладку не снимает, а сбрасывает (D10).

**D5. Главное приложение хранится явно, обмен передаёт места целиком.**
Главное приложение — `State::main[W]`; при первом обращении это приложение
из поля `main` раздела, а без него — приложение, записанное в главную ячейку
шаблона. Главное место — место главного приложения. Обмен мест в режиме
`swap`: сначала снимается раскладка `W` (D4), затем вызванное и главное
приложения меняются местами целиком — исходным местом вместе с изменённым
прямоугольником, — и главным становится вызванное; окна обоих встают
в прямоугольники своих новых мест. Так прямоугольник, заданный
пользователем окну Chrome AI, достаётся herdr, а Chrome AI встаёт туда,
где herdr стоял, — с его изменённым размером, если herdr тоже растягивали.
Если главного приложения нет, вызванное получает главную ячейку шаблона, как
сейчас. В коде `swap_cells` сменяется на `swap_places`, `State::main_app`
читает `State::main`.

Рассмотренные варианты:

- *Главное — приложение, стоящее в главной ячейке шаблона* (как сейчас).
  Отвергнут: после записи workspace с растянутым главным окном его место
  в файле — `rect`, главной ячейки нет ни у кого, и обмен ставил бы
  вызванное приложение в ячейку шаблона, а главное оставлял на месте;
  то же после обмена с приложением, чьё место — `rect`.
- *Менять только изменённые прямоугольники, оставляя исходные места.*
  Отвергнут: расстановка по команде вернула бы оба приложения на прежние
  исходные места и отменила бы обмен, а запись в конфиг назвала бы главным
  не то приложение.

**D6. Обмен мест в режиме `swap` для всех приложений: решение D7
`workspace-overrides` отменяется.** Без поля `mode` приложение берёт режим
workspace, в том числе приложение, место которого — `rect` (запись файла
или запись дополнительного приложения сессии). Исключение D7 было нужно,
пока место приложения без ячейки нельзя было обменять осмысленно: главное
приложение перемещалось в прямоугольник калькулятора, а подгонка окна
калькулятора пропадала при следующем поднятии. С раскладкой в памяти обмен с таким
приложением и есть то, что просит пользователь. Отказаться можно полем
`mode = "stack"` у записи приложения в workspace (шаг 5, решение D1). Первое
нажатие, которое открыло или перетащило приложение, по-прежнему выбирает его
без обмена (решение D15 `shared-windows`).

Следствия для сценариев `workspace-overrides`: «Приложение без workspace»
(калькулятор) — второе нажатие ставит калькулятор на главное место,
третье возвращает; «Клавиша переопределения при окне в активном
workspace» — Super+V меняет Chrome AI местами с herdr; «Приложение без ячейки
не меняется с главным» заменяется сценарием обмена. Решение D12
`workspace-overrides` (уточнение сценария калькулятора) теряет основание
вместе с D7.

Отвергнуто: оставить D7 и ввести раскладку только для приложений с ячейкой —
тогда пример пользователя (Chrome AI с записью сессии в `work`) не работал
бы вовсе.

**D7. Нажатие клавиши неглавного приложения в режиме `swap` ставит его
на главное место.** Шаг цикла выводится из активного окна: если активное
окно — последний экземпляр вызванного приложения, нажатие заканчивает цикл
(`key-cycle-stack`, D3). После перетаскивания окна мышью оно активно,
и Super+V вернул бы фокус herdr, ничего не переставив, — ровно то, что
пользователь назвал ошибкой. В режиме `swap` выбрать экземпляр значит
поставить приложение на главное место, поэтому окно неглавного приложения
выбранным не считается, даже если активно. Правило: в режиме `swap`, если
вызванное приложение не главное, нажатие начинает цикл заново — выбирается
активное окно, если оно экземпляр вызванного приложения, иначе первый
экземпляр, prev — первое окно главного приложения. Когда приложение уже
главное, шаг цикла прежний: следующий экземпляр, а за последним — конец
цикла и обратный обмен. В режиме `stack` правило не действует.

Выбирается активное окно, а не следующее за ним: пользователь смотрит на это
окно и его хочет видеть на главном месте. Правило «клик мышью учёта не
меняет» остаётся для приложения, которое уже главное (сценарий «Клик мышью
по экземпляру» уточнён).

Рассмотренные варианты:

- *Оставить шаг по активному окну.* Отвергнут: пример пользователя.
- *Отличать нажатие сразу после открытия или перетаскивания признаком
  в записи цикла.* Отвергнут: пользователь перетаскивает окно в `work`
  клавишей Shift+Super+V, сдвигает его мышью и нажимает Super+V —
  признак перетаскивания был бы ещё в силе, и нажатие опять закончило бы
  цикл.

Следствие: нажатие, которое открыло или перетащило приложение, выбирает его
без обмена, а следующее нажатие ставит его на главное место; возврат —
третьим нажатием. Прежде второе нажатие возвращало фокус к prev.

**D8. Память окна одинакова в обоих режимах; режим задаёт только клавишу.**
`State::geom` ведётся для всех workspace: прямоугольник окна запоминается
при снятии раскладки (D3) и при постановке окна на место в `W`. Окно,
приходящее на стол `W` (поднятие, следование за пользователем, уход к другому
своему workspace), встаёт в запомненный прямоугольник, а без него — на место
своего приложения в раскладке. Окно, которое уже стоит на столе `W` как окно
`W`, поднятие не двигает — в режиме `swap` тоже. `raise_target` теряет
признак `stack`: перенос — прежний прямоугольник, приход — запомненный или
место, остальное — не трогать. `arrive_rect`, `follow_plan`, `send_to`
и `bring` — так же. Что остаётся особенным у режима `stack`: клавиша поднимает
окно наверх, не меняя мест, а prev — активное окно workspace.

Отвергнуто: сохранить в режиме `swap` расстановку по местам при каждом
поднятии. Поднятие тогда ставило бы окна по раскладке, снятой в тот же
момент, — то есть оставляло бы первые экземпляры на месте и сдвигало только
остальные экземпляры в стопку; пользы в этом нет, а поведение режимов
расходится без причины. Вернуть стопки на места — дело расстановки
по команде.

У общего окна запомненные прямоугольники и места в раскладках разных
workspace независимы, как и прежде (решение D6 `shared-windows`): раскладка
`W` снимается только на столе `W`.

**D9. Возврат к исходному месту.** Когда в `W` не остаётся ни одного окна
приложения — окно закрыто, отделено командой отделения окна или снято сверкой
состава, — изменённое место приложения в `W` снимается, и следующее окно
приложения встаёт на исходное. То же, когда обмен мест передаёт место
с изменённым прямоугольником приложению, у которого в `W` нет окон:
изменённый прямоугольник принадлежит окну, а не месту.

Событие `closewindow` несёт только адрес, и закрытое окно уже не прочитать
у композитора. Поэтому у изменённого места хранится адрес окна, с которого
оно снято (`Moved::owner`): при закрытии или отделении окна с этим адресом
демон ищет другое окно приложения в `W`; есть — место остаётся (владельцем
становится первое оставшееся окно), нет — изменённое место снимается.
Владелец назначается при снятии раскладки, при обмене мест и при постановке
окна на место, у которого владельца нет (раскладка из снимка сессии после
перезагрузки).

Как понимается просьба пользователя после обмена: Chrome AI сдвинут в `R`,
Super+V поменял его местами с herdr — теперь `R` — место herdr, и herdr
стоит в `R`. Закрытие Chrome AI убирает изменённое место того места, которое
занимает Chrome AI (главного), а herdr остаётся в `R`: сдвигать окно, которое
пользователь видит на экране, закрытие другого окна не должно.

Рассмотренные варианты:

- *При каждом закрытии проверять все изменённые места на наличие окон.*
  Отвергнут: после перезагрузки раскладка из снимка живёт раньше, чем
  появятся окна, и закрытие любого окна стёрло бы её.
- *Снимать вместе с местом и запись дополнительного приложения сессии.*
  Отвергнут как выход за просьбу: запись снимает команда отделения окна
  (требование «Отделение окна»), закрытие её не трогало и не трогает.

**D10. Расстановка по команде сбрасывает изменения, но не обмен.**
Ctrl+Super+Пробел снимает изменённые прямоугольники всех мест `W`, окна
стола встают на исходные места, назначенные сейчас, а запомненные
прямоугольники окон `W` заменяются местами плана у окон этого стола
и забываются у окон на других столах и на `special:pool` — в обоих режимах.
Назначение мест и главное приложение команда не меняет (сценарий «Обмен
ячеек сохраняется» остаётся).

Отвергнуто: возвращать раскладку к файлу целиком, вместе с обменом, —
пользователь уже проверил и принял поведение, при котором расстановка обмен
сохраняет; полный возврат к файлу даёт перечитывание конфига.

**D11. Запись workspace пишет раскладку.** Команда записи workspace снимает
раскладку активного workspace текущего стола и пишет в раздел места
приложений из неё: прямоугольник места, совпадающий с ячейкой шаблона, —
именем этой ячейки (сначала проверяется исходная ячейка места, затем ячейки
шаблона по порядку), иначе `rect`; `main` — главное приложение. Общее окно,
ушедшее за пользователем на другой стол, даёт место из раскладки этого
workspace, а не своё нынешнее положение (прежний `live_rect` брал положение
окна, где бы оно ни стояло, и записывал место из другого workspace).
Порядок записей, `chain`, `mode` и комментарии сохраняются по решению D9
`workspace-overrides`. После записи раскладка workspace собирается заново
из записанного файла (D12): изменённые места становятся исходными.

**D12. Перечитывание изменённого раздела применяет раскладку сразу.**
Сейчас правка раздела доходит до окон при следующем поднятии, потому что
поднятие в режиме `swap` расставляет окна по ячейкам. После D8 поднятие окна
на столе не двигает, поэтому правка раздела (в том числе откат `chezmoi
apply`) иначе до экрана не дошла бы. Решение: у workspace, чей раздел
изменился или исчез, перечитывание снимает раскладку в памяти (назначение
мест, главное приложение, изменённые места) и запомненные прямоугольники
окон, раскладка собирается заново из нового файла, и если workspace активен
на каком-либо столе, его окна на этом столе сразу встают на места из файла
без смены фокуса и порядка по глубине. Окна неактивного workspace встанут
на места при его поднятии: запомненных прямоугольников у них больше нет.
После записи workspace (D11) это не сдвигает первые экземпляры: файл
записан с их мест.

Рассмотренные варианты:

- *Применять при следующем поднятии с признаком «раскладка собрана заново
  и ещё не применена».* Отвергнут: пока признак в силе, снятие раскладки
  пришлось бы пропускать, и после Ctrl+Super+W сдвинутое окно не меняло бы
  место до поднятия workspace — ровно то, что пользователь делает сразу
  после записи.
- *Не применять вовсе.* Отвергнут: требование «Слежение за конфигом» велит,
  чтобы правка файла возвращала расстановку без перезапуска демона.

**D13. Снимок сессии хранит раскладку; прямоугольник записи сессии не
переписывается.** Раскладка — часть состояния workspace между сохранениями,
как назначения ячеек, которые снимок уже хранит. Команда сохранения сессии
снимает раскладку всех столов с активным workspace и пишет у workspace
главное приложение (`main`) и изменённые места (`moved`, таблица «приложение →
прямоугольник»), а у окна — прямоугольники по всем его workspace, не только
режима `stack` (пересмотр D1 `session-instances`: там прямоугольник для
режима обмена не писался, потому что место задавала ячейка, а теперь окно
может стоять не на месте приложения — например, второй экземпляр).
Восстановление и загрузка ставят окно в прямоугольник записи для workspace,
а без него — на место приложения в раскладке, одинаково в обоих режимах.

Прямоугольник записи дополнительного приложения сессии — место, с которым
приложение принято, — команда сохранения сессии больше не переписывает
(`update_extra_rects` и `extra_rect` уходят): сдвинутое окно даёт
изменённое место в раскладке, как у приложения конфига, и расстановка
по команде возвращает его на место приёма. Прежняя перезапись к тому же
клала `Place::Rect` в назначение места и после обмена мест отнимала у
приложения главное место — с явным главным приложением (D5) и отдельным
изменённым местом этого больше нет.

Рассмотренные варианты:

- *Не писать раскладку в снимок.* Отвергнут: после перезапуска демона обмен
  мест (он уже в снимке) остался бы, а прямоугольники, между которыми
  обменивались, пропали бы.
- *Оставить перезапись прямоугольника записи сессии.* Отвергнут: два
  источника одного места — запись и раскладка — и потеря главного места
  после обмена.

**D14. Совместимость.** Поля `main` и `moved` у workspace в снимке
необязательные: снимок прежнего формата читается, главное приложение тогда —
по полю `main` раздела конфига или главной ячейке, изменённых мест нет.
Прежняя версия демона пропускает новые поля: `SessionWorkspace` неизвестных
полей не запрещает. Прямоугольники `rects` у окна для workspace режима `swap`
прежняя версия читает и кладёт в память, которой в режиме `swap` не
пользуется.

**D15. Состояние для проверок.** `workspaced status --json` дополняется
полями `main` (workspace → главное приложение) и `moved` (workspace →
приложение → прямоугольник) рядом с существующим `cells`: по ним ведутся
проверки раздела 3 `tasks.md`. Требование «Состояние для панели» перечня
полей ответа `status` не содержит и не меняется; панель новых полей не
читает.

**D16. Порядок архивации.** Требования взяты из дельт `workspace-overrides`
(«Цепочка приложения», «Файл конфига и его разделы», «Запись по команде
сохранения») и `session-instances` («Файлы сессий», «Загрузка сессии»,
«Восстановление при старте»), поэтому изменение архивируется после них.
Требование «Раскладка клавиш сессии» (hyprland-binds) не меняется: строки
о Ctrl+Super+S и Ctrl+Super+Пробел остаются верными («обновляет места
дополнительных приложений по нынешнему положению окон», «окна
приложений — на свои места»).

OpenSpec не даёт убрать или переименовать сценарий в изменённом
требовании: при архивации он потерялся бы. Поэтому сценарии, чьё
поведение меняется, сохраняют прежние имена с новым содержанием:
«Ручная подгонка сохраняется до следующего поднятия» (подгонка сохраняется
и после поднятия), «Приложение без ячейки не меняется с главным» (теперь —
при `mode = "stack"` у записи), «Прямоугольник режима stack в снимке»
(прямоугольник пишется для обоих режимов), «Места дополнительных приложений
обновляются» и «Места описанных приложений не трогаются» (через раскладку
в снимке, файл конфига не меняется).

## Risks / Trade-offs

- [Раскладка видна демону только в момент действия] → `workspaced status
  --json` между действиями показывает раскладку на момент последнего
  действия; проверки сначала выполняют действие (D2, D15).
- [Обмен с маленьким окном уводит главное приложение в маленький
  прямоугольник] → это и просил пользователь; для записи, которой это
  не нужно, есть `mode = "stack"` (D6).
- [Второе нажатие после открытия или перетаскивания теперь ставит приложение
  на главное место, а не возвращает фокус] → поведение цикла в режиме
  `swap` стало единым: выбрать — значит поставить на главное место (D7).
- [Экземпляры, кроме первого, при обмене встают стопкой на место
  приложения, даже если их двигали отдельно] → так устроена стопка в режиме
  `swap`; при поднятии их прямоугольники сохраняются (D3, D8).
- [Сохранение файла конфига сдвигает окна активного workspace, если раздел
  изменился] → это и есть применение правки; после записи workspace первые
  экземпляры уже на своих местах (D12).

## Migration Plan

Бинарник собирается и подменяется, `workspaced.service` перезапускается.
Снимок прежнего формата читается (D14); раскладка при перезапуске
без перезагрузки снимается с экрана при первом же действии, поэтому окна
не сдвигаются. Откат — прежний бинарник: он пропускает новые поля снимка,
а в режиме `swap` снова расставляет окна по ячейкам при поднятии.
