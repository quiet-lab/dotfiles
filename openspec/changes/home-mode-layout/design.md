# Design: Режим home — раскладка по домам

## Context

Мотивация — в `proposal.md`. До изменения (коммит демона `7a0aab8`):

- Раскладка workspace в памяти — назначения мест `State::cells`, главное
  приложение `State::main`, изменённые места `State::moved`, запомненные
  прямоугольники окон `State::geom` (изменение `live-layout`, решения
  D1–D5). Назначения при первом обращении — места записей раздела
  эффективного конфига (`State::cells_of`).
- Режим `swap`: клавиша неглавного приложения меняет его местами с главным
  целиком, с изменённым прямоугольником (`swap_places`); конец цикла —
  обратный обмен. Режим `stack`: подъём окна без переноса.
- Расстановка (`arrange_layout`) и перечитывание изменённого раздела
  снимают раскладку через `State::reset_layout`, и она собирается из файла
  заново (изменение `arrange-restores-config`).
- Порядок ячеек шаблона в памяти — по именам (`BTreeMap`).

## Решения

### D1. Отдельный режим `home`, а не переделка `swap`

Домашнее место приложения — его место в разделе эффективного конфига
(ячейка или `rect`; у дополнительного приложения сессии — прямоугольник
записи). Клавиша приложения `A` режима `home` пересобирает назначение мест
целиком (`home_layout`, `home_to_main_plan`): `A` — в главной ячейке
шаблона и главное, остальные — по домам, вытесненные — в свободные ячейки
(D2, D3). Окна приложений, чьё место изменилось, встают в прямоугольники
новых мест (`Daemon::home_to_main`), остальные окна не двигаются. Цикл,
prev, перезапуск цикла клавишей неглавного приложения и конец цикла
общие с `swap` (`Mode::takes_main`): prev — первое окно приложения,
главного в начале цикла, а конец цикла — то же действие для него.

Рассмотренные варианты:

1. Третье значение поля `mode`. **Выбран** пользователем: `swap` остаётся
   по умолчанию и без изменений, режим задаётся там, где нужен.
2. Переделать `swap` под правило «по домам». Отвергнут: обмен мест целиком
   — решение D5 `live-layout`, на него опираются сценарии и записи
   workspace других разделов.
3. Признак у шаблона. Отвергнут: поведение клавиши задаёт поле `mode`
   у workspace и у записи, шаблон описывает только геометрию.

Пересчёт целиком, а не перестановка двух приложений, делает правило
«приложение, стоящее не на своём месте, уступает его хозяину» следствием:
каждое нажатие начинает с домов.

### D2. Вытесненные разбираются в порядке записей раздела

Вытесненным считается приложение, чей дом — главная ячейка, кроме `A`.
Таких бывает несколько, если дом в главной ячейке у нескольких записей;
они берут свободные ячейки по порядку записей раздела — по тому же порядку,
по которому конец цикла выбирает следующее приложение. Приложение
с несколькими окнами занимает место стопкой.

Рассмотренные варианты: порядок раздела (**выбран** пользователем);
порядок, в котором приложения были главными (отвергнут: нужна история
нажатий, а пересчёт в D1 её не хранит).

### D3. Сначала освобождённый дом вызванного, затем шаблон по порядку

Свободной считается ячейка шаблона, которая не главная, не дом приложения,
оставшегося дома, и ещё не занята другим вытесненным. Первым берётся дом
`A`, если он ячейка и свободен, затем остальные свободные ячейки в порядке
записи в шаблоне. Так herdr уходит туда, откуда пришло вызванное
приложение, и после возврата `A` домой меняется местами только пара
«`A` — herdr», как при обмене. Ради порядка шаблона ячейки шаблона хранятся
в порядке файла (`IndexMap`), иначе порядок был бы алфавитным.

Без свободной ячейки вытесненное встаёт стопкой в дом `A`. Если дом `A` —
прямоугольник (дополнительное приложение сессии или запись с `rect`),
вытесненное встаёт в этот прямоугольник: правило «стопкой в дом `A`»
применено буквально, хотя прямоугольник может быть меньше ячейки.
Решено самостоятельно по духу правила («вытесненное — в освободившееся
место»); при неудобстве вытесненное возвращается в центр клавишей.

Рассмотренные варианты: дом `A` первым (**выбран** пользователем); строго
по порядку шаблона (отвергнут: в `work` без Chrome herdr уходил бы
в `left_bottom`, а `left_top` пустовала бы).

### D4. Изменённый прямоугольник принадлежит дому

У приложения режима `home` изменённый прямоугольник действует, только
пока приложение стоит дома (`State::moved_applies`, `State::at_home`):
в главной ячейке и в чужой свободной ячейке окно получает геометрию
ячейки. Снятие раскладки (`absorb_plan`) у такого приложения вне дома
изменённый прямоугольник не меняет, а уход из дома его не снимает —
вернувшись, приложение встаёт в свой прямоугольник. Снятие при закрытии
последнего окна (D9 `live-layout`) и при расстановке не меняется.

У приложения другого режима, чьё место изменила клавиша режима `home`
(смешанный раздел, D7), изменённый прямоугольник снимается: в `swap` он
принадлежит месту, а место сменилось.

Рассмотренные варианты: прямоугольник у дома (**выбран** пользователем);
прямоугольник у места, как в `swap` (отвергнут: растянутое в центре окно
передавало бы размер следующему вызванному).

### D5. Раскладка при первом обращении и расстановка

У workspace, чьё поле `mode` — `home`, `State::cells_of` при первом
обращении собирает раскладку по домам с главным приложением по конфигу
(поле `main`, без него — запись с домом в главной ячейке) в главной
ячейке (`config_main`, `home_layout`). Расстановка и перечитывание
раздела по-прежнему снимают раскладку через `State::reset_layout`
и получают ту же раскладку по домам: «главное приложение из `main`
в главной ячейке, остальные по домам». У workspace режима `swap`
с отдельными записями `home` раскладка при первом обращении — просто
дома, как раньше.

### D6. Запись workspace пишет дома

Команда записи workspace (Ctrl+Super+W) пишет у приложения режима `home`
его домашнее место с изменённым прямоугольником, если он есть
(`save::record_place`), а `main` — главное приложение; после записи
раскладка собирается заново, и главное приложение остаётся в центре.
Нынешнее место вне дома в файл не попадает: оно следствие нажатия,
а не описание. Поле `mode = "home"` в разделе сохраняется.

Правило записано в требовании «Расстановка окон» (ws-daemon) рядом
с остальной семантикой режима, а не в требовании «Запись по команде
сохранения» (ws-config): его полный текст есть в дельтах ещё
не архивированных `live-layout` и `session-windows-transient`, и правка
там потребовала бы переносить и их.

### D7. Смешанные режимы в одном разделе

`mode = "home"` допустим и у записи в workspace другого режима, и наоборот:
действие клавиши определяет режим вызванного приложения, как и прежде.
Клавиша режима `home` пересчитывает назначения из домов (D1), обмен мест
приложения режима `swap` в разделе `home` идёт по правилам `swap`;
следующая клавиша режима `home` возвращает всех по домам. Отдельных
запретов проверка конфига не вводит: у записей общей цепочки режим
по-прежнему один (решение D3 `shared-app-chain`).

### D8. Состояние и подсказка

`workspaced status --json` показывает у режима `home` то же, что у `swap`:
`cells` — нынешнее назначение мест, `main`, `moved`. Режимов ни `status`,
ни `keys --json` не выводят, поэтому их вывод не меняется.

### D9. Постановка окна задаётся дважды

При проверке вживую окно, переносимое из ячейки высотой 1065 в ячейку
высотой 2140, вставало в 2141 px: Hyprland 0.56.2 меняет размер плавающего
окна вокруг его центра, при нечётной разнице высот положение становится
дробным, и после переноса окно на пиксель выше. Снятие раскладки принимало
это за сдвиг мышью. `hypr::d_place` теперь подаёт пару «размер, положение»
дважды: вторая пара снимает дробную половину пикселя. Это исправление,
возвращающее поведение к требованию «Расстановка окон» (прямоугольник —
ровно как записан); требование не меняется.

### D10. Раскладка снимка со старым шаблоном

Снимок сессии хранит назначения мест именами ячеек. После смены шаблона
`work` (`thirds` → `thirds-split`) снимок называл ячейки `left`, которых
в новом шаблоне нет, и окна оставались без места. Загрузка снимка
(`session::apply_lists`, `stale_cell`) теперь отбрасывает раскладку
workspace (назначения, главное приложение, изменённые места), если она
называет ячейку не из нынешнего шаблона, и раскладка собирается из конфига;
записи дополнительных приложений сессии сохраняются. Требования
ws-sessions не правятся: прежде поведение при такой ячейке не было
определено, а их полные тексты есть в дельтах трёх ещё не архивированных
изменений.

### D11. Дельты соседних изменений переносятся сюда

Требования «Цепочка приложения» и «Расстановка окон» (ws-daemon), «Файл
конфига и его разделы» (ws-config) изменены в ещё не архивированных
`live-layout`, `work-area-center` и `shared-app-chain`; их поздняя
архивация затёрла бы режим `home` полным текстом без него. Поэтому дельты
этого изменения построены на последних текстах (`shared-app-chain`
для «Цепочки приложения», `work-area-center` для «Расстановки окон»,
`live-layout` для «Файла конфига и его разделов»), а дельты этих требований
там сняты — так же, как в D2 изменения `arrange-restores-config`.
С архивацией этого изменения их правила входят в основную спецификацию.

## Risks / Trade-offs

- Раскладка по домам пересчитывается каждым нажатием: сдвиг мышью окна,
  стоящего вне дома, держится только до следующей перестановки этого
  приложения.
- Правила `live-layout`, `work-area-center` и `shared-app-chain`
  для перенесённых требований попадают в основную спецификацию раньше
  архивации этих изменений (D11).
