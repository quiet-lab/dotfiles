# Design: Окна сессии живут в workspace, пока открыты

## Context

Мотивация — в `proposal.md`, модель окон — в
[`docs/window-model.md`](../../../docs/window-model.md), разделы 2.4, 2.5
и 2.7. Решение пользователя от 29.09.2026 из четырёх пунктов:

1. Окно, открытое в workspace по ходу работы и не описанное в его разделе
   конфига, входит в workspace, пока открыто, но в конфиг не попадает.
   С закрытием последнего окна приложения запись о нём (дополнительное
   приложение сессии) исчезает из workspace.
2. Запись workspace (Ctrl+Super+W) сохраняет в разделе конфига все окна,
   открытые в нём в этот момент.
3. Сохранение сессии (Ctrl+Super+S дважды) конфиг не меняет и запоминает,
   какие окна, не входящие в конфигурацию workspace, сейчас в нём открыты:
   командную строку, каталог и прямоугольник.
4. Восстановление сессии сначала поднимает workspace по конфигу, затем
   запускает окна из сохранённого списка, которых в конфиге нет. Такое окно
   входит в workspace по пункту 1. Пока окно не появилось, запись ожидания
   не забирает окон других workspace: приложение запускается своей командой.

Поправка пользователя к пункту 4 (29.09.2026): общие окна остаются общими
независимо от того, как запущены. Запись сессии получает общее окно своего
приложения, окно, общее при сохранении, возвращается одним окном во все
свои workspace, а запрещено брать только окна другого приложения — варианта
по семейству (решение D3).

Сверка с действующими спецификациями (в редакции после архивации активных
изменений) и кодом демона (коммит `d1cff0c`):

- **Пункт 1 расходится.** ws-sessions, «Дополнительные приложения сессии»:
  запись снимается при появлении приложения в конфиге, при исчезновении
  workspace и по команде отделения. Закрытие окна запись не снимает:
  обработчик `closewindow` (`Daemon::on_event`) снимает только изменённое
  место (`drop_moved_of`).
- **Запись без окон забирает чужие окна.** ws-daemon, «Захват открытых окон
  приложения»: приложению без окон в поднимаемом workspace достаются окна
  других workspace. Правило действует для всех приложений эффективного
  конфига, в том числе для записей сессии (`share_plan`). Так 28.09.2026
  запись `wezterm` в `surf`, оставшаяся от закрытого окна, получила по
  семейству окно herdr из `work`.
- **Пункт 2 расходится в мелочи.** ws-config, «Запись по команде
  сохранения»: дополнительные приложения сессии записываются все
  (`save_workspace` берёт `State::extra[ws]` целиком), в том числе запись
  без окон.
- **Пункт 3 совпадает.** `save_session` принимает неучтённые окна столов
  по общему правилу и пишет записи дополнительных приложений с классом,
  командной строкой, каталогом и прямоугольником; конфиг не меняется.
  После пункта 1 в снимок сами собой попадают только записи с окнами.
- **Пункт 4 расходится частично.** ws-sessions, «Восстановление при старте»:
  дополнительное приложение восстанавливается «так же, как приложение
  конфига», значит и с отдачей окон других workspace. Приложения записей
  сессии в разделе эффективного конфига стоят после приложений файла
  (`merge_extra` дописывает их в конец), поэтому запускаются позже;
  но экземпляры с командной строкой запускаются до всех приложений.

## Goals / Non-Goals

**Goals:** запись сессии живёт, пока есть её окно; записи сессии получают
общие окна своего приложения, но не окна вариантов по семейству;
восстановление сначала поднимает конфиг, затем окна сессии; запись
workspace не пишет записей без окон.

**Non-Goals:** формат снимка, правила принятия окна (ws-daemon, «Посторонние
окна»), команда отделения, клавиши приложений. Записи сессии остаются
в эффективном конфиге, как прежде.

## Decisions

### D1. Запись снимается при закрытии последнего окна в её workspace

После каждого события `closewindow` демон проверяет все записи сессии:
запись, у приложения которой в её workspace не осталось окон (по тегам
состава, с окнами вариантов, которые workspace отдельно не описывает,
и со скрытыми окнами), снимается вместе с местом в раскладке
(`sweep_extras`). Если окон приложения не осталось нигде, запись
с командой запуска снимается во всех workspace — то же правило, что при
отделении последнего окна (`drop_extra_app`): программа уходит из сессии.

Проверяются все записи, а не записи закрытого окна: закрытое окно
у композитора уже не прочитать, а какие у него были теги, демон не хранит.
Проверка дешёвая: записей немного, а список окон обработчик события и так получает.
Это верно, потому что без окон, кроме ожидающих (D2), записи не живут:
запись заводится вместе с окном, а уходят окна только закрытием,
отделением (снимает запись само) и сверкой состава (запись к этому времени
уже снята).

Отвергнуто: хранить у демона копию тегов окон ради закрытия — второе
состояние, которое нужно поддерживать при каждом изменении тегов.

### D2. Запись из снимка ждёт своего окна

Запись, взятая из снимка при старте или загрузке сессии, живёт без окон,
пока её окно не появится: `State::extra_wait` хранит пары (workspace,
приложение), `apply_lists` заносит туда все записи снимка. Закрытие окон
такую запись не снимает, а снимок переносит её как есть — так же, как
записи экземпляров, ждущие ленивого поднятия (`carried_entries`).
Исключение — закрытие последнего окна приложения вообще (D1): программа
уходит из сессии, и ожидающие записи уходят вместе с ней, как при
отделении.

Запись выходит из ожидания, когда у приложения появляется окно в её
workspace (`settle_extra_wait`). Окно входит в workspace разными путями:
ожидание запуска, запись снимка экземпляра, захват при поднятии, живое
окно при перезапуске демона. Поэтому сверка выполняется после каждого
сообщения демону (событие композитора, команда, выход процесса) и после
старта. Композитор при этом спрашивается, только пока ожидающие записи
есть. Это не опрос: сверка идёт по событию и видит итог его обработки.

Отвергнуто: держать записи снимка вне эффективного конфига до появления
окна. Восстановление экземпляров выдаёт окну теги состава только тех
workspace, которые описывают его приложение в эффективном конфиге
(`entry_members`), и место окна берёт из раскладки; без записи окно
не вошло бы в свой workspace.

Если запуск записи не дал окна (процесс вышел), запись остаётся ждать:
сроков у ожидания нет, следующее поднятие workspace запускает приложение
снова. Решение принято по ходу работы: пользователь об этом случае
не говорил, а снимать запись по выходу процесса нельзя — одноэкземплярное
приложение (Telegram) передаёт окно уже работающему процессу и выходит.

### D3. Запись сессии получает общее окно своего приложения, но не окна вариантов

Поправка пользователя от 29.09.2026: «Общие окна должны оставаться общими.
Вне зависимости от того, как они запущены». Окно приложения конфига и окно,
открытое по ходу работы, одинаково могут быть общими для нескольких
workspace. Поэтому запись сессии — дополнительное приложение и запись
о месте приложения конфига — при поднятии workspace получает окна других
workspace с тегом экземпляра своего приложения, как приложение раздела
файла. Запрещено только одно: окна варианта по семейству (`share_plan`,
параметр `session`: для записей сессии берутся окна, чей тег называет само
приложение записи). Окно варианта принадлежит другому приложению, и запись
семейства не должна его забирать — это и был случай 28.09.2026: запись
`wezterm` в `surf` получала окно herdr.

Узкий запрет случай 28.09 закрывает полностью: запись закрытого окна
wezterm снимается с закрытием (D1), а ждущая запись `wezterm` из снимка
получает только окна с тегом `app:wezterm#…`, но не `app:herdr#…`.
Приложения раздела файла получают окна вариантов по семейству, как прежде.

Окно, которое при сохранении было общим, восстанавливается одним
экземпляром во все свои workspace: запись экземпляра хранит состав
и прямоугольники по workspace (изменение `session-instances`), запись
о месте приложения в каждом workspace получает это же окно, второй
экземпляр не запускается.

Отменено прежнее решение этого изменения: записи сессии не получали окон
других workspace совсем, и запись о месте `chrome-ai` в `work` без записи
экземпляра запускала второе окно браузера. Пользователь его отверг.

### D4. Порядок восстановления: сначала конфиг, затем окна сессии

Поднятие workspace запускает приложения в порядке раздела эффективного
конфига. Записи сессии `merge_extra` дописывает в конец раздела, поэтому
приложения файла запускаются первыми. Экземпляры снимка с командной
строкой делятся (`instance_launches`): экземпляры приложений файла
запускаются, как прежде, до захвата и запуска приложений, а экземпляры
записей сессии — после приложений конфига. Приложение записи сессии,
чей экземпляр запускается позже, получает шаг `Wait` и не запускается
второй раз своей командой.

### D5. Запись workspace пишет только записи с окнами

`save_workspace` пропускает записи сессии без окон в workspace
(`absent_records`): в `[apps]`, в таблицу `apps` раздела и в поле `main`
они не попадают. Такие записи — только ожидающие (D2) — остаются в сессии:
окно, которое ещё не открылось, не входит в workspace «в этот момент».

### D6. Сохранение сессии не меняется

Пункт 3 совпадает с действующим поведением (см. Context), код команды
сохранения не меняется. В спецификацию добавлено, какие записи попадают
в снимок: записи с окнами и ожидающие записи.

## Risks / Trade-offs

- Закрытие последнего окна программы снимает и её ожидающие записи в других
  workspace (D1, D2): если после перезагрузки Telegram, восстановленный
  в `work`, закрыт до первого перехода на стол `surf`, где он тоже был, то
  `surf` его не запустит. Так же работает отделение.
- Сверка ожиданий после каждого сообщения стоит одного запроса списка окон,
  пока ожидающие записи есть; после восстановления их не остаётся.
- Поведение меняется только в обработке событий: проверить его можно
  перезагрузкой и закрытием окна; перезагрузку и оценку того, что окна
  встали на места, выполняет пользователь.
