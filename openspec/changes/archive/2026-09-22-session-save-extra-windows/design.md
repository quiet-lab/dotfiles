# Design: Дополнительные окна workspace на уровне сессии

## Context

Мотивация — в `proposal.md`; место изменения в серии — в
[`docs/window-model.md`](../../../docs/window-model.md) (раздел 2.7 «Сессии»
и план серии в разделе 5). Что есть сейчас в демоне:

- Состав workspace задаёт только конфиг: `raise` берёт список приложений из
  `cfg.workspaces[ws].apps`, а место окна — из `State::cells` (назначения,
  засеянные из конфига при первом обращении к workspace).
- Окно без тега `app:` — постороннее: демон помнит его команду и каталог
  в `State::foreign`, но за workspace оно не следует и в состав для панели не
  входит.
- Частью workspace постороннее окно становится единственным способом — командой
  `save-workspace`, которая правит `config.toml` через `toml_edit`.
- `reload_config` оставляет `State::cells` как есть: назначения пересобираются
  только у workspace, к которым демон ещё не обращался.
- Снимок сессии (`state.rs`, `Session`) хранит списки столов, назначения ячеек
  по workspace и плоский список окон: у окна приложения — имя приложения, у
  постороннего — командная строка и каталог.

Решение пользователя от 22.09.2026, которое это изменение выполняет: сохранение
сессии не меняет конфиг и поведение workspace, а только запоминает
дополнительные приложения активного workspace; для записи в конфиг нужна
отдельная комбинация клавиш. Клавиши заданы пользователем:
`CTRL+SUPER+s CTRL+SUPER+s` — сохранить сессию, `CTRL+SUPER+s CTRL+SUPER+w` —
записать workspace в конфиг; прежняя `SUPER+TAB SUPER+s` снимается.

## Goals / Non-Goals

**Goals:**

- Случайное нажатие не правит файл под chezmoi: файл меняет только цепочка,
  которая кончается на `w`.
- Окно, открытое по ходу работы, можно одной командой сделать частью workspace
  на время сессии, не трогая конфиг.
- Дополнительное приложение сессии ведёт себя как приложение конфига во всём,
  кроме места хранения: переезды, парковка, расстановка, плитка панели,
  восстановление.
- Снимки прежнего формата читаются без ошибки.

**Non-Goals:**

- Демон не принимает окна в workspace сам: правило «окно входит по событию
  своего появления» — шаг 3 серии, и для него нужна проба о диалогах.
- Поведение клавиши приложения не меняется: цикла по экземплярам и режима
  `stack` здесь нет.
- Общие окна двух workspace не вводятся: дополнительное приложение живёт
  ровно в одном workspace.

## Decisions

**D1. Эффективный конфиг = файл плюс дополнительные приложения сессии.**
Демон держит два значения: `cfg_file` — то, что прочитано из `config.toml`,
и `cfg` — эффективный конфиг, где к приложениям добавлены дополнительные
приложения сессии, а к таблицам `apps` соответствующих workspace — их места.
Всё, что уже написано поверх `cfg` (поднятие, цепочка приложения, захват окон,
парковка, состояние для панели, запуск приложений), продолжает работать без
изменений и само собой начинает учитывать дополнительные приложения.

Отвергнуто: отдельный список дополнительных приложений, который каждое место
кода учитывает само. Он потребовал бы правки десятка функций (`raise`,
`make_main`, `app`, `remove`, `state_json`, `rect_for`, `adopt_plan`,
`spawn`, загрузка сессии), и каждая пропущенная означала бы, что окно
где-то ведёт себя не как приложение.

**D2. Запись дополнительного приложения живёт в снимке при своём workspace.**
В `SessionWorkspace` рядом с `cells` появляется таблица `extra_apps`:
имя → `{ class, cmd, cwd, rect }`. Имя — ключ таблицы, поэтому в конфиг оно
переезжает как есть. Поле `extra_apps` необязательное, и снимок прежнего
формата читается без ошибки.

Отвергнуто: хранить дополнительные приложения отдельным разделом верхнего
уровня со ссылкой на workspace — тогда сведения об одном workspace лежат
в двух местах, а при удалении workspace из конфига их надо чистить отдельно.

**D3. Запись без `cmd` называет приложение конфига и задаёт ему только место.**
Если посторонним оказалось окно, подходящее по `class` и `title` приложению,
которое в конфиге уже описано, новой записи о приложении не появляется: окно
получает тег этого приложения, а в сессию попадает запись с одним лишь
прямоугольником — она добавляет приложение конфига в этот workspace.

Так закрывается изъян из `todo.md`: окно `google-chrome-ai` — это окно
приложения `chrome-ai`, а не повод завести приложение с командой
`/opt/google/chrome/chrome`, которой на хосте нет. Если приложение уже входит
в этот workspace, записи не появляется вовсе: окно просто становится ещё одним
его экземпляром и встаёт на место приложения при следующем поднятии.

**D4. Конфиг главнее сессии.** Если в конфиге появляется приложение с именем
дополнительного приложения сессии, сессионная запись снимается
с предупреждением в журнале. Запись «только о месте» (D3) снимается, когда
приложения с таким именем в конфиге не стало. Так же снимается запись, чей
workspace из конфига исчез. Проверка выполняется при каждой пересборке
эффективного конфига, то есть при чтении конфига, при перечитывании и при
восстановлении сессии.

**D5. Имя нового дополнительного приложения — по классу окна, как у команды
записи в конфиг.** Класс приводится к нижнему регистру, недопустимые знаки
заменяются дефисом, совпадение с уже занятым именем разводится суффиксом
`-2`, `-3`. Правило и код те же, что у `save-workspace`, поэтому переезд
записи из сессии в конфиг имя не меняет.

Цена решения: два посторонних окна одного класса становятся двумя
приложениями с одинаковым выражением `class`. Пока живут теги, окна
различаются; после перезапуска демона без тегов (например, после перезагрузки
системы) оба окна достаются первому приложению по имени, а второе
запускается заново. Это та же цена, что у неотличимых окон одного процесса,
и отдельного решения здесь не требуется: окна разных приложений обычно
различаются классом.

**D6. Сохранение сессии не трогает места уже описанных приложений.** Команда
добавляет в назначения ячеек workspace записи только о вновь принятых окнах.
Ни `main`, ни места приложений, которые в workspace уже есть, не меняются:
именно из-за их правки случайное нажатие прежней цепочки портило
и расстановку, и конфиг.
Запись о новом приложении добавить необходимо — без неё демон не знал бы, куда
ставить окно.

**D7. Окно без командной строки в сессию не попадает.** Если `/proc` не дал
команду (процесс уже вышел, окно чужого пользователя), восстановить приложение
нечем. Такое окно остаётся свободным, а в журнал идёт строка с адресом
и классом. Так же поступает и снимок сессии с посторонними окнами.

**D8. Перечитывание конфига сбрасывает ячейки изменённого workspace.**
При перечитывании демон сравнивает раздел каждого workspace в прежнем и новом
файле; если раздел изменился, назначения ячеек этого workspace снимаются
и при следующем обращении собираются из нового файла. Ячейки workspace,
раздел которого не менялся, остаются: иначе обмен ячеек по клавише
сбрасывался бы каждой правкой соседнего workspace.

Сравнивается только раздел workspace. Изменение шаблона на назначения не
влияет: назначение хранит имя ячейки, а прямоугольник берётся из шаблона
в момент расстановки.

**D9. Поиск приложения по окну идёт сначала по вариантам, затем по
семействам.** Тот же порядок, что у захвата открытых окон (`adopt_plan`):
более точное совпадение побеждает, внутри каждой группы — по именам. Так окно
Chrome профиля `AI.dev2026` достаётся варианту `chrome-ai`, а не семейству.

**D10. Команда записи в конфиг сохраняет имя `save-workspace`.** Меняется
только цепочка. Имя подкоманды и действия `[[binds]]` остаются, чтобы
не ломать то, что на них ссылается, а новая команда называется `save-session`
по действию, а не по клавише.

**D11. Восстановление дополнительного приложения идёт обычным путём запуска
приложения.** Отдельного механизма нет: приложение есть в эффективном
конфиге, поэтому `raise` запускает его, если окон нет, а `spawn` берёт команду
и каталог из записи. Окно опознаётся по потомкам процесса и по выражению
`class`, собранному из сохранённого класса (`regex::escape`).

Отсюда известное ограничение: окно программы из контейнера (distrobox)
восстановить не удастся — в `/proc` лежит путь внутри контейнера. Оно и
сегодня так для посторонних окон снимка; обходится записью в конфиг вручную,
как это сделано для Яндекс.Браузера.

**D12. Демон работает по событиям, таймеров в нём не остаётся.** Запрет
таймеров шире одного изменения, поэтому он записан отдельно:
[`docs/decisions/0007-no-timers.md`](../../../docs/decisions/0007-no-timers.md).
Здесь — что именно переведено на события. Раньше в демоне был поток тактов
(сообщение каждые 100 мс), и на нём держалось три вещи:

- **Снимок сессии.** Был отложенной записью: обработчик ставил отметку, а такт
  через 500 мс писал `default.toml`. Стал записью в самом обработчике —
  события композитора (открытие, закрытие и перемещение окна, смена стола)
  и команды, изменившей состояние. Команда пишет снимок до ответа клиенту,
  поэтому к возврату команды файл уже обновлён. Какие команды считаются
  изменяющими состояние, решает `changes_state`; `status`, `sessions`
  и `session list` файла не трогают.
- **Выход запущенного процесса.** Был опросом `try_wait` в такте. Стал
  событием: на каждый запуск заводится поток, который делает `child.wait()`
  и присылает демону `ChildExited`. Заодно поток забирает код возврата,
  и процесса-зомби не остаётся.
- **Предельный срок ожидания окна** (30 с у приложения, 30 с у постороннего
  окна снимка, 2 с после выхода процесса) снят целиком. Ожидание живёт
  до окна. Если процесс вышел, а подходящее свободное окно уже есть
  (одноэкземплярное приложение вроде Telegram открыло его в прежнем процессе),
  окно принимается сразу; если окна нет, запись переходит в состояние «процесс
  вышел, окно ожидается» и ждёт первого подходящего `openwindow`. Клавиша
  при этом не остаётся без ответа: повторное нажатие, пока процесс жив,
  игнорируется (запуск идёт), а после выхода процесса — принимает подходящее
  свободное окно либо снимает прежнее ожидание и запускает приложение заново.
  Переходы вынесены в `pending_step` и проверены тестом.
- **Исполняемый файл** запущенного процесса (`/proc/<pid>/exe` после того, как
  обёртка-скрипт выполнила настоящий бинарник) уточняется при появлении окна,
  а не опросом.

Ожидание постороннего окна из снимка сессии выхода процесса не переживает:
восстановить окно уже нечем, запись снимается со строкой в журнале. Цена —
редкий случай, когда процесс передаёт запрос уже работающему экземпляру
и выходит раньше, чем появится окно: тогда окно останется свободным
на своём месте вместо места из снимка.

После этого в коде демона не осталось ни `Instant`, ни `Duration`,
ни `thread::sleep` — таймеров нет совсем. Сроки, упомянутые
в спецификациях (50 мс до панели, 5 с на перезапуск юнита), — это пределы
наблюдаемого поведения, а не таймеры демона.

**D13. Перечитывание конфига идёт по событиям завершённой записи, без
задержки.** Раньше наблюдатель ждал 200 мс после первого события и подавлял
события чаще 300 мс — задержка вместо разбора того, что именно произошло.
Теперь наблюдатель учитывает только два вида событий: закрытие файла,
открытого на запись (`IN_CLOSE_WRITE`, в крате `notify` —
`Access(Close(Write))`), и появление файла под своим именем после записи
во временный файл с переименованием (`Modify(Name(To))` и `Modify(Name(Both))`).
Первое покрывает правку на месте (`nvim`, `tee`), второе — `chezmoi apply`
и редакторы, заменяющие файл целиком. `Modify(Data)` не учитывается: оно
приходит посреди записи, и конфиг читался бы неполным. `Create` тоже
не учитывается: за созданием файла всегда следует закрытие, и учёт обоих дал бы
два перечитывания на одно сохранение. Наблюдается каталог, а не файл: при
замене файла меняется inode, и наблюдение за самим файлом терялось бы.

Если после такого события конфиг не разбирается (редактор пишет в два приёма,
и первое закрытие даёт неполный файл), демон пишет в журнал «конфиг
не перечитан, действует прежний» и перечитает по следующему событию — это
принятая цена.

Своих перечитываний команды не делают: `save-workspace` записывает файл
во временный и переименовывает его, а это то же событие завершённой записи,
которое ловит наблюдатель. Явный вызов после записи давал второе перечитывание
и второй `hyprctl reload config-only` на одно сохранение.

**D14. Риск потери последних 500 мс снят.** В `design.md` изменения
`workspace-daemon` был принят риск: при остановке демона терялись изменения,
не успевшие попасть в отложенную запись снимка. С записью в обработчике
события отложенного состояния не существует, и обработчик SIGTERM ради этого
больше не нужен.

**D15. Окно приложения, исчезнувшего из конфига, освобождается сразу.**
Раньше такое окно оставалось с тегом: демон не считал его ни окном приложения
(приложения нет), ни посторонним (тег есть). Проверка вживую 22.09.2026
показала, чем это кончается: окно Alacritty приняли в сессию, записали
в конфиг, затем конфиг откатили через `chezmoi apply` — окно осталось с тегом
`app:alacritty#1`, `status` показывал `foreign: false`, сохранение сессии
его не отбирало, и в снимок сессии как постороннее оно не попадало. Теперь
после каждой пересборки эффективного конфига демон снимает с таких окон теги
`app:` и заводит их посторонними с командной строкой и каталогом процесса,
записывая строку в журнал. Пересборка идёт при перечитывании конфига,
при сверке окон на старте демона и при загрузке сессии, поэтому отдельного
места для проверки не нужно. Окна дополнительных приложений сессии под правило
не попадают: эти приложения входят в эффективный конфиг (D1).

Захвату по классу это не мешает: освобождённое окно остаётся без тега,
и приложение с подходящим `class` заберёт его при следующем поднятии workspace
или вызове по клавише — как любое окно без тега.

Этой же сверкой снимаются записи ожидания окна: проверка вживую показала
и такой случай. Временное приложение `failtest` с `cmd = "false"` вызвали
дважды, процесс оба раза сразу вышел, конфиг откатили — и запись
`{"app":"failtest","pid":…}` осталась в `pending` команды `status` с мёртвым
pid до перезапуска демона. Ждать окно приложения, которого нет, незачем.
Запущенный процесс при этом не убивается: демон его не контролирует, а окно,
если оно всё-таки появится, придёт посторонним, как любое окно без тега.

**D16. Окно из песочницы flatpak записывается командой `flatpak run`.**
Командная строка процесса в песочнице ведёт внутрь неё: `save-session` записал
для Postman путь `/app/extra/Postman/postman` с аргументами окна и каталогом
`/home/mne`, а на хосте такого пути нет, и восстановить окно по снимку было бы
нечем. Поэтому для процесса в песочнице демон записывает
`flatpak run <идентификатор приложения>` и исходные аргументы процесса,
а каталог не записывает: рабочий каталог песочницы на хосте тоже ничего
не значит. Идентификатор берётся из `/proc/<pid>/cgroup`: процесс
песочницы лежит в юните `app-flatpak-<идентификатор>-<номер>.scope`, хвост
с номером добавляет systemd, а экранирование `\xNN` в имени юнита
раскодируется. Юнита такого вида нет — процесс работает не в песочнице,
и командная строка записывается как есть.

Правило одно на все места записи: снимок сессии, дополнительное приложение
сессии и запись приложения в конфиг берут командную строку и каталог одной
и той же функцией.

Цена: снимок, записанный прежней версией демона, хранит путь из песочницы,
с живым окном он не совпадёт, и окно останется свободным на своём месте.
Переписывается такой снимок сам собой — первой же записью после того, как
состояние изменится.

## Risks / Trade-offs

- **Эффективный конфиг не равен файлу.** `workspaced status --json` и поведение
  демона показывают приложения, которых в файле нет. Смягчение: демон пишет
  в журнал строку при каждом добавлении и снятии дополнительного приложения,
  а `save-workspace` переводит их в файл.
- **Два приложения с одним классом** (D5) после перезагрузки сливаются в одно.
  Принято.
- **Окна из контейнера не восстанавливаются** (D11). Принято, как и сегодня.
- **Сброс ячеек при перечитывании** (D8) отменяет обмен ячеек, сделанный
  клавишей, у того workspace, чей раздел правился. Это и есть желаемое:
  расстановка возвращается к описанной в файле.
- **Снимок сессии пишется чаще** (D12): раньше отложенная запись склеивала
  события, идущие подряд, теперь на каждое приходится запись файла. Файл
  небольшой, запись атомарная (временный файл и переименование), а событий
  окон в сессии немного — поток событий композитора не такой частый, чтобы
  это было заметно.
- **Поток на каждый запуск приложения** (D12) живёт, пока жив процесс. Потоков
  столько же, сколько запущенных демоном приложений, — единицы.

## Migration Plan

Снимки сессий прежнего формата читаются как есть: раздела `extra_apps` в них
нет, поле необязательное. Обратной несовместимости нет — снимок нового формата
прежний демон прочитал бы, потеряв дополнительные приложения.

В `config.toml` строка `save_workspace = "SUPER+TAB SUPER+s"` заменяется двумя
строками; `keys.lua` демон перегенерирует сам при перечитывании конфига.
