# Design: Окна без класса свободны, сбой запуска не обрывает поднятие

## Context

Мотивация и ход происшествия — в `proposal.md`. Что было в демоне
до изменения:

- `join_window` проверял `ignore_classes`, затем искал приложение по `class`
  и `title` (`app_for_window`). Пустой класс ни одному выражению приложений
  конфига не подходил, поэтому окно диспетчера задач уходило в последнее
  правило — новое дополнительное приложение с именем по классу. Из пустого
  класса `app_name` строил имя `app`.
- Запись дополнительного приложения хранит класс как есть, а эффективный
  конфиг превращает его в выражение `regex::escape(class)`. Для пустого
  класса это выражение `^(?:)$`, и оно подходит любому окну без класса.
  Поэтому окно диспетчера задач Яндекс.Браузера в `surf` нашло приложение
  `app` из `work`, а ветвь «приложение известно только сессии другого
  workspace» завела в `surf` запись под тем же именем — с командной строкой
  другой программы.
- `merge_extra` обходит workspace по именам и кладёт описание приложения
  в `cfg.apps` из каждой записи; побеждает последняя (`work`), отсюда
  команда Chromium при поднятии `surf`.
- `Daemon::raise_on` вызывал `self.spawn(…)?`: ошибка запуска одного
  приложения прерывала поднятие до переноса окон и до `assign_desktop`.
- `Daemon::detach` снимал запись только в активном workspace и только
  когда других окон приложения нет. Окно диспетчера Chromium с тегом
  `app:app#1` оставалось открытым в `work`, поэтому отделение окна в `surf`
  запись не сняло — и не должно было: окна двух разных программ числились
  одним приложением.

Причина ENOENT проверена по живой системе. Бинарник `/usr/lib/chromium/chromium`
существует, каталог процесса `/home/mne` тоже. Но `/proc/<pid>/cmdline`
основного процесса Chromium — одна строка
`/usr/lib/chromium/chromium --ozone-platform=wayland` без нулевых байтов
между аргументами: Chromium, как и Яндекс.Браузер
(`/opt/yandex/browser/yandex_browser --ozone-platform=…`), переписывает
свою командную строку (setproctitle). `proc_info` делил её по нулевым
байтам и получал один элемент, который `Command::new` принимал за имя
программы целиком. Каталог и окружение к ошибке отношения не имели:
`spawn` при отсутствии каталога запускал процесс без `current_dir`.

## Goals / Non-Goals

**Goals:**

- Окно без класса не входит ни в один workspace ни при каких условиях.
- Поднятие workspace доводится до конца, даже если одно приложение
  не запустилось; причина видна в журнале целиком.
- Команда, которую демон записывает для окна, запускается.
- Одно имя дополнительного приложения — одна программа; отделение
  последнего окна не оставляет запись в другом workspace.

**Non-Goals:**

- Опознание диалогов по родителю окна: Hyprland 0.56.2 его не сообщает
  (открытый вопрос `docs/open-questions/hyprland-window-parent.md`).
- Восстановление окон, которые без родительского процесса не открываются
  (`steamwebhelper` запускается только из Steam): команда теперь
  запускаемая, но окно такой процесс не открывает, и демон, как и раньше,
  пишет «процесс завершился, окна нет».

## Decisions

**D1. Окно без класса свободно всегда — проверкой `classless` в самом
начале.** Функция `classless(c)` (класс пуст или из пробелов) проверяется:
первой в `join_window` (новая причина `Free::NoClass`, «у окна нет
класса»), в `matcher_fits` — поэтому ни `app_for_window`, ни захват
открытых окон `adopt_plan`, ни ожидание запуска по выражениям такое окно
не берут, даже если выражение подходит пустой строке; в `Pending::matches`
и в `Daemon::on_open` — ожидание запуска не принимает окно без класса
и по родству процессов (диспетчер задач — окно того же процесса Chromium,
и если бы Chromium ждал своё первое окно, диспетчер мог бы занять его
место); в `save_workspace` — команда записи workspace в конфиг окно без
класса пропускает. Правило одно на все пути, потому что сохранение сессии
(`session_plan`) решает через тот же `join_window`. Рассматривался вариант
добавить `""` в `ignore_classes` конфига: он не закрывает захват
и ожидание запуска и зависит от конфига пользователя, поэтому отвергнут.
Окно без класса, совпавшее с посторонним окном снимка, по-прежнему ставится
на своё место из снимка: это свободное окно, в workspace оно не входит.

**D2. Сбой запуска — предупреждение, а не ошибка поднятия.** Запуск
вынесен в функцию `start(cmd, args, cwd, env)`: она выбирает каталог
(`launch_dir`: заданный, если есть, иначе домашний с предупреждением),
запускает процесс в собственной сессии и при ошибке возвращает текст
с командой, аргументами, каталогом и ошибкой ОС. Ею пользуются
`Daemon::spawn` и `Daemon::spawn_foreign`. `Daemon::raise_on` ловит ошибку
`spawn`, пишет предупреждение «workspace …: …; поднятие продолжается без
этого приложения» и идёт дальше; этим закрыты и `move-desktop` (он
поднимает workspace и преемника через `raise_on`), и ленивое поднятие.
`session::load` так же продолжает работу после сбоя `spawn_for_session`
и после ошибки поднятия одного из workspace. Клавиша приложения (цепочка)
по-прежнему возвращает ошибку клиенту: там запуск — единственное действие
команды. Прежний запуск без `current_dir` при отсутствии каталога наследовал
каталог демона, то есть зависел от того, как запущен сам демон; домашний
каталог от этого не зависит.

**D3. Одно имя — одна программа; отделение снимает запись с командой
везде.** В ветви `join_window` «приложение известно только сессии другого
workspace» окно получает имя прежней записи, только если его командная
строка начинается с того же исполняемого файла (`same_program`); иначе
заводится новое имя по классу (`app_name`). Поэтому `join_window` получает
командную строку вместо признака `has_cmd`. Запись одной программы в двух
workspace допустима и остаётся: это одно приложение, у которого есть место
в каждом из них (так было задумано и раньше: запись о месте без команды
в другом workspace не выжила бы, поэтому там заводится полная запись). `drop_extra_app` снимает запись с командой во всех workspace
вместе с назначениями мест — с последним окном программа уходит
из сессии; запись без команды (только место приложения конфига) снимается
лишь в активном workspace стола, потому что приложение конфига живёт дальше
и его места в других workspace остаются в силе. Тест
`extra_app_names_do_not_repeat` проверял только построение имени
и остался как есть; новый тест `same_class_of_another_program_gets_its_own_name`
проверяет выбор имени.

**D4. Запускаемая команда — в `proc_info`, одно правило для всех мест.**
Функция `launchable(cmd, cwd, exe)`:

1. одна строка с пробелами, если файла с таким именем нет, делится
   по пробелам (Chromium, Яндекс.Браузер);
2. абсолютный путь остаётся, если файл есть;
3. относительный путь (`./steamwebhelper`) превращается в абсолютный
   от рабочего каталога процесса без раскрытия символических ссылок —
   иначе программа, которая смотрит на своё имя, получила бы другое;
4. имя без каталога остаётся, если находится в `PATH`;
5. не найденный файл заменяется путём из `/proc/<pid>/exe`;
6. иначе команды нет: `proc_info` возвращает пустую команду и пишет
   предупреждение.

Правило стоит в `proc_info`, а не в записи снимка, потому что `proc_info` —
единственный источник командной строки окна: из него берутся посторонние
окна (`st.foreign`), дополнительные приложения, снимок и сверка при загрузке.
Пустая команда уже означает «окно свободно, в снимок не попадает»
(`Free::NoCommand`, пропуск в `session::snapshot`). Снимок прежней версии
с сырыми командами читается: `spawn_missing_foreign` приводит команду тем же
правилом без шага 5 (процесса уже нет) и сверяет с открытыми окнами
в приведённом виде, а `same_window` при сверке сравнивает команду снимка
в исходном и приведённом виде. Проверено при перезапуске демона: запись
снимка `./steamwebhelper` запущена как
`/home/mne/.local/share/Steam/ubuntu12_64/steamwebhelper`.

**D5. Спецификация «Файлы сессий» тоже меняется.** Требование говорило
«MUST записываться командная строка процесса как есть» — после D4 это
неверно. Правило приведения записано в «Файлы сессий», где уже описаны
команды flatpak, а «Дополнительные приложения сессии» ссылается на него
и добавляет единственность имени.

## Risks / Trade-offs

- Приложение, которое открывает первое окно с пустым классом и задаёт
  класс позже, демоном больше не принимается: запуск будет ждать окна
  до следующего нажатия клавиши. Среди приложений конфига таких нет;
  если появятся, окно придётся описывать иначе.
- Деление строки Chromium по пробелам ломает аргументы с пробелами внутри.
  Точнее восстановить их нельзя: разделители процесс сам затёр.
- Путь из `/proc/<pid>/exe` у программы, запущенной через интерпретатор,
  указывает на интерпретатор; он берётся только тогда, когда записанный
  файл не найден, и лучше пустой команды.
