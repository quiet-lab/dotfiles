# Design: Семейства и варианты приложений, несколько окон у приложения

## Context

Мотивация — в `proposal.md`, целиком замысел и место этого изменения в серии —
в `docs/window-model.md` (шаг 1). Что есть сейчас в демоне:

- Окно приложения помечается единственным тегом `app:<имя>`; поиск окна
  (`find_app_window`) возвращает одно окно, а захват открытых окон
  (`adopt_untagged`, `pick_candidate`) берёт одного кандидата на приложение и
  только тогда, когда окна с тегом ещё нет.
- Место окна берётся из таблицы `apps` workspace (`State::rect_for`); приложения
  вне workspace демон ставит в центр экрана (`Target::Center`).
- Обмен ячеек (`make_main`) переставляет два окна: окно приложения и окно
  главной ячейки.
- Поля приложения: `cmd` (обязательное), `args`, `cwd`, `env`, `chain`, `class`,
  `title`. Ни семейств, ни вариантов в формате нет; herdr отличается
  от остальных окон wezterm только заголовком `^herdr · `.
- Два профиля Chrome — одно приложение на профиль, класс окна у обоих
  `google-chrome`, различают их только теги демона.

Пробная задача о профилях Chrome выполнена 21.09.2026 (Hyprland 0.56.2,
Chromium 153, Chrome 153 из контейнера `fedora-box`), её итоги записаны
в `docs/window-model.md`. Коротко: окна двух профилей одного процесса совпадают
по `class`, `initialClass`, `initialTitle` и `pid`; протокол xdg-toplevel-tag
Chromium не поддерживает, поэтому `xdgTag` и `xdgDescription` пусты;
`/proc/<pid>/cmdline` содержит аргументы первого запуска; ключ `--class` под
ozone действует на процесс, а не на окно, и при запуске второго профиля в уже
работающий процесс не применяется; `--window-name` помечает окно, но навсегда
заменяет заголовок страницы и не наследуется окнами, открытыми по Ctrl+N;
наследование приложения от активного окна ненадёжно — окно другого профиля,
открытое из меню аккаунтов, совпадает и по pid, и по классу, и по прежнему
активному окну, а окна, восстановленные браузером при старте, приходят без
истории фокуса. Надёжен только отдельный каталог данных: он даёт всем окнам
варианта собственный `app_id`, включая окна по Ctrl+N и восстановленные.

## Goals / Non-Goals

**Goals:**

- Приложение в демоне — набор экземпляров; порядок экземпляров устойчив
  и переживает перезапуск демона.
- Вариант отличается от семейства признаками окна, а не тем, кто его запустил.
- Формат конфига растёт только добавлением полей: прежний файл остаётся
  правильным, а прежние теги окон — читаемыми.

**Non-Goals:**

- Поведение клавиши не меняется: цикл по экземплярам и второй режим workspace —
  следующее изменение серии.
- Демон не заводит новых экземпляров по своей воле: второе окно открывает
  пользователь средствами приложения.
- Состав workspace по-прежнему определяется конфигом: окно, появившееся
  по ходу работы, остаётся посторонним до захвата при поднятии или цепочке.

## Decisions

**D1. Вариант — плоская запись `[apps.<имя>]` с полем `family`.** Имя приложения
уже служит ключом во всех местах, где приложение называется: таблица `apps`
workspace, `main`, `chain`, `action = { app = … }`, тег окна, снимок сессии.
Плоская запись оставляет их без изменений, и workspace ссылается на вариант
ровно так же, как раньше на приложение. Отвергнуто: вложенная таблица
(`[apps.wezterm.variants.herdr]`) — потребовала бы составного имени варианта
во всех перечисленных местах; вывод семейства из имени (`chrome-ai` → `chrome`) —
имя перестаёт быть свободным, а `yandex-browser` случайно становится вариантом
`yandex`. Уровней ровно два: `family` MUST называть приложение без своего
`family`. Цепочки вариантов усложнили бы правило «более точное совпадение
побеждает», а необходимости в них не видно.

**D2. Поля варианта не наследуются от семейства.** Вариант сам называет свои
`cmd`, `class` и `title`. Запись читается как есть, и `class` варианта не нужно
мысленно складывать с `class` семейства. Обратная сторона — повтор выражения
класса у варианта, который отличается только заголовком (`chromium` и его
вариант с `title`); повтор одной строки дешевле неявного правила.

**D3. `cmd` становится необязательным, но `cmd` или `class` обязателен.**
Запись-семейство часто нужна только для того, чтобы собрать окна под общей
клавишей и в общей ячейке, а открывать «пустое» окно семейства незачем.
Приложение без `cmd` и без `class` ни запустить, ни узнать нельзя, поэтому такой
конфиг отклоняется. Приложение без `cmd`, у которого окон нет, при поднятии
workspace оставляет ячейку пустой и пишет строку в журнал: оставлять такой
случай без сообщения нельзя.

**D4. Тег экземпляра — `app:<имя>#<номер>`.** Номер даёт устойчивое имя
экземпляру, которое живёт в композиторе, а не в памяти демона: после перезапуска
демона порядок экземпляров восстанавливается из тегов. Номер — наименьший
свободный среди живых окон приложения, начиная с 1: так номера не растут
без предела за сеанс работы. Тег `app:<имя>` без номера, оставшийся от прежней
версии демона или от прежней сессии, читается как экземпляр. Отвергнуто: второй
тег вида `inst:<имя>#<n>` рядом с `app:<имя>` — два тега об одном и том же
приходится держать согласованными; порядок окон из `hyprctl clients -j` —
композитор его не обещает; адрес окна в памяти демона — не переживает
перезапуск. Разделителем выбран `#`, потому что в именах приложений он
не встречается и проверка конфига его запрещает вместе с двоеточием. Проверка
на живом окне 22.09.2026 (Hyprland 0.56.2) показала, что композитор тег
`app:probe#1` принимает и снимает, поэтому разделителем остаётся `#`.
Тег прежней версии без номера занимает номер 1: следующее окно того же
приложения получает 2, и ни одно окно не теряет своего номера при захвате
остальных.

**D5. Порядок экземпляров — по возрастанию номера; «первый экземпляр» — окно
с наименьшим номером.** Это вырожденный случай будущего цикла: шаг 2 начинает
цикл с первого экземпляра, поэтому фокус, который шаг 1 отдаёт первому
экземпляру, совпадёт с первым нажатием клавиши после введения цикла.
Отвергнуто: порядок по последнему фокусу (`focusHistoryID` композитора) — сам
по себе он удобнее, но при введении цикла поведение клавиши пришлось бы менять
второй раз, а документ прямо говорит, что цикл идёт по порядку и вмешательство
мыши учёта не меняет. Номера у семейства и у его вариантов свои, поэтому в наборе
семейства номера повторяются; такие окна идут по имени приложения (вариант
раньше семейства). Фокус получает первый экземпляр, который не скрыт
пользователем на `special:hidden`. При захвате окна на обычных столах
разбираются раньше окон на `special:pool`, поэтому первым экземпляром
становится окно на столе, а не припаркованное.

**D6. Клавиша приложения с двумя окнами: стопки меняются ячейками целиком, фокус
первому экземпляру, второй экземпляр не запускается.** Документ описывает
поведение клавиши для шага 2, а шаг 1 поведения клавиш не меняет; из двух
прочтений «прежнего поведения» для приложения с двумя окнами выбрано то, которое
шаг 2 продолжит без переделки: обмен ячеек работает над стопкой как над одним
окном, а цикл внутри стопки добавит шаг 2. До шага 2 ко второму экземпляру переходят
мышью или Alt+Tab. **Решение принято без пользователя и ждёт его подтверждения.**

**D7. Место окна — правило из четырёх шагов.** Ячейка или `rect` приложения
в workspace; то же, записанное для его семейства; `rect` самого приложения;
центр экрана. Правило собрано в одном требовании («Расстановка окон»), чтобы
шаги 3 и 5 вставляли в него свои случаи (положение по умолчанию у workspace,
переопределения) одной строкой, а не переписывали расстановку заново.
Если workspace описывает и семейство, и его вариант, окно варианта расставляет
запись варианта, а запись семейства его не трогает: иначе место окна зависело бы
от того, какое из двух имён идёт раньше по алфавиту. **Решение принято без
пользователя и ждёт его подтверждения.**

**D8. Глубину стопки демон не переупорядочивает.** Окна стопки получают одно
место, и порядок по глубине остаётся тот, что сложился в композиторе; наверх
поднимается только окно, которому передаётся фокус (это уже делает
`bring_to_top`). Раскладывать стопку в порядке номеров при каждой расстановке
значило бы без нужды переставлять окна, а видимого выигрыша до шага 2 нет.
**Решение принято без пользователя и ждёт его подтверждения.**

**D9. Захват берёт все подходящие окна и работает даже у приложения с окнами.**
Иначе второе окно браузера никогда не попадёт в стопку: появившееся окно
до шага 3 остаётся посторонним, и единственный повод его принять — захват
при поднятии workspace или по цепочке. Сопоставление окна идёт сначала
по вариантам, затем по семействам — так выполняется правило «более точное
совпадение побеждает». Пересекающиеся выражения двух вариантов одного семейства
статически не проверить (пересечение регулярных выражений), поэтому окно
достаётся первому варианту в порядке имён с предупреждением в журнале; сам
по себе такой конфиг — ошибка пользователя, а не случай, который демон обязан
разрешать осмысленно. **Порядок «первый по имени» выбран без пользователя
и ждёт его подтверждения.**

**D10. Профиль Chrome `AI.dev2026` переезжает в каталог данных
`~/.config/google-chrome-ai` и получает класс окна `google-chrome-ai`.**
Решение пользователя от 21.09.2026 по итогам пробной задачи; других надёжных
способов различать окна профилей нет (см. Context). Каталог выбран рядом
с основным каталогом браузера (`~/.config/google-chrome`): он на виду там же,
одинаково доступен из хоста и из контейнера `fedora-box` (там `$HOME` общий) и,
как основной каталог, не попадает под chezmoi. Класс `google-chrome-ai` образован от класса по умолчанию
и не совпадает ни с одним выражением действующего конфига: `(?i)^google-chrome$`
у `chrome` сопоставляется целиком, поэтому окна нового варианта ему
не достанутся. Внутри нового каталога профиль называется `Default` — так Chrome
находит его сам; ключ `--profile-directory=Default` в команде запуска всё же
указывается явно, чтобы случайно созданный второй профиль не изменил поведение. Цена решения, о которой пользователь предупреждён: второй
процесс браузера (PSS от 300 МиБ); в каждом экземпляре пропадает переключатель
профилей и пункт «открыть в другом профиле»; внешние ссылки открываются
в экземпляре по умолчанию; каталог профиля копируется целиком (338 МиБ);
правило непрозрачности браузеров в `hyprland.lua` и ярлык, экспортированный
distrobox, надо расширить. Прежний профиль (подкаталог `Profile 1`
в `~/.config/google-chrome`) удаляется только после того, как пользователь
проверит вход в аккаунты и расширения в новом экземпляре.

**D11. Семейство Chrome в этом изменении не заводится.** До переезда профиля
`chrome` и `chrome-ai` — два приложения с одним классом `google-chrome`,
и вариантами одного семейства по `class` они быть не могут: демон не отличил бы
их окна, а правило «более точное совпадение побеждает» опирается только
на признаки окна. После переезда каждое из них опознаётся своим классом, и любое
из них можно объявить вариантом семейства Chrome — но польза от такой записи
появляется вместе с общей клавишей и общей ячейкой для всех окон Chrome,
то есть на шаге 5. Поэтому после переезда `chrome` и `chrome-ai` остаются двумя
независимыми приложениями, каждое со своей стопкой окон; прежняя оговорка «окна
двух профилей неотличимы, их различают только теги демона» перестаёт
действовать. **Решение отложить семейство Chrome принято без пользователя и ждёт его
подтверждения.**

**D12. Клавиши остаются на тех же приложениях, что сейчас.** Super+T — `herdr`,
Super+C — `chromium`, Super+E — `neovide`, Super+B — `chrome`, Super+V —
`chrome-ai`. Семейство `wezterm`, которое вводит это изменение, клавиши
не получает и ни в один workspace не входит: иначе Super+T начал бы действовать
на все окна wezterm, включая терминал, в котором работает агент, и шаг 1
изменил бы то, что клавиша делает. Клавиша семейства осмысленна вместе
с переопределениями шага 5. **Решение принято без пользователя и ждёт его
подтверждения.**

**D13. herdr опознаётся классом `wezterm-herdr`, а не заголовком.** `wezterm
start --class <имя>` меняет `app_id` под Wayland для всех окон этого экземпляра
(проверено по справке `wezterm start`), а заголовок окна задаёт программа внутри
терминала и он может измениться. Заодно семейство `wezterm` с классом
по умолчанию `org.wezfurlong.wezterm` перестаёт пересекаться с вариантом:
терминал агента больше не подходит выражению `herdr` ни по классу, ни
по заголовку.

**D14. Сессии и панель этим изменением не меняются.** Формат снимка уже хранит
список окон, поэтому несколько окон одного приложения записываются без правки
формата; при загрузке приложение не запускается, если хотя бы одно его окно
живо, а если живых окон нет, оно запускается один раз, сколько бы его окон
ни было в снимке, так что после перезагрузки системы возвращается один
экземпляр. Это
принятое ограничение до шага 7, оговорённое в `docs/window-model.md`. Панель
строит состав окон workspace из данных демона по экземплярам его приложений:
значков становится больше, предел в 10 значков остаётся, а окно варианта
не исчезает из плитки, потому что считается окном своего семейства.

**D15. Команда сохранения записывает место первого экземпляра.** Запись
описывает место приложения, а стопка стоит в одном месте, поэтому второй
экземпляр в файле ничего бы не добавил; отдельные записи для окон появятся
на шагах 3 и 4 вместе с принятием окон и общими окнами. **Решение принято
без пользователя и ждёт его подтверждения.**

## Risks / Trade-offs

- [Захват всех подходящих окон втягивает в workspace окна, которые раньше
  оставались свободными: второе окно Chromium с другого стола при первом же
  поднятии `work` переезжает в ячейку `left`] → это и есть цель модели; до шага 4
  ненужное окно убирается вручную (Super+Z на `special:hidden` — такие окна
  захват не берёт), а снятие окна с workspace по Super+Backspace даёт шаг 4.
- [Семейство с широким выражением класса может забрать окно, которое
  пользователю нужно свободным (терминал агента)] → семейство `wezterm`
  в workspace не входит и клавиши не имеет (D12), поэтому захват для него
  не запускается; вариант `herdr` его окно не берёт, так как класс другой.
- [Композитор может не принять тег с `#`] → задача 1.2 проверяет это на живом
  окне; при отказе разделителем становится `-`, требования не меняются
  (спецификация называет вид тега, а не знак).
- [Несколько окон одного приложения в снимке, а восстанавливается одно] →
  принятое ограничение до шага 7; после перезагрузки системы пользователь
  открывает второе окно сам.
- [Переезд профиля Chrome: копия каталога 338 МиБ, второй процесс, внешние
  ссылки идут в экземпляр по умолчанию] → цена решения, принятая
  пользователем (D10); откат — вернуть команду `chrome-ai` с
  `--profile-directory="Profile 1"` и прежним классом, новый каталог удалить.
  Прежний профиль удаляется только после проверки пользователем.
- [Приложение с `class`, но без `cmd`, при пустом наборе окон оставляет ячейку
  пустой] → строка в журнале при каждом поднятии; для приложения, которое должно
  открываться, `cmd` остаётся обязательным по смыслу, и проверка конфига
  требует хотя бы одно из двух полей.

## Migration Plan

1. Собрать демон (`cargo test`, `cargo build --release`), применить конфиг
   (`chezmoi apply`), перезапустить `workspaced.service`, выполнить
   `hyprctl reload config-only`. Порядок именно такой: новый демон со старым
   конфигом отверг бы файл (см. `docs/agent-session-tips.md`).
2. Поднять `work` и `surf`: открытые окна получают теги с номерами экземпляров,
   стопки встают в свои ячейки.
3. Переезд профиля Chrome `AI.dev2026` — отдельная группа задач: она идёт
   до задач, которые опираются на класс варианта, и заканчивается проверкой
   пользователя.
4. Откат: вернуть прежний конфиг и прежнюю сборку демона из git. Теги с номером
   прежний демон читать не умеет, поэтому после откатной установки окна
   с такими тегами считаются посторонними и захватываются заново по `class` —
   окна не теряются, но их приходится расставить одним поднятием workspace.

## Open Questions

- Нужна ли общая клавиша и общая ячейка для всех окон Chrome (семейство над
  `chrome` и `chrome-ai`) — вопрос решается вместе с переопределениями
  на уровне workspace (шаг 5) и на спецификации этого изменения не влияет.
