# Design: Переопределения на уровне workspace

## Context

Мотивация — в `proposal.md`, замысел целиком и место шага в серии —
в [`docs/window-model.md`](../../../docs/window-model.md): раздел 2.1 (уровни
конфигурации: приложение, workspace, положение по умолчанию у workspace),
раздел 2.2 (семейства и варианты), раздел 2.3 (цикл по клавише и два режима),
раздел 2.5 (таблица клавиши приложения, случаи «а»—«в»), раздел 5, шаг 5.
Решения прежних шагов действуют и здесь:
[`app-families`](../archive/2026-09-22-app-families/design.md) — правило места
окна (D7), семейство Chrome не заводится (D11), клавиши остаются на тех же
приложениях (D12); [`key-cycle-stack`](../archive/2026-09-22-key-cycle-stack/design.md)
— цикл по экземплярам, prev в двух режимах, память прямоугольников режима
`stack` по workspace (D9); [`shared-windows`](../shared-windows/design.md) —
состав workspace тегами (D1), клавиша приложения по случаям таблицы (D7),
перетаскивание как операция `app --pull` без клавиши в конфиге (D8), выбор
открытого или перетащенного приложения без обмена ячеек (D15).

Что есть сейчас в демоне (коммит `2bbe38c`, шаг 4 выполнен, не заархивирован):

- Запись приложения в таблице `apps` workspace — перечисление `Placement`
  (`config.rs`): имя ячейки строкой или `{ rect = … }`. Других полей у записи
  нет; порядок записей хранится (`IndexMap`).
- Поле `mode` есть только у workspace (`Workspace::mode`). Цикл (`Daemon::cycle`,
  `select_window`, запуск в `CycleStep::Launch`, `anchor_window`) берёт режим
  у workspace.
- Клавиша есть только у приложения (`App::chain`). `keys::collect` группирует
  приложения с одной цепочкой в привязку `workspaced app a b c` и отклоняет
  две такие записи внутри одного workspace; демон выбирает кандидата
  по активному workspace (`app_route`).
- `app_route` считает приложение описанным в workspace по точному имени
  записи (`w.apps.contains_key`), тогда как состав, сверка и принятие окон
  считают описанным и приложение, чьё семейство записано в workspace
  (`ws_has_app`, инвариант D1 шага 4).
- Случай «в» наступает только по признаку `--pull`: `app_route` поднимает
  запущенный workspace с приложением всегда, когда тот есть.
- `save_workspace` (`save.rs`) собирает таблицу `apps` раздела заново из
  назначений ячеек (`State::cells_of`, `BTreeMap`) и заменяет ею прежнюю:
  записи идут по алфавиту, а не в порядке файла, комментарии внутри таблицы
  теряются.

## Goals / Non-Goals

**Goals:**

- Workspace задаёт приложению клавишу и режим клавиши рядом с местом, в той же
  записи.
- Одна цепочка может означать разные приложения в разных workspace, и выбор
  делается при нажатии по активному workspace, без таймеров и без
  перегенерации привязок.
- Таблица клавиши приложения (`docs/window-model.md`, раздел 2.5) выполняется
  целиком, включая случай «в» от собственной клавиши.
- Приложение без ячейки в workspace режима обмена ячеек не меняется местами
  с главным.
- Команда записи workspace в конфиг не теряет переопределений.

**Non-Goals:**

- Положение по умолчанию у workspace (уровень 3 раздела 2.1).
- Память о геометрии по режиму приложения.
- Переопределения в снимке сессии (шаг 7) и показ общих окон в плитках (шаг 6).

## Decisions

**D1. Переопределение — поля записи приложения в таблице `apps`
workspace.** Запись может быть строкой (имя ячейки), таблицей `{ rect = … }`
или таблицей с полями `cell` либо `rect` (ровно одно из двух), `chain`
и `mode`:

```toml
[workspaces.surf.apps]
chrome = { cell = "left", chain = "SUPER+B" }
yandex-browser = { cell = "center", chain = "SUPER+Y" }
chrome-ai = { cell = "right", chain = "SUPER+V" }
```

Прежние формы остаются, и файлы, записанные до шага, читаются без правки.
Поле клавиши называется `chain`, как у приложения и у workspace: одно имя для
одного понятия во всём файле. Место в таблице обязательно: запись без `cell`
и `rect` отклоняется с указанием workspace и приложения.

Рассмотренные варианты:

- *Отдельная таблица `[workspaces.<имя>.overrides.<приложение>]`.* Отвергнут:
  сведения об одном приложении в одном workspace расходятся по двум местам,
  и запись в конфиг командой сохранения должна согласовывать обе таблицы.
- *Поле `key`.* Отвергнут: в файле уже три поля `chain` с тем же смыслом
  (у `[keys]`, у приложения, у workspace), четвёртое имя путало бы.
- *Запись без места* (`{ chain = "…" }`, место по правилу мест из
  `rect` приложения или центра экрана). Отвергнут на этом шаге: это
  и есть положение по умолчанию у workspace (уровень 3 раздела 2.1), имя
  и форма которого не выбирались; кроме того, обмен ячеек и запись в конфиг
  получили бы третий вид места. Если уровень 3 будет введён, запрет снимается
  без изменения остальных полей.

**D2. Ключ приложения в workspace: переопределение главнее собственной
клавиши.** Ключ приложения `X` в workspace `V` — `chain` записи `X` в `V`,
а если его нет — собственный `chain` приложения. Workspace `V` откликается
на цепочку `K`, если в нём есть запись приложения с ключом `K` в `V`.
Переопределение освобождает собственную клавишу приложения в `V`: другое
приложение `V` может занять её своим ключом. Если собственную клавишу `X`
в `V` не занял никто, она по-прежнему ведёт цикл `X` в `V` (D4, шаг 2):
пользователь, привыкший к собственной клавише, в `V` ничего не теряет.
Переопределение, совпадающее с собственной клавишей, ничего не меняет
и переопределением для таблицы клавиши не считается: случая «в» с ним
не бывает, потому что одна цепочка не может означать и «поднять `V`»,
и «перетащить из `V`».

Отвергнуто: *переопределение отнимает собственную клавишу в `V` совсем*
(клавиша `K` в `V` ничего не делает для `X`). Такая клавиша в `V` попадала
бы в общие правила и перетаскивала бы окна `X` из `V` в тот же `V` — пустое
действие; проще и понятнее вести цикл.

**D3. Одна привязка на цепочку; решение — в демоне при нажатии.** Все
приложения, отзывающиеся на цепочку `K` (собственной клавишей или
переопределением в каком-либо workspace), дают одну привязку, которая
вызывает `workspaced key '<K>'`. Демон разбирает цепочку, сравнивает её
с ключами приложений по своему эффективному конфигу и выбирает путь по
активному workspace текущего стола (D4). Привязки по-прежнему зависят только
от конфига, а не от состояния: `workspaced keys --lua` печатает одно и то же
при одном файле (требование «Генерация привязок для Hyprland» не меняется).
В `workspaced keys --list` у такой привязки действие `key <K>`, а в колонке
источника перечислены все отозвавшиеся записи через запятую
(для Super+V в конфиге сессии — `workspaces.surf.apps.chrome-ai`, для цепочки,
общей у приложений разных workspace, — `apps.firefox-front,apps.firefox-chat`). Таймеров и ожиданий
решение не требует: это чтение состояния в обработчике команды.

Цепочка передаётся в командной строке в кавычках оболочки: в ней бывают
пробелы (`SUPER+TAB v`). Демон приводит её к каноническому виду тем же
разбором, что и конфиг (`keys::parse_chain`), поэтому регистр клавиши
и порядок модификаторов не важны.

Рассмотренные варианты:

- *Прежняя привязка `workspaced app a b c` с перечнем приложений.* Отвергнут:
  у приложения с переопределением две клавиши, `K` и `K'`, и по одному имени
  демон не отличит «нажата собственная клавиша» (перетащить, случай «в») от
  «нажата клавиша workspace» (поднять `V`).
- *Привязки по активному workspace*: демон при каждом поднятии перегенерирует
  код и вызывает `hyprctl reload`. Отвергнут: привязки перестали бы зависеть
  только от конфига, перезагрузка конфига композитора на каждое поднятие
  тяжела и оставляет промежуток, когда ещё действует прежняя привязка, а
  активных workspace несколько — по одному на стол, и привязки пришлось бы
  менять и при смене стола.
- *Подкарта на каждый workspace.* Отвергнут по той же причине: переключать
  подкарты пришлось бы по событиям смены стола и поднятия.

**D4. Путь клавиши — пять шагов по порядку.** Нажата цепочка `K`, на
текущем столе активен `W` (или активного нет), `Own(K)` — приложения
с собственной клавишей `K`, по именам:

1. `W` откликается на `K` приложением `X` — цикл `X` в `W`.
2. Приложение из `Own(K)` описано в `W` — цикл его в `W` (D2).
3. Запущенный workspace `V` откликается на `K` — поднять `V` и начать цикл
   отозвавшегося приложения. Порядок поиска прежний: список текущего стола,
   затем столы по возрастанию номера. Это случай «б» таблицы и клавиша `K'`
   переопределения: «`K'` по-прежнему поднимает `V`».
4. Приложение `X` из `Own(K)` описано в запущенных workspace, и все они
   переопределили его клавишу (иначе сработал бы шаг 3) — случай «в»: при
   активном `W` окна `X` перетаскиваются в `W` по правилам перетаскивания
   шага 4 (решения D8 и D15 `shared-windows`); без активного `W` перетаскивать
   некуда, и поднимается первый такой `V`, как на шаге 3.
5. Иначе приложение — первое из `Own(K)`, а если собственной клавиши `K` нет
   ни у кого, первое приложение, которому `K` назначена переопределением:
   при активном `W` оно открывается в `W` (случай «а»), без него — цикл
   по его окнам вне workspace.

Если приложение описано в двух запущенных workspace и один из них клавишу
не переопределяет, побеждает случай «б» (шаг 3 раньше шага 4): поднять
workspace, где приложение отзывается на собственную клавишу, естественнее,
чем перетаскивать окно. Перетаскивание по-прежнему доступно явно
(`--pull`).

Пример из документа (раздел 2.5) на конфиге сессии (D10): `surf` запущен
на столе 2 и назначает `chrome-ai` клавишу Super+V, собственная клавиша
`chrome-ai` — Shift+Super+V. На столе 1 с активным `work` Super+V поднимает
`surf` (шаг 3), Shift+Super+V перетаскивает окно в `work` (шаг 4), и окно
становится общим; в `surf` обе клавиши ведут цикл `chrome-ai` (шаги 1 и 2).
После перетаскивания `work` описывает `chrome-ai` записью сессии без
переопределения, поэтому Shift+Super+V в `work` ведёт цикл там (шаг 1),
а Super+V по-прежнему поднимает `surf`: `work` на неё не откликается.

Рассмотренные варианты:

- *Случай «в» при любом запущенном `V` с переопределением, даже если другой
  запущенный workspace клавишу не переопределяет.* Отвергнут: одна и та же
  клавиша то поднимала бы, то перетаскивала в зависимости от того, какие
  workspace сейчас в списках столов.
- *Клавиша переопределения без запущенного `V` ничего не делает.* Отвергнут:
  пользователь нажимает клавишу приложения и ждёт приложение; открыть его
  в текущем workspace (случай «а») — то же, что делает собственная клавиша.

**D5. Команда `workspaced app <имя>` — собственная клавиша приложения.**
Она проходит те же шаги с `Own = {имя}`, где откликом workspace считается
запись приложения без переопределения; признак `--pull` по-прежнему
перетаскивает сразу после шага 2. Так действие `{ app = … }` в `[[binds]]`
и ручной вызов ведут себя так же, как собственная клавиша, и случай «в»
наступает и от них. Несколько имён (`workspaced app a b`) — кандидаты по
порядку, как раньше: такую привязку печатали прежние версии, и копия
`keys.lua`, оставшаяся от них, должна работать до первой перезагрузки
конфига композитора.

**D6. «Описано в workspace» — запись приложения или его семейства.** Шаги 1,
2 и 4 считают приложение описанным в `W`, если в `W` есть запись самого
приложения или его семейства, — так же, как состав и сверка шага 4
(`ws_has_app`). Отсюда правила для семейств (`docs/window-model.md`,
раздел 2.2):

- `W` описывает только семейство — клавиша семейства (его ключ в `W`) ведёт
  цикл по всем окнам семейства, включая окна вариантов: они стоят в его
  стопке. Собственная клавиша варианта в том же `W` ведёт цикл только по
  окнам варианта (шаг 2), а обмен ячеек, если он есть, переносит стопку
  семейства целиком, потому что окно варианта расставляет запись семейства.
- `W` описывает и семейство, и вариант — каждая запись отзывается на свой
  ключ, и цикл семейства не включает окон варианта (правило «более точное
  совпадение побеждает», решение D7 `app-families`).
- `W` описывает только варианты — клавиша семейства в `W` приложением `W`
  не считается и идёт по общим правилам (поднять workspace, описывающий
  семейство, или открыть семейство в `W`).

Так достигается цель шага из документа: «на одном workspace профили Chromium
отзываются на общую клавишу семейства, на другом — каждый на свою». Первое —
workspace, описывающий семейство (ключ записи семейства или собственный
`chain` семейства); второе — workspace, описывающий варианты, каждый со своим
ключом. Проверяется на временном конфиге (задача 3.6), в конфиге сессии
семейства Chrome нет (D10).

Отвергнуто: оставить точное совпадение имени, как в `app_route`. Тогда
собственная клавиша варианта в workspace, описывающем семейство, поднимала бы
другой workspace, хотя окна варианта стоят здесь, в стопке семейства.

**D7. Режим на уровне приложения — режим цикла его клавиши.** Режим
приложения `X` в `W` — `mode` записи `X` в `W`; без него — режим `W`, кроме
одного случая: в `W` режима `swap` приложение без ячейки (запись с `rect`,
в том числе запись сессии, а для варианта без своей записи — запись
семейства с `rect`) выбирается в режиме `stack`. Весь цикл идёт в режиме
вызванного приложения: выбор экземпляра, prev в начале цикла (в `swap` —
окно главной ячейки, в `stack` — активное окно workspace), конец цикла
(обратный обмен ячеек или подъём prev) и запуск без окон (в `swap` —
приложение сначала занимает главную ячейку). Другое приложение, которое
вызывающее приложение вытесняет из главной ячейки, своего режима не
проявляет: обмен делает тот, чья клавиша нажата.

Документ (раздел 2.1) называет переопределяемый режим «поведением окна
по клавише», поэтому память о геометрии остаётся за режимом workspace:
в `W` режима `swap` окно приложения с режимом `stack` при поднятии `W`
встаёт на место из конфига, а в `W` режима `stack` окно приложения с режимом
`swap` возвращается в запомненный прямоугольник, который после обмена ячеек
и есть прямоугольник новой ячейки. Режим `swap` у приложения в `W` режима
`stack` допустим.

Исключение для приложения без ячейки снимает противоречие, отмеченное
в рисках шага 4: обмен ячеек с приложением, у которого ячейки нет, уводил
главное приложение на место калькулятора, а сценарий «Приложение без
workspace» требует, чтобы окно калькулятора оставалось, где его поставил
пользователь. Явное `mode = "swap"` у записи с `rect` возвращает прежнее
поведение.

Рассмотренные варианты:

- *Режим приложения распространяется и на память о геометрии.* Отвергнут
  на этом шаге: поднятие, следование общего окна, перенос, расстановка
  и сохранение (`raise_target`, `leave_geom`, `follow_plan`, `arrange`,
  `update_extra_rects`) проверяют режим workspace, и перевести их все
  на режим приложения — работа, которой документ не требует. Условие
  пересмотра: пользователь заметит, что окно приложения `stack` в `work`
  после поднятия возвращается на место из конфига.
- *Приложение без ячейки по умолчанию в режиме workspace*, как сейчас.
  Отвергнут по причине выше.
- *Запретить `mode = "swap"` у приложения в workspace режима `stack`.*
  Отвергнут: с разделением «режим клавиши у приложения, память о геометрии
  у workspace» такой обмен определён, а лишний запрет — ещё одно правило для
  пользователя.

**D8. Проверки конфига.** К прежним проверкам добавляется:

- внутри одного workspace ключи записей приложений MUST различаться;
  ошибка называет workspace, оба приложения и цепочку. Проверка идёт по
  ключам (D2), поэтому переопределение, совпавшее с собственной клавишей
  другого приложения того же workspace, — ошибка, а переопределение,
  освободившее собственную клавишу, делает её доступной другим;
- цепочка переопределения участвует в проверках совпадения и начала цепочки
  вместе с остальными привязками: все приложения одной цепочки образуют
  одну привязку (D3), и она не может совпадать с цепочкой workspace,
  служебной цепочкой или записью `[[binds]]` и не может быть началом другой;
- сочетания из `reserved` в переопределении недопустимы, как везде;
- `mode` записи — `swap` или `stack`, иначе отказ с указанием workspace,
  приложения, значения и допустимых; `cell` и `rect` вместе либо ни одного —
  отказ с указанием workspace и приложения.

Одна цепочка у приложений разных workspace по-прежнему допустима. Записи
сессии переопределений не несут, поэтому проверка файла их не касается;
если при работе запись сессии даёт второе приложение с тем же ключом в `W`
(перетащено приложение, чья собственная клавиша занята в `W`
переопределением другого), отзывается запись, стоящая раньше в разделе, —
записи файла идут раньше записей сессии.

**D9. Запись workspace в конфиг правит записи на месте.** `save_workspace`
больше не собирает таблицу `apps` заново, а обходит существующую: у записи
приложения меняется только место (строка ячейки, `cell` или `rect`), поля
`chain` и `mode` и комментарии остаются; строковая запись остаётся строкой,
пока у неё нет других полей; записи, которых в файле не было (дополнительные
приложения сессии, свободные окна стола), добавляются в конец в порядке
раздела эффективного конфига. Так же исправляется расхождение с требованием
«Файл конфига и его разделы»: порядок записей MUST сохраняться, а нынешняя
запись идёт по алфавиту из `BTreeMap` назначений ячеек, и сохранение `surf`
переставило бы `chrome-ai` перед `yandex-browser`, изменив конец цикла.

Отвергнуто: собирать таблицу заново, переписывая в неё `chain` и `mode`
из конфига. Комментарии внутри таблицы и порядок всё равно пропадали бы.

**D10. Конфиг сессии: собственные клавиши браузеров — Shift+Super+буква,
клавиши `surf` — прежние.** `chrome`, `chrome-ai` и `yandex-browser` получают
собственные `chain` Shift+Super+B, Shift+Super+V, Shift+Super+Y, а записи
`surf` переопределяют их на Super+B, Super+V, Super+Y. Что видит пользователь:

- в `surf` Super+B/V/Y работают как раньше;
- на столе с `work` Super+B/V/Y поднимают `surf`, как раньше (шаг 3 D4);
- Shift+Super+B/V/Y на столе с `work` перетаскивают окно браузера в `work`,
  оно становится общим (случай «в»), а если `surf` не запущен, открывают
  браузер в `work` (случай «а»);
- на столе без активного workspace Super+B/V/Y поднимают `surf`,
  Shift+Super+B/V/Y тоже (шаг 4 D4 без `W`).

Сочетания Shift+Super+B, Shift+Super+V и Shift+Super+Y свободны: проверено
по `workspaced keys --list` 23.09.2026. Комментарий в `hyprland.lua`
о мозаике dwindle «через Super+Shift+V» привязки не имеет и устарел; его
нужно поправить тем же изменением.

Рассмотренные варианты:

- *Буквально как в примере документа*: собственная клавиша `chrome-ai`
  остаётся Super+V, а `surf` получает новую. Отвергнут: в `surf`, где
  пользователь работает с браузерами чаще всего, сменились бы все три
  привычные клавиши. Документ описывает механизм (собственная клавиша
  перетаскивает, клавиша workspace поднимает), а не конкретные сочетания;
  механизм тот же.
- *Переопределить только `chrome-ai`.* Отвергнут: правило «Shift+Super+буква
  браузера — забрать его окно сюда» проще запомнить, когда оно действует для
  всех браузеров `surf`.
- *Завести семейство Chrome.* Отвергнут: ни один workspace сессии не
  описывает все окна Chrome одной записью, и общая клавиша семейства была бы
  не нужна (решение D11 `app-families` остаётся в силе).

**D11. Сессии не меняются.** Записи дополнительных приложений сессии
(`ExtraApp`) несут класс, команду, каталог и прямоугольник; ключа и режима
в них нет, и ключ такого приложения в workspace — его собственная клавиша,
а режим — по правилу D7 (без ячейки — `stack` в workspace режима `swap`).
Снимок сессии и его формат не меняются; переопределения живут в файле
конфига.

**D12. Сценарий «Приложение без workspace» уточняется.** Требование «Цепочка
приложения» шага 4 говорит, что второе нажатие цепочки калькулятора
«возвращает фокус окну главной ячейки `dev-front`». С правилом D7 калькулятор
выбирается в режиме `stack`, и prev — окно, активное до первого нажатия. Если
это окно главной ячейки, результат тот же; формулировка сценария меняется
на «возвращает фокус окну, активному до первого нажатия».

**D13. Workspace, описывающий приложение через семейство, откликается на его
собственную клавишу (принято при реализации 23.09.2026).** Шаг 3 решения D4
считает откликом запущенного `V` не только запись с ключом `K`, но и описание
приложения из `Own(K)` через семейство: у варианта без своей записи в `V`
переопределения нет, и его собственная клавиша в `V` ведёт цикл (шаг 2 D4,
решение D6). Без этого уточнения шаги 3 и 4 такой `V` не видели бы: шаг 3 —
потому что у `V` нет записи с ключом `K`, шаг 4 — потому что `V` клавишу
не переопределял, и клавиша открывала бы вариант в текущем workspace,
отнимая его окна у `V`, хотя `V` на неё откликается. Команда
`workspaced app` по решению D5 уже считала описание через семейство
откликом, поэтому уточнение выравнивает клавишу с командой. Дельта ws-daemon
(«Цепочка приложения», шаг 3) дополнена той же оговоркой.

**D14. Запись-таблица без переопределений пишется короткой формой (принято
при реализации 23.09.2026).** `save_workspace` меняет у записи-таблицы только
поле места на прежней позиции, если в ней есть `chain`, `mode` или другие
поля. Запись `{ rect = … }` без других полей — это прежняя короткая форма
окна вне ячейки, и окно, вернувшееся в ячейку, записывается строкой, как
до шага: иначе в файле появлялась бы третья форма `{ cell = "left" }` для
записи без переопределений, а обратный путь строка → `{ rect }` → строка
перестал бы быть симметричным. Если таблица `apps` раздела записана в одну
строку и в неё добавлена запись, строка форматируется заново (пробел перед
закрывающей скобкой иначе оказывается перед запятой); комментариев в такой
таблице не бывает. Дельта ws-config («Запись по команде сохранения»)
уточнена.

**D15. Ошибка места запоминается при разборе, отказ даёт проверка (принято
при реализации 23.09.2026).** Запись приложения разбирается собственным
посетителем serde: строка — ячейка, таблица — поля `cell`, `rect`, `chain`,
`mode`, а неизвестный ключ пропускается через `IgnoredAny`, и обёртка
`serde_ignored` пишет предупреждение с полным путём
(`workspaces.pair.apps.chrome-ai.colour`). Запись без места или с обоими
полями разбор не отклоняет, а отмечает полем `WsApp::place_error`: отказ
с именами workspace и приложения выдаёт `Config::validate`, где эти имена
известны (решение D8). Поэтому у `WsApp` кроме `place`, `chain` и `mode`
есть четвёртое поле, которого нет в задаче 1.1.

## Risks / Trade-offs

- [Одна цепочка означает разное в разных workspace, и пользователь может
  не помнить, что `K` делает здесь] → `workspaced keys --list` показывает
  все отозвавшиеся записи в колонке источника; в конфиге сессии правило одно
  для трёх браузеров (D10).
- [Копия `keys.lua` прежней версии вызывает `workspaced app chrome` для
  Super+B, а конфиг назначает `chrome` клавишу Shift+Super+B] → копия
  нужна только при ошибке конфига; после перезагрузки конфига композитора
  демон сам вызывает `hyprctl reload config-only`, и код привязок
  печатается заново.
- [Переопределение, совпавшее с собственной клавишей другого приложения
  из другого workspace, делает одну цепочку общей для двух приложений]
  → это прежнее правило «одна цепочка у приложений разных workspace
  допустима»; выбор делает активный workspace (шаг 1 D4).
- [Смена `chain` или `mode` в записи workspace меняет раздел, и перечитывание
  конфига пересобирает назначения ячеек этого workspace, отменяя обмен
  ячеек, сделанный клавишей] → так уже действует любая правка раздела
  («Слежение за конфигом»); сравнивать только места — усложнение без явной
  пользы.

## Migration Plan

Бинарник собирается и подменяется, `workspaced.service` перезапускается;
демон перечитывает конфиг и вызывает `hyprctl reload config-only`, после чего
Super+B/V/Y и Shift+Super+B/V/Y вызывают `workspaced key`. Конфиг сессии
меняется тем же изменением после подмены бинарника: прежний бинарник таблицу
с `cell` и `chain` не читает. Откат — прежний бинарник вместе с прежним
`config.toml` (`git revert` правки конфига и `chezmoi apply`).
