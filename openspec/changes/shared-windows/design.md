# Design: Общие окна

## Context

Мотивация — в `proposal.md`, замысел целиком и место шага в серии —
в [`docs/window-model.md`](../../../docs/window-model.md): раздел 2.4
(геометрия и память о состоянии окна), раздел 2.5 (принадлежность окон,
таблица клавиши приложения, Super+Backspace), раздел 5, шаг 4. Решения
прежних шагов действуют и здесь:
[`app-families`](../archive/2026-09-22-app-families/design.md) — теги
экземпляров (D4, D5), правило места окна (D7), глубина стопки (D8), захват
всех окон семейства или варианта (D9), место первого экземпляра при записи
(D15); [`key-cycle-stack`](../archive/2026-09-22-key-cycle-stack/design.md) —
цикл по экземплярам, режим `stack` и память прямоугольников по workspace (D9);
[`windows-join-workspace`](../archive/2026-09-23-windows-join-workspace/design.md)
— принятие появившегося окна (D1, D2), отделение окна (D5), снимок только
по команде (D6), порядок окон по глубине (D8);
[`move-desktop-successor`](../archive/2026-09-23-move-desktop-successor/) —
преемник на прежнем столе.

Что есть сейчас в демоне (коммит `3f78938`, после изменения
[`classless-windows-stay-free`](../archive/2026-09-23-classless-windows-stay-free/design.md)):

- Тег `app:<имя>#<номер>` связывает окно с приложением. Состав workspace
  в тегах **не** хранится: окно входит в workspace, если workspace описывает
  его приложение или семейство в эффективном конфиге (файл вместе
  с дополнительными приложениями сессии). Так считают `placed_windows`,
  `ws_app_of`, `remember_geometry`, `detach_step`, парковка в `raise_on`
  и `state_json`. Поэтому «общее окно» сейчас — это окна приложения, которое
  описано в двух workspace, и они уходят за последним поднятием.
- `raise_on` переносит на стол все окна приложений workspace, откуда бы они
  ни были, и паркует на `special:pool` окна приложений, которых
  в поднимаемом workspace нет.
- `st.geom` уже хранит прямоугольник окна отдельно для каждого workspace
  (решение D9 `key-cycle-stack`), `st.cells` — назначения ячеек
  по приложениям.
- `detach` закрывает окно всегда (решение D5 шага 3).
- Цепочка приложения, не описанного в активном workspace, поднимает первый
  подходящий workspace текущего стола, затем другого стола, а если такого
  нет в списках — первый workspace конфига с этим приложением на текущем
  столе (ветвь «3б» в `Daemon::app`).
- Изменение `classless-windows-stay-free` оставило свободными окна без
  класса, развело по именам разные программы с одним классом и научило
  `detach` снимать запись дополнительного приложения с командой во всех
  workspace сразу (`drop_extra_app`): тогда окно входило ровно в один
  workspace, и его закрытие означало уход программы из сессии. С этим
  пересекается решение D9.

## Goals / Non-Goals

**Goals:**

- Окно может входить в несколько workspace, и это переживает перезапуск
  демона.
- Общее окно стоит там, где работает пользователь, и возвращается
  в запомненное для каждого workspace состояние.
- Super+Backspace убирает окно из одного workspace, не закрывая его, пока
  окно нужно другому.
- Одно правило размещения общего окна для всех операций: поднятие,
  вытеснение, перенос, преемник, смена стола, отделение, удаление workspace
  из списка стола.

**Non-Goals:**

- Переопределения на уровне workspace (шаг 5).
- Общее окно в плитках обоих столов (шаг 6).
- Состав workspace и прямоугольники режима `stack` в снимке сессии (шаг 7).

## Decisions

**D1. Состав хранится тегом `ws:<имя>` у окна, по тегу на каждый workspace.**
Окно входит в workspace `W`, если у него есть тег `ws:W`. Тег ставится тем же
диспетчером `tag`, что и тег экземпляра, и так же читается из
`hyprctl clients -j`. Вывод состава из описания приложения в конфиге,
как сейчас, остаётся только в сверке для окон без тегов состава (D2).

Инвариант: тег `ws:W` есть только у окна, приложение которого (само или его
семейство) описано в `W` эффективного конфига. Поэтому каждое вхождение окна
в workspace, где приложение не описано, заводит запись о месте в сессии —
так уже делает принятие окна (решение D2 шага 3), так же делает
перетаскивание (D8). Из инварианта следует, что правило места окна
(решение D7 `app-families`) для члена `W` всегда находит запись приложения
или его семейства, и что клавиша приложения по-прежнему узнаёт «приложение
входит в `W`» по конфигу.

Рассмотренные варианты:

- *Состав по приложению, как сейчас.* Отвергнут: нельзя убрать из workspace
  одно окно, не убрав приложение целиком, и нельзя перетащить одно
  приложение, не сделав общими все его окна во всех workspace, описывающих
  его. Super+Backspace и перетаскивание в такой модели не выражаются.
- *Один тег со списком workspace* (`ws:work,surf`). Отвергнут: каждое
  изменение — снятие прежнего тега и постановка нового, два диспетчера
  вместо одного, а между ними окно на мгновение без состава; разбор списка
  сложнее разбора отдельных тегов.
- *Список в памяти демона.* Отвергнут: перезапуск демона терял бы состав,
  хотя номера экземпляров он не теряет (`docs/window-model.md`, оговорка
  про сессии в разделе 5), и после перезапуска общие окна снова стали бы
  общими по приложению.
- *Состав в снимке сессии.* Отвергнут для этого шага: снимок пишется только
  по команде сохранения (решение D6 шага 3), и изменения состава между
  сохранениями перезапуск демона отменял бы. Запись состава в снимок —
  задача шага 7, и там она дополнит теги, а не заменит их.

**D2. Окно входит в workspace по четырём событиям и выходит по трём;
состав сверяется с конфигом.** Входит (`docs/window-model.md`, раздел 2.5):
демон запустил окно для workspace (`adopt` с `Pending.workspace`); окно
появилось на столе с активным workspace (`join`, `capture_new`); workspace
забрал окно при поднятии (D3); окно перетащено в workspace (D8). Выходит:
Super+Backspace (D9); окно закрыто; сверка с конфигом.

Сверка выполняется там же, где сейчас снимаются теги исчезнувших
приложений (`free_stale_tagged`: после перечитывания конфига, при старте
демона, при загрузке сессии). Тег `ws:W` снимается, если `W` нет
в эффективном конфиге или `W` не описывает приложение окна. Окно, у которого
тегов состава не осталось, становится свободным окном приложения: тег
экземпляра остаётся, окно стоит, где стояло.

Окно с тегом экземпляра, но без тегов состава, при старте демона получает
состав по прежнему правилу, чтобы переход на новую версию не рассыпал
workspace: окно на столе, где активен workspace, описывающий его приложение,
входит в этот workspace; окно на `special:pool` входит во все workspace
из списков столов, которые описывают его приложение и не активны; иначе окно
остаётся свободным. То же правило действует после загрузки сессии: окна,
переиспользованные загрузкой, приходят без тегов состава, если их запустил
прежний демон. Отвергнуто: не выводить состав вовсе и ждать поднятия — до
первого поднятия окна `work` не входили бы в `work`, и поднятие `surf` на том
же столе оставило бы их на месте.

**D3. Поднятие забирает окна других workspace, только если в поднимаемом
окон приложения нет.** Для каждого приложения поднимаемого workspace `W`
порядок такой: свободные подходящие окна (без тега, с тегом исчезнувшего
приложения, с тегом экземпляра без состава) захватываются всегда, как
сейчас; если после этого у приложения нет ни одного окна в `W`, демон
добавляет тег `ws:W` окнам этого приложения, входящим в другие workspace
(«забирает в общее пользование»: по семейству — все окна семейства,
по варианту — окна варианта, решение D9 `app-families`); запуск — только
когда окон не нашлось и там. Окна, которые уже есть в `W`, демон не
дополняет окнами других workspace.

Документ (раздел 2.5, «Общие окна») говорит: «при поднятии workspace сначала
ищет окна для своих приложений среди открытых окон любого запущенного
workspace и забирает их… Новое окно запускается только тогда, когда
подходящего не нашлось». Условие «сначала ищет… новое запускается, когда
не нашлось» здесь прочитано как поиск вместо запуска: он нужен тогда, когда
в `W` окна приложения нет.

Рассмотренные варианты:

- *Забирать все окна приложения при каждом поднятии.* Отвергнут: это
  возвращает состав по приложению (D1), второе окно браузера, открытое
  в `V`, при следующем поднятии `W` становилось бы общим само, а
  Super+Backspace отменялся бы первым же поднятием.
- *Не забирать, а запускать новое окно.* Отвергнут: противоречит документу
  и даёт второй экземпляр приложения там, где пользователь ждёт своё окно.

Следствие, принятое сознательно: Super+Backspace над последним окном
приложения, которое описано для `W` в файле конфига, убирает окно из `W`
до следующего поднятия `W`. Описание в файле требует окна приложения, и
поднятие найдёт его в другом workspace. Убрать приложение из `W` насовсем
можно только правкой файла. Для приложения, попавшего в `W` сессией
(принятием или перетаскиванием), такого нет: вместе с последним окном
снимается и запись (D9), и `W` приложение больше не описывает.

**D4. Размещение общего окна — одно правило из четырёх шагов.** Чистая
функция `window_home` отвечает, где должно стоять окно, входящее в workspace:

1. на столе, где сейчас композитор, если активный там workspace содержит
   окно;
2. иначе на своём нынешнем столе, если активный там workspace содержит окно;
3. иначе на столе с наименьшим номером, где активен workspace, содержащий
   окно;
4. иначе на `special:pool`.

Окно на `special:hidden` правило не трогает никогда. Правило применяют
поднятие (к окнам поднимаемого workspace и к окнам, уходящим со стола),
смена стола (D5), перенос workspace и поднятие преемника (D10), отделение
окна (D9), удаление workspace из списка стола (`remove`). Шаги 1 и 2 и есть
«следование за пользователем» из документа; шаги 3 и 4 отвечают на вопрос,
которого документ не касается: куда уходит общее окно, когда пользователь
не на столе ни одного из его workspace.

Рассмотренные варианты:

- *Последний посещённый стол вместо наименьшего номера в шаге 3.* Отвергнут
  на этом шаге: нужен журнал посещений столов, а случай — окно в трёх
  workspace, два из которых активны на разных столах, а пользователь на
  третьем — редок. Правило однозначно и легко проверяется; заменить шаг 3,
  если случай окажется частым, можно, не трогая остальных.
- *Окно следует за последним поднятием* — нынешнее поведение, которое шаг
  и снимает (`docs/window-model.md`, раздел 1).
- *Окно остаётся там, где стоит, пока его не позовут клавишей.* Отвергнут:
  документ требует следования за пользователем, а окно, пропавшее из
  workspace после перехода на стол, выглядит закрытым.

**D5. Следование — по событию смены стола, стол уточняется у композитора.**
Обработчик события `workspace` (номер стола 1…8), кроме ленивого поднятия,
переносит на новый стол окна активного там workspace, которые стоят на
других столах или на `special:pool`, и ставит их в состояние для этого
workspace (D6). Прежде чем двигать окна, обработчик спрашивает текущий стол
у композитора (`sync_current`): событие приходит отдельным соединением
и может отстать от команды демона, а по устаревшему событию общее окно
уехало бы со стола, где пользователь уже находится. Фокус демон не трогает:
при смене стола его передаёт композитор; окно, у которого после переноса
фокус, демон поднимает наверх, чтобы перенесённое окно не заслонило его.

Рассмотренные варианты:

- *Переключать столы только через демон* (Super+1…8 — действием демона,
  а не диспетчером композитора), чтобы окна переехали до смены стола и не
  появлялись с запаздыванием. Отвергнут как единственный механизм: стол
  меняется и помимо клавиш (клик по плитке панели, запрос активации окна,
  переход композитора за перенесённым окном), и обработчик события нужен
  всё равно. Как дополнение к событию его можно ввести позже, если
  запаздывание окажется заметным; решение записано здесь, чтобы не
  изобретать его заново.
- *Опрос положения окон.* Запрещён правилом о таймерах
  ([`docs/decisions/0007-no-timers.md`](../../../docs/decisions/0007-no-timers.md)).

**D6. Состояние общего окна — своё в каждом workspace, по режиму этого
workspace.** Это правило `docs/window-model.md`, раздел 2.4, и шаг его не
меняет, а применяет к следованию. В режиме обмена ячеек окно встаёт
в ячейку своего приложения в том workspace, куда пришло (`st.cells` уже
хранит назначения по workspace; одно окно в двух workspace стоит в двух
разных ячейках). В режиме `stack` окно встаёт в прямоугольник
`st.geom[W][адрес]`, а без него — на место из конфига. Прямоугольник
в режиме `stack` запоминается и перед тем, как окно уходит со стола
workspace за пользователем, а не только перед парковкой: иначе ручная
подгонка общего окна в `surf` терялась бы при каждом переходе на стол
`work`. Перенос workspace на другой стол по-прежнему расстановкой
не считается: окна, которые едут вместе с workspace, сохраняют
прямоугольники (решение изменения `move-desktop-keeps-geometry`).

Отвергнуто: один прямоугольник на окно для всех workspace — документ прямо
требует двух разных запомненных мест.

**D7. Клавиша приложения — три случая таблицы документа.** Порядок выбора
в `Daemon::app`:

1. приложение описано в активном workspace текущего стола `W` — цикл в `W`,
   как сейчас;
2. задан признак перетаскивания и на столе есть `W` — перетаскивание (D8);
3. приложение описано в запущенном workspace `V` — поднять `V` (случай «б»):
   сначала по списку текущего стола, затем на столе с наименьшим номером,
   как сейчас;
4. на столе есть `W` — открыть приложение в `W` (случай «а») по правилам
   захвата при поднятии (D3): свободные окна захватываются, без них окна
   других workspace (в том числе не запущенных, оставшихся
   на `special:pool`) становятся общими, и только без окон приложение
   запускается; окна входят в `W` с записью о месте;
5. активного workspace на столе нет — цикл по окнам приложения вне
   workspace, как сейчас.

«Запущенным» считается workspace, который числится в списке какого-либо
стола, в том числе ожидающий ленивого поднятия. Ветвь «3б» нынешнего кода
(поднять на текущем столе workspace конфига, которого нет ни в одном списке)
снимается: по таблице документа это случай «а». Случай «в» без
переопределений шага 5 наступает только по явному признаку `pull`.

Рассмотренные варианты:

- *Оставить ветвь «3б».* Отвергнут: документ относит этот случай к «а», а
  поднятие чужого workspace на текущем столе вытесняет тот, в котором
  пользователь работает.
- *Выразить случай «в» без переопределений*, например считать, что `V`
  «переопределяет» клавишу, когда `V` активен на другом столе. Отвергнут:
  это подмена условия документа, и в шаге 5 её пришлось бы отменять.

**D8. Перетаскивание — операция `app --pull`, без новой клавиши в конфиге.**
Команда `workspaced app <имя> --pull` и действие `[[binds]]`
`{ app = "<имя>", pull = true }` добавляют окна приложения в активный
workspace текущего стола `W`. Берутся те же окна, что забирает поднятие
(D3): все окна приложения (по семейству — семейства, по варианту —
варианта), кроме скрытых, из любых workspace и свободные; из прежних
workspace они не уходят. `W` получает запись о месте приложения: для
приложения файла конфига — запись без команды, как при принятии окна
(решение D2 шага 3); для дополнительного приложения сессии другого
workspace — полную запись с классом, командной строкой и каталогом, как
делает `join_window` для такого случая. Место — по правилу места окна,
а без записи — центр экрана с размером окна. Окна переезжают на текущий
стол (D4, шаг 1), и цикл начинается с первого экземпляра. Если у приложения
окон нет, перетаскивание сводится к случаю «а»: приложение запускается в `W`.
Если приложение в `W` уже описано, признак ничего не меняет — идёт обычный
цикл.

Перетаскиваются все окна приложения, а не одно активное: так одно правило
«забрать в общее пользование» действует и при поднятии, и при
перетаскивании, а стопка приложения не делится между workspace. Лишнее окно
убирается из `W` по Super+Backspace.

Клавиши перетаскивания в конфиге сессии шаг не заводит: с шага 5
собственная клавиша приложения, нажатая в workspace, который его не
описывает, перетаскивает окно сама (случай «в»), и отдельная клавиша стала
бы лишней. До шага 5 операцию вызывают командой; проверки агента делают
так же.

Документ относит к шагу 4 требование «Генерация привязок для Hyprland»
(раздел 5), но в разделе 3 оставляет его без изменений, потому что перечня
действий оно не содержит. Здесь принято второе: ключ `pull` описан
в требовании «Цепочки клавиш и привязки», генерация привязок не меняется —
действие демона и так превращается в вызов подкоманды.

Рассмотренные варианты:

- *Отдельная подкоманда `workspaced pull <имя>`.* Отвергнут: перетаскивание
  — один из случаев клавиши приложения, и признак у той же подкоманды
  оставляет шагу 5 единственную точку входа.
- *Новая клавиша в конфиге сессии уже сейчас.* Отвергнут по причине выше.

**D9. Super+Backspace снимает тег, закрывает только последний.** Команда
`detach` снимает с активного окна тег `ws:W` активного workspace текущего
стола. Если у окна остались другие теги состава, окно не закрывается,
а уходит по правилу D4: на стол, где активен другой его workspace, либо на
`special:pool`; фокус демон не назначает. Если тегов не осталось, окно
закрывается штатным запросом, как сейчас. Когда из `W` уходит последнее
окно приложения, у которого в `W` есть запись сессии, запись снимается
в `W`, если окна приложения остаются в других workspace: они продолжают
опираться на свои записи. Если окно закрывается и других окон у приложения
нет нигде, действует правило изменения `classless-windows-stay-free`: запись
с командой снимается во всех workspace (`drop_extra_app`), потому что
программа уходит из сессии. Функцию нужно научить различать эти два случая.

Отвергнуто: закрывать окно всегда (как на шаге 3) — общее окно пропало бы
и из другого workspace; оставлять окно на столе свободным — оно продолжало
бы заслонять окна `W`, хотя пользователь его оттуда убрал.

**D10. Перенос и преемник подчиняются тому же правилу.** Перенос
`move-desktop` — поднятие с явным столом, и общее окно перенесённого
workspace едет с ним: пользователь переходит туда же (D4, шаг 1). Преемник
на прежнем столе поднимается без перехода и потому не забирает общее окно,
которое стоит на столе пользователя в активном там workspace (D4, шаг 1
для чужого стола не выполнен, шаг 2 оставляет окно на месте). Когда
пользователь вернётся на прежний стол, окно придёт туда по событию смены
стола (D5). Вытеснение (`raise_on`) и `remove` уводят со стола окна, не
входящие в поднятый workspace, тоже по правилу D4: общее окно, чей другой
workspace активен на соседнем столе, уходит туда, а не на `special:pool`.

**D11. Панель получает состав по тегам; сама панель не меняется.** В
состоянии для панели список окон workspace строится по тегам `ws:`, и общее
окно стоит в списке каждого своего workspace. В `workspaced status --json`
у окна появляется поле `workspaces`. Панель (`tiles/Workspaces.qml`,
`itemsFor`) берёт окна стола по их фактическому положению и сначала
разбирает активный workspace, поэтому общее окно в двух списках она
покажет один раз — в плитке стола, где окно стоит. Показ в плитках обоих
столов — шаг 6.

**D12. Запись workspace в конфиг — по составу.** Команда `save_workspace`
берёт окна активного workspace текущего стола по тегам. Пользователь
находится на этом столе, поэтому по правилу D4 все нескрытые окна workspace
стоят на нём, и место общего окна читается у композитора как есть.
Приложение общего окна записывается в раздел под своим именем с `rect`
первого экземпляра (решение D15 `app-families`); после записи то же
приложение описано в двух разделах файла, и общее окно становится общим
на уровне конфига: после перезагрузки поднятие второго workspace заберёт
окно первого (D3). Команда сохранения сессии обновляет место записи
дополнительного приложения только по окну, которое стоит на столе своего
workspace; для общего окна, ушедшего за пользователем на другой стол,
берётся запомненный прямоугольник режима `stack`, а в режиме обмена ячеек
запись не меняется.

**D13. Конфликтов «два workspace на одном столе» не возникает.** На столе
активен ровно один workspace, поэтому окно, входящее в активный `W`
и неактивный `U` того же стола, стоит там как окно `W`; при поднятии `U`
на этом столе оно остаётся на месте и встаёт в состояние для `U` (D6).
Окно, чьи workspace активны на двух разных столах, стоит на одном из них
по правилу D4, и какой из столов это будет, решает пользователь, переходя
между ними. Скрытое окно (`special:hidden`) не переносится ни поднятием, ни
следованием, как и раньше.

**D14. Что переживает перезапуск демона и перезагрузку.** Теги живут
в композиторе, поэтому после перезапуска демона общие окна остаются общими,
а окно, убранное из `W` по Super+Backspace, в `W` не возвращается. Записи
дополнительных приложений после перезапуска берутся из снимка, и сверка
(D2) снимает теги `ws:W`, которым записи больше не соответствуют: общее
окно, перетащенное после последнего сохранения, перестаёт быть общим —
это то же правило «изменения после снимка теряются», что действует для
принятых окон (спецификация ws-sessions, «Файлы сессий»). После
перезагрузки тегов нет; общие окна собираются заново по записям снимка
и описаниям в файле: поднятие каждого workspace забирает окна по D3.
Отдельно состав в снимок не пишется до шага 7.

## Risks / Trade-offs

- [Окно при переходе на стол появляется с запаздыванием на время обработки
  события] → переносы и расстановка уходят одной последовательностью
  диспетчеров; если запаздывание заметно, к событию добавляется
  переключение столов через демон (D5).
- [Super+Backspace над окном приложения из файла конфига отменяется
  следующим поднятием] → принято сознательно (D3), описано в требовании
  и в `AGENTS.md`.
- [При первом старте новой версии состав выводится по описанию приложений,
  и окно на `special:pool`, чьё приложение описано в двух неактивных
  workspace, войдёт в оба] → так это окно вело себя и до шага 4; лишнее
  вхождение убирается по Super+Backspace.
- [Приложение, перетащенное в workspace режима обмена ячеек, при выборе
  клавишей занимает главную ячейку, а прежнее главное приложение встаёт
  на его место, заданное прямоугольником] → так уже ведёт себя любое дополнительное
  приложение сессии (`swap_cells`); шаг это правило не меняет, а место
  и режим приложения внутри workspace задаст шаг 5.

## Migration Plan

Бинарник собирается и подменяется, `workspaced.service` перезапускается.
При старте сверка (D2) выдаёт теги состава окнам с тегами экземпляров.
Откат — прежний бинарник: он теги `ws:` не читает и выводит состав
по приложению, как раньше; лишние теги на окнах ему не мешают.
